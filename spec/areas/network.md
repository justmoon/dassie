# Network

How Dassie nodes find each other and stay connected: the node table, link states and how they spread, membership through bootstrap nodes, names, peering and its lifecycle, bans, and routing. The messages these use are in [Peer protocol](peer-protocol.md).

**Paths:** `crates/dassie-peer/src/node/`, `crates/dassie-peer/src/names/registrar.rs`, `crates/dassie-peer/src/names/holders.rs`, `crates/dassie-peer/src/names/registrant.rs`, `crates/dassie-peer/src/table.rs`, `crates/dassie-peer/src/routing.rs`, `crates/dassie-peer/src/channel.rs`, `crates/dassie-peer/src/persist.rs`, `crates/dassie-peer/src/config.rs` (every timer and bound, with the dev values), `crates/dassie-peer/src/hooks.rs`, `crates/dassie-node/src/env.rs` (bootstrap list)
**Read with:** [Peer protocol](peer-protocol.md), [Settlement](settlement.md), [Connector](connector.md), [Identity](identity.md), [Node](node.md)

## The peer node

`dassie-peer`'s `PeerNode` is a sans-IO state machine that `dassie-node` drives; its changes are written in the same transaction as the ledger's ([Node](node.md)). It wakes only when a timer is due. Every table it keeps is bounded, so no other node can grow its memory.

A node's ILP address is `<scheme>.das.<nodeId>`, with the allocation scheme set by the node's realm. A peer is a connector endpoint at its own such address, which ILDCP tells it ([Connector](connector.md)).

## Node table

The table holds what a node knows about other nodes: per node, its key, its newest link state, why it is in the table, its registration with us and our peering with it.

- **A node enters only for a reason:** it is this node, a configured bootstrap node, a peer (or being asked to peer), on the majority of bootstrap lists, or registered with us. A link state of a node not in the table is dropped, so gossip alone cannot fill the table.
- **When the table is full,** a newcomer takes the place of the node whose strongest reason ranks lowest, if that ranks below the newcomer's (self, bootstrap, peer, majority, registered, in that order). Registrations cannot push out the nodes a node depends on.
- A node is removed a grace period after its last reason is gone, with its link state.
- **Downlinks** ([below](#downlinks)) are in the table under a bound of their own: they take no other node's place, and none takes theirs.

## Link states

### The own link state

- A node without a valid URL issues no link state ([Peer protocol](peer-protocol.md#verification)), unless it is a periphery node, whose link state has none ([Periphery nodes](#periphery-nodes)).
- It is issued at start, when its neighbors, schemes, hubs, URL or alias change (debounced), and periodically regardless.
- **Sequence:** `max(now, last + 1)`, with the last value persisted, so it only rises across restarts. If the persisted value is further ahead of the clock than any node accepts, it was issued under a wrong clock and no node holds it; the sequence starts again from `now`.
- A core node's neighbors are its advertised peers ([Advertised peers](#advertised-peers)); a periphery node lists none ([Periphery nodes](#periphery-nodes)). Its schemes are those the node peers on: active, synced with their ledger at least once, and able to receive a peer's settlement ([below](#asking-and-answering)).
- A member of settlement hubs names them, each with its scheme ([Peer protocol](peer-protocol.md#link-states)).
- **It always fits what every node decodes.** Its neighbors are bounded by the core peering slots, its schemes by `MAX_SCHEMES` and its hubs by `MAX_OWN_HUBS` (`crates/dassie-peer/src/node/mod.rs`), and the configuration is checked at start against the link state's bounds in entries and bytes ([Peer protocol](peer-protocol.md#link-states)), so a node never signs one that others refuse.
- A new own link state is flooded to peers at once, and sent directly to the bootstrap nodes we are not peered with, so they can answer refreshes for it.

### Receiving a link state

Cheap checks come first, so floods are cheap: an echo of our own state, a node not in the table, a sequence not newer than the one held, or a sequence too far in the future is dropped before the signature is checked.

- **Rate per subject.** Each node may issue only a bounded burst of states, then a steady rate; the excess is neither stored nor forwarded. The rate is checked before the signature, but a token is spent only on a state that verifies, so forged states cannot use up the real node's allowance.
- **Freshness.** A state is fresh while its sequence is within a window around now. Routing uses only fresh states, and stale ones are refreshed.

### How link states spread

The gossip defaults (copies before suppression, forward jitter, heartbeat interval, staleness, re-issue) are the original's, kept because they proved sound; the peering timings were set from the network simulation ([peering-lifecycle](../decisions/peering-lifecycle.md)). All are in `crates/dassie-peer/src/config.rs`.

- **Flooding.** A state taken from a `linkStateUpdate` is forwarded after a random delay to every peer except its subject and the peer it came from, unless enough copies arrived meanwhile. Our own new state goes at once. States learned from refreshes, sweeps, registrations and peering requests are not forwarded, nor is a periphery node's, and a periphery node forwards none. Nothing is forwarded to a downlink.
- **Heartbeats.** A node sends its current state to every peer it is not terminating with, advertised or not, at random intervals and once when a peering forms, so both sides can confirm each other ([Advertised peers](#advertised-peers)).
- **Refresh.** A node picks stale or missing states one at a time and asks the node itself, at the URL of its last state; sometimes, or when it has no state of the node, it asks another node instead, together with other stale ones. A node asked about that brings back nothing newer backs off exponentially.
- **Anti-entropy sweep.** Periodically, whether or not anything is stale, a node asks a random peer (or a bootstrap node) for the states of the next few nodes in its table, round and round. Flooding alone loses an update until the next re-issue when a message is lost, a node is down or the network splits; the sweep repairs it within one pass of the table. A peer is not asked for its own state, which its heartbeats bring. A bootstrap node that a node without peers asks is asked for its own state too, whenever the sweep's window holds its ID: once a pass of the table, which for a newcomer, whose table fits in one request, is every sweep. Where it is the only bootstrap node, or the others are out of reach, nothing else brings its state to that node. Without that, a newcomer that registered before its schemes synced, and whose new link state then got lost on the way, would not peer with its bootstrap node until its next re-issue: that holds the newcomer's state without the schemes, and the newcomer has none of the bootstrap node's.

## Membership

The network's members are the nodes that a majority of the bootstrap nodes list. Bootstrap nodes take registrations and serve lists of the nodes registered with them. The design and its economics are [membership-economics](../decisions/membership-economics.md).

### Bootstrap nodes

- The bootstrap node list is `DASSIE_BOOTSTRAP_NODES` (format and validation in `crates/dassie-node/src/env.rs`). A bad entry stops the node at startup, as does a node listed twice, which would vote twice. The default is the public testnet's four nodes ([bootstrap-network](../decisions/bootstrap-network.md)); tests and the dev environment set their own, so they stay off the testnet. An empty list makes a node run alone.
- Bootstrap nodes are always in the table, with their configured key.
- A node takes registrations only when it is one of its own bootstrap nodes, so each bootstrap node lists itself in its own configuration. Each testnet bootstrap node runs `xrpl-testnet-xrp` and `xrpl-testnet-dsusd`, so a new node on either has someone to peer with.

### Node lists and the majority

- A node polls each bootstrap node for its list's hash, and downloads the list when the hash changed. A list is accepted only on a connection pinned to the bootstrap node's configured key ([Peer protocol](peer-protocol.md#message-set)).
- A bootstrap node serves its unexpired registrations and itself. It lists itself and registers with the other bootstrap nodes like any node. It does not serve the majority back, which would keep a node listed forever once it had made it.
- A node is in the majority when strictly more than half of the *configured* bootstrap nodes list it, not of those that answer, so silencing bootstrap nodes cannot shrink the quorum. A list not fetched for a long time no longer votes.
- **Membership freeze.** Majority nodes are added to the table, and lose their place only while more than half of the configured lists are fresh. Otherwise membership freezes, so bootstrap nodes going offline, or a node cut off from them, do not empty every table in the network. The majority set is persisted.

### Registration

**Client side.** A periphery node registers nowhere, and a bootstrap node refuses its registration. Any other node with a link state registers with every bootstrap node other than itself at start, renews before its registration lapses, registers again if a bootstrap node's list still lacks it a while after, and backs off exponentially after failures. The owner can also register at once ([RPC](rpc.md)).

**Bootstrap side.** Registration is free, so it is throttled instead ([roadmap](../roadmap.md#registration-fees)):

- new registrations draw from a global bucket, spent only when a registration succeeds;
- one registration per URL host and port, and a cap per /24 (IPv4) or /48 (IPv6) of the address it came from;
- before accepting a new registration, or one whose URL changed, the bootstrap node probes that URL; a renewal from the probed URL is answered at once;
- a registration expires unless renewed, and the node leaves the served list;

**Probes.** Registration and peering probe the requester's URL the same way: a `linkStateRequest` for the requester itself, on a connection pinned to its key, which must return a verified state of that node at the registered sequence or later. That proves the URL serves the node's key. Since a requester picks the URL, probes are rate-limited, never made twice at once to the same node or host, and the requests waiting on them are bounded; a node cannot be used to hammer a third party.

Every probe spends a token of the node's probe bucket, whatever its outcome: failing probes are what it is there to stop. In front of it, each /24 (IPv4) or /48 (IPv6) the requests come from has a small share of its own. A probe holds a token of its network's share while it is in flight and gives it back if it succeeds, so only failing probes spend the share. One network's failing probes therefore cannot starve requesters from other networks: keeping the bucket empty takes failing probes from many networks at once. Nodes that share a network spend nothing on probes that succeed, and wait only while a share's worth of them is in flight. Loopback is no network where private peers are allowed ([HTTP](http.md)), so dev nodes draw only on the bucket. The shares are bounded in number; when they are full, the network that has spent least loses its share first.

### How a node joins

1. It registers with each bootstrap node, which probes its URL and lists it.
2. Other nodes poll the lists; once a majority lists it, they add it to their tables.
3. They learn its link state from refreshes, sweeps or flooding.
4. Nodes that peer with it advertise it as a neighbor, which makes it routable.

## Names

A node's owner can register a name for the node's ID, held by the bootstrap nodes as its registrars ([the design](../designs/names.md), [names-by-earliest-commitment](../decisions/names-by-earliest-commitment.md)); the messages are in [Peer protocol](peer-protocol.md#names). The registrar's side is built, releasing a split included: the rule in `crates/dassie-peer/src/names/registrar.rs`, who may ask what in `crates/dassie-peer/src/node/names.rs`. So is every node's view of who holds a name, in `crates/dassie-peer/src/names/holders.rs`, which needs nothing of the peer node, so that a front door keeps one too and serves a name for its holder ([HTTP](http.md#front-doors)); and the registrant, which registers names for its node and renews them, in `crates/dassie-peer/src/names/registrant.rs`. A node answers Open Payments under the names it holds, and its client takes an answer under a name only from the name's holder ([Payments](payments.md#the-nodes-names)). Fees are not built ([roadmap](../roadmap.md#names)). Names work only once every bootstrap node runs a release that has them: an older one refuses their messages with 400 ([Peer protocol](peer-protocol.md#versions)), and a registration is abandoned while any registrar refuses, so the bootstrap nodes are upgraded first.

**Testnet only, until fees.** Names run in the test realm only. A node of the `live` realm has names off (`names_enabled` in the peer protocol's `Config`, derived from the realm by the node's engine, `names_enabled` in `crates/dassie-node/src/engine/core/mod.rs`; the peer protocol knows no realm): it is no registrar, though one of its own bootstrap nodes, and refuses every name message with 409 as any other node does; it reads no name lists and holds no names; and it refuses the owner's registrations and renewals as a failed precondition that says why, which the wallet shows instead of the form. Names are free and only throttled, so on a network with real money whoever registers first could keep the names worth having for good; on the testnet that costs nothing, since its names may be reset at any time. Names come to the live realm with registration fees ([roadmap](../roadmap.md#names)).

### The registrar

A node is a registrar when it is one of its own bootstrap nodes, as it takes registrations only then ([Bootstrap nodes](#bootstrap-nodes)). Any other node refuses every name message with 409, the list requests too: only registrars' lists count. Everything a registrar decides is by its own log and clock; registrars never agree on time or order with each other.

- **The log.** A commitment is logged at the next position and at the registrar's time, `max(now, last + 1)`, both persisted, so both only rise across restarts, as the own link state's sequence does ([The own link state](#the-own-link-state)). Its window closes a set time after it was logged. It is on disk, in the batch that logs it, before its receipt goes out, so a crash loses no receipted commitment and never reorders the log. A restart keeps every commitment and name on disk, even beyond bounds a later release lowered: the bounds then refuse new commitments until there is room again, as the log's windows close and freed names are forgotten. A commitment in the log sent again gets its receipt again, at no cost, since a registrant retries until it holds every receipt.
- **Unsealing.** An unsealing is valid if it opens a commitment in the log, sealed for its sender, before the commitment's window closes, for a name that is not reserved, and the name was neither listed nor in its grace period here when the commitment was logged. An invalid one is refused with 409. A valid one is answered alike whether it still contends for the name or has lost already, to a name granted since its commitment was logged, so the answer says nothing of commitments still sealed. One taken already is answered as taken for as long as its commitment is in the log, after its window closed too, so a registrant whose answer was lost and who retries late counts the registrar as having taken it, as it has.
- **Deciding.** As windows close, commitments are decided in the order of the log. One never unsealed lapses. One that contends is granted the name if no commitment earlier in the log won it, and only once every earlier window has closed, since until then an earlier commitment can still take the name; nothing about a name is shown before. The rest lose. So the commitment logged first among a name's valid unsealings wins, whenever it was unsealed, and a name waits a window before it is granted.
- **Holding.** A granted name is listed for a lifetime. Its holder alone renews it, once its expiry is near, to a lifetime past that expiry, or in its grace period, to a lifetime from now; a renewal before its expiry is near is answered with the expiry it has, so a holder cannot move the list's hash at will. Unrenewed, it leaves the list at its expiry, stays the holder's for its grace period, and is then free. What it was is kept until no commitment in the log was logged while it was held, so such a commitment stays void for it.
- **The list** is the names listed, with their holders and expiries, sorted by name, served by hash and download like the node list ([Node lists and the majority](#node-lists-and-the-majority)), and rebuilt only once a grant, a renewal or an expiry changed it. Its bound, `MAX_NAME_LIST`, holds the bound on names below.
- **Free, so throttled,** as registration is until there are fees ([roadmap](../roadmap.md#registration-fees)). New commitments draw from a global bucket, spent only on one logged; the log holds a bounded number from each /24 or /48, and from each node, which together with the names it holds stay under a cap of their own. That cap is also the holder's: an unsealing is refused with 409 once the node named in it holds that many names with its unsealings that contend, so commitments other nodes log for a node, which count against their senders, do not take it past the cap. The log is bounded, and so are the names with the commitments in the log, each of which may become one, so a grant never finds the names full. A bound refuses with 503, a cap with 409 and the bucket with 429, as for registration.
- **Events in counts.** Each step of the registrar's timer reports what it decided, names granted, unsealings lost, commitments lapsed and names freed, in one event of counts, however many it decided; what it lists is read from its state. The node's event queue is bounded and drops its oldest, and a registrar back after a downtime past its windows or its names' grace may decide every commitment and free every name in one step, after the peering events of the same tick, which the node acts on, were queued.
- **Timers and bounds** are `RegistrarConfig` (`crates/dassie-peer/src/names/registrar.rs`). The window gives a commitment and its unsealing each a request's time and retries (`least_window_ms`); renewals and the grace period leave room for a renewal to be retried at the longest backoff; the wait before a split is released is longer than a registration, or a renewal that arrived late, takes to reach every list (`least_release_ms`, [below](#releasing-a-split)); a list stays fresh for less than a window ([Holders](#holders)); dev values follow production's rules (`Config::DEV`).

### Holders

Every node, a registrar too, takes as a name's holder the node that a quorum of the configured registrars list for it ([the design](../designs/names.md#5-holding-a-name)).

- **Reading the lists.** A node polls each registrar's name-list hash with its node list, at the same interval, and downloads the list only when the hash changed. A list is taken only on a connection pinned to the registrar's configured key, as a node list is ([Node lists and the majority](#node-lists-and-the-majority)). A registrar's own list is its own, without asking.
- **The quorum** is n - f of the n *configured* registrars, not of those that answer, where f is the largest with n ≥ 3f + 1: three of four, four of five, and all of up to three. A quorum is more than two thirds, so it names at most one holder for a name, and any two quorums share an honest registrar, which lists one holder: a registrar that shows nodes different lists cannot lead two of them to different holders. A strict majority, as membership takes, would let one such registrar do that after an honest split ([names-by-earliest-commitment](../decisions/names-by-earliest-commitment.md)).
- **Votes and the freeze.** Only a fresh list votes, unlike for membership, and the holders are taken only while a quorum of the lists are fresh. An honest registrar lists a new holder for a name only a window after it stopped listing the last, at a release or the end of a grace period, and a list is fresh for less than a window, counting the time it took to fetch (`Config::validate`); so the fresh lists two nodes vote with never show one honest registrar listing two holders, which the quorum's argument needs. That window is the registrar's clock's, so the argument assumes an honest registrar's clock never steps forward by more than the margin between a window and a list's freshness with its fetch: a larger step would bring its listing of the next holder within a list's freshness of its last listing of the previous one. A list kept from before a release would lend the honest registrar's vote to a holder it no longer lists, and with one faulty registrar give two nodes different holders. Otherwise the view freezes: it keeps every holder it had, one whose name has expired since too, rather than lose names to registrars going down or to a node cut off from them. The view is persisted, so a freeze outlasts a restart; until a quorum of the lists are fetched after it, the node keeps what it had.
- **The expiry** a node shows for a name is the latest one a quorum of the lists give it, by the registrars' clocks.
- **No registrars configured**, no list can confirm a persisted view: a node with no bootstrap nodes holds no names in its view, and removes the persisted one.
- **One event per change of the view.** Taking the view again reports that it changed, with how many names gained a holder and lost one, in a single event however many names changed; a registrar's releases in one check are one event too. The node's event queue is bounded and drops its oldest, and one list going stale can take every name away at once: per-name events would push out the peer events the driver acts on in the same tick. Whoever needs the names reads the view.
- **Bounds.** The registrars are the bootstrap nodes, at most `MAX_REGISTRARS`, each list is bounded by `MAX_NAME_LIST`, and a holder needs more than two thirds of the lists, so a view holds at most `MAX_HOLDERS`, one and a half lists' worth (`crates/dassie-peer/src/names/holders.rs`).

### Releasing a split

Two registrants that commit to a name at nearly the same time may be logged in different orders by different registrars and split the vote, so that no holder has a quorum. A registrar releases a split rather than keep the name from everyone until it expires ([the design](../designs/names.md#5-holding-a-name)).

- **The rule.** A registrar drops a name it lists when more than f of the other registrars' fresh lists lack its holder for it, listing nobody or another node, for longer than a set wait (`release_after_ms`). The name is free at once there: a new commitment may have it, while one logged while it was held stays void for it.
- **Never a holder with a quorum.** A holder that a quorum of honest registrars list is missing from at most f lists, so it is never released, however late or seldom the lists arrive: a list not fresh counts for nothing, nor one not fetched.
- **Not for a registration or a renewal on its way.** A registration's commitments are all logged within the first one's window, so every registrar grants it within a window of the first; a renewal that reached a registrar late lists the name there again at most a renewal's retries after it expired there, as its grace allows; a list fetched before stays fresh for a while, and the next one comes a poll and a download later. The wait is longer than all of these together (`least_release_ms`), so lists that are merely late release nothing.
- **Checked at each poll** and after each list read, by the registrar's own view of the others' lists; a check that finds the name not split starts the wait again. The wait is not persisted: after a restart it starts again, which only delays a release.
- **A faulty registrar** can keep a split from being released, by showing each side its own holder confirmed, and can have a name released whose quorum needed its own list, by showing the registrars that list it another holder.

### The registrant

A node registers a name for itself when its owner asks ([RPC](rpc.md), [Wallet](wallet.md#pages)), at every configured registrar, and renews the names it holds ([the design](../designs/names.md#3-registering)). A periphery node does too, reaching the registrars over the connections it opens, as it reads their lists ([Periphery nodes](#periphery-nodes)); a registrar commits and unseals at itself as at the others. The steps are `crates/dassie-peer/src/names/registrant.rs`; `crates/dassie-peer/src/node/names.rs` sends them.

- **Starting.** A name is refused when it is reserved, when the node holds it, when a fresh list names anyone for it, since a commitment logged while the name is listed is void there ([The registrar](#the-registrar)), while as many registrations are under way as a registrar logs from one node, and while the names the node holds with its registrations under way reach the names a registrar grants one node, which counts its commitments with its names alike. A finished registration gives way only to one that starts. The salt comes from the node's RNG, and the registration is on disk with it in the batch before its first commitment leaves, so a restart commits to the same commitment again, which a registrar that logged it answers with the same receipt.
- **Committing.** The commitment goes to every registrar at once, and to each again with a backoff until it answers with its receipt. The window is counted from when the registration started, which is no later than any registrar logged it, less a margin for clocks that run at different rates (`CLOCK_RATE_PERCENT`). A registration that does not hold every receipt while an unsealing would still have a request's time is abandoned, and no registrar learns the name: a registrar that is down or refuses blocks a registration rather than becoming a vote it cannot count on ([the design](../designs/names.md#6-why-it-holds)).
- **Unsealing.** With every receipt, the node unseals at every registrar at once, each again until it answers or the window closes; a 409 is final there. A restart while unsealing unseals again, which a registrar that took it answers alike.
- **Decided by the view** ([Holders](#holders)): held, and the registration is done; lost, to another holder; split, while the fresh lists name this node and another for it; or not held, once a window and the wait before a split is released have passed. A finished registration stays for the owner to see, and gives way to a new one, the oldest first, when the registrations are full; the name may be registered again, with a new salt.
- **Renewing.** A name is the node's while its view gives it the name, or more than f fresh lists name it, so at least one honest registrar; and, once it has expired, for the registrars' grace period after the latest expiry these gave, so that a registrar whose renewal came late is renewed in its grace period even after the view lost the quorum. One they stop showing before it expires was released or lost, and is the node's no more. Each of its names is renewed at every registrar that does not list another node for it, once the expiry that registrar last gave it, in its list or in its answer to a renewal, is within the time to renew; at a registrar that never gave one, once the expiry the view or the lists gave is. An answer that leaves the name due, from a registrar whose clock is behind, is asked again after a backoff, as a failure is; so is a registrar that lists nobody for the name and answers 409, until the name is the node's no more. The owner may renew at once, which a registrar takes only once the expiry is near.
- **The registrars' rules** (their window, the time to renew, the grace period, the caps on a node) are read from the node's own configuration of a registrar (`RegistrarConfig`), which every node shares.
- **Bounds.** At most `MAX_REGISTRATIONS` registrations, as many under way at once as a registrar logs from one node, and as many names renewed as a registrar grants one node, which an honest quorum never exceeds. So the events a step queues are bounded by these, however many names the registrars list, as the registrar's and the view's are ([Holders](#holders)).

## Peering

Each node looks for a few peers on its own (auto-peering). A peering is between two nodes, one per pair, and settles on one or more settlement methods, each a scheme both settle on ([Settlement methods](#settlement-methods)).

### Looking for peers

- **Target.** Only advertised peers count toward it ([Advertised peers](#advertised-peers)), so a node whose peers went silent, flap or are stuck looks for others. Downlinks do not count.
- **Candidates** are table nodes with a fresh link state listing a scheme we peer on, not peered or being asked, not banned, not in backoff, and with room for a settlement channel. Nodes our routes do not reach come first, then majority nodes. One attempt runs at a time.
- After a restart with peers, a node waits a heartbeat's time before looking, so the peers it has can confirm themselves first.
- **Slot caps.** A node starts a bounded number of outbound peerings and holds a bounded total; inbound requests are accepted only below a cap under that total, so requests alone cannot fill every slot. Downlinks take none of these slots ([Downlinks](#downlinks)).
- **Bridge rule.** If a majority node with a fresh link state has stayed unreachable by our routes for a while, the node starts one more outbound peering, with such a node, if it can. This joins separate islands of peers that each met their target.
- **Backoff.** A failed attempt backs off from that node exponentially. A refusal for "unknown node" is retried after one list poll instead, since the responder has not seen the majority list us yet; one for "concurrent request" after a short wait.

### Asking and answering

1. The asking node sends `peeringInfoRequest` for the scheme, and its scheme builds the request data from the answer.
2. It sends `peeringRequest` with its signed link state and the scheme's data.
3. The responder checks the request (`crates/dassie-peer/src/node/peering.rs` has the order and the refusal reasons), takes in the requester's link state, and probes its URL as for registration; a periphery requester has none, and is not probed ([Downlinks](#downlinks)). Its scheme then accepts, opening the peer's accounts; a downlink's open only once value moves with it ([Downlinks](#downlinks)). The peering is persisted before the acceptance is sent, and so before the requester uses it.
4. On acceptance, the requester's scheme finalizes the peering and opens the peer's accounts.

The settlement schemes have their say through `PeeringHooks` (`crates/dassie-peer/src/hooks.rs`, [Settlement](settlement.md)).

- **Only on a scheme that has seen its ledger.** A node offers, asks for and accepts peerings on a scheme only once the scheme has synced with its ledger at least once: before that, a peer's settlement would be booked as the owner's deposit ([Settlement](settlement.md#the-scheme-interface), [synced-before-peering](../decisions/synced-before-peering.md)). A request on another scheme is refused as unsupported, and the requester backs off as from any refusal; once the scheme has synced, the node's link state lists it. Having synced once, a scheme stays peered on across restarts, its ledger reachable or not.
- **Not on a scheme peers cannot pay.** While a scheme's ledger stops what peers pay us, as while an issuer froze our line deep, a peer's settlement would only fail, so the node leaves the scheme out as before its first sync, until it can receive again; peerings already made on it stay ([Settlement](settlement.md#when-peers-cannot-pay-us)).
- **Not on an owner book.** A scheme configured not to peer keeps the owner's holdings on its ledger and peers with nobody: the node leaves it out as before a first sync, for as long as it runs so ([Settlement](settlement.md#owner-books)).
- **Not on a stopped scheme.** A scheme whose effects the books refused stops until the node restarts, and refuses a peer's settlement meanwhile ([Settlement](settlement.md#the-scheme-interface)). So the node leaves it out as before its first sync: its link state no longer lists it, it asks for no peering on it, and refuses a request on it as unsupported. Peerings already made on it stay, and a repeat request on one is still answered with the stored peering; a restart lists it again.

- **Repeats.** A request from a node already peered with a method on the same scheme is answered at once, without a probe, as accepted. This covers an acceptance that got lost.
- **Crossings.** When both ask at once, the lower node ID's request wins.

### Settlement methods

A peering's methods are the schemes it settles on, each with what the scheme keeps for the peer, the credit extended on it and how long the room on it has been short ([settlement-methods](../decisions/settlement-methods.md), `crates/dassie-peer/src/node/methods.rs`). The peering itself, its settlement channel, its advertise flag and hold-down, and the mark of an end for room stay one for the pair.

- **Which schemes.** A peering with a node settles on each hub both are in and take new peers over, one of them at least with an account in it ([joining by being paid](../designs/settlement-hubs.md#5-joining)), by their hub lists (link-state extension type 7), or, where either lists none, on the hub both name in type 5 over the first hub scheme both run; then on each scheme both run whose peers trust each other without limit, as only the test stub with unlimited trust's do ([Settlement](settlement.md#the-stub-scheme)). A scheme that would settle directly, neither over a hub nor of unlimited trust, is never a method: a node neither asks on it nor takes a peering or method asked on it (`PeeringHooks::trusts_unlimited`, [hubs-only](../decisions/hubs-only.md)). Each scheme counts once, however often the other's link state lists it. The first of them is the one the peering is asked for on, and stays the peering's first method while it lasts.
- **Agreeing more.** The node that asked for the peering asks for each further method, one at a time: the scheme's peering info, then `methodAdd` with the scheme's data, answered as a peering request is, the method recorded before the acceptance goes out; on acceptance its scheme finalizes the method. A scheme both come to run is asked for so too. A refusal backs off as a failed peering attempt does, and the next request is for the next scheme the peering lacks, so a scheme refused holds up no other. An acceptance that arrives after a Prepare of the peer's on the method did, which found no method and was answered with our drop, adds nothing: the method is asked for again once the drop is heard. The node's hooks decide whether it asks for or takes a further method at all (`PeeringHooks::wants_method`).
- **Bounded:** at most one method per scheme, and at most `MAX_METHODS` (`crates/dassie-peer/src/node/mod.rs`), the number of schemes a node peers on, so what a peer can cost, summed over its methods, stays bounded.
- **Winding one down.** A method is dropped as a peering ends, on that method alone, so the node that drops it collects on it first, as the owner's removal of its scheme does ([Settlement](settlement.md#schemes-and-ledgers)). From its decision the method takes no new Prepares from the peer, each refused for want of room on it (T04), and counts as unavailable, as one withdrawn for room does; for the peer nothing changes. The node waits for its own settlements on the method under way, then asks the peer to settle on it once (`settlementRequest`, naming its scheme), and waits until what the peer says it has on its way on it is booked, counted in the method's units: each wait at most `depeer_wait_ms`, so a method is dropped within two of them of the decision. The decision is kept across a restart, which takes the steps again from the start. Then the node drops the method and tells the peer with `methodDrop`, again until it hears back, and the peer drops it at once and settles nothing more on it; the peering goes on, on its other methods. A peering whose last method is wound down ends once it is collected, told at once. Neither side pays the rest: what a dropped method's accounts show stays owed, for a later method on its scheme to settle.
- **Dropping one at once,** without collecting, since no settlement on it could be booked (one that still arrives is acknowledged, and books nothing: [Settlement](settlement.md#incoming-settlements)): a method on a scheme the node no longer runs, and one on a scheme that has not been able to receive a peer's settlement for as long as a silent peer is kept (`peer_dead_ms`), counted from the node's start at the earliest ([Settlement](settlement.md#when-peers-cannot-pay-us)). A peering being ended collects on its first method, in whose units the peer says what it has on its way ([Termination](#termination)), and winds none down meanwhile, so one that loses that method ends at once, told at once. A peering left with no method ends, told at once, as one on a scheme the node does not run did ([Termination](#termination)). A method one side still holds after the other's drop was lost with a restart is told so by the first Prepare on it ([One-sided peerings](#one-sided-peerings)).
- **Prepares** travel on a method, named in each `methodPacket` ([Peer protocol](peer-protocol.md#message-set)); which method a packet takes is the node's.
- **What the node takes.** It asks for and takes a further method on a scheme it runs and peers on, once the method's two accounts with the peer fit the room a peering's first method's would: the core peers' share, or the downlinks' for a downlink, unless the peer has accounts on that ledger already ([account-budgets](../decisions/account-budgets.md)). Each method keeps its own accounts, credit, position, requests to settle and backoff, on its own ledger ([Settlement](settlement.md#positions-and-thresholds)), and the store keeps every method with its peering.
- **Which method a packet takes,** by structure, never by room. A peer is one connector endpoint with a slot per method ([Connector](connector.md#settlement-method-slots)): a peer's Prepare books on the method it came on, and its Fulfill or Reject answers on it; our Prepare goes on the method of the ledger it came in on where a first hop has that method available, and otherwise on the drawn hop's available method with the best rate ([Connector](connector.md#routing)). A method short of room answers T04 and never moves the packet to another. A dropped method's slot takes no new packet, and what is in flight on it resolves or expires there. Every method carries packets, so a peer stays advertised while one of its methods is not withdrawn, and its packets take that one.

### Roles

The **junior** is the node whose peering request was accepted, the **senior** the node that accepted it; when requests cross, the lower node ID is the junior. The junior extends the senior a default credit line, the senior extends the junior none at first, and credit then grows with what a peer earned us ([Settlement](settlement.md#credit), [earned-trust](../decisions/earned-trust.md)).

## Lifecycle

A peering is `requesting`, `peered` or `terminating` ([peering-lifecycle](../decisions/peering-lifecycle.md)). "Peered" in other documents covers `peered` and `terminating`; "active" means `peered`.

**Withdrawing is prompt, ending is not.** A node takes a peer out of its link state moderately soon, weighing route flaps against stale routes that lose packets: a withdrawn peer stays peered, and comes back once it is healthy and its hold-down is over. Ending a peering is for good, and needs much stronger evidence: the owner's word, a peer silent or short of room for as long as a silent peer is kept, or a scheme the node no longer runs ([Termination](#termination)). Nothing that withdraws a peer ends it.

### Advertised peers

A node lists a peer as a neighbor in its link state, and routing uses the edge, only while the peer is `peered`, **confirmed** (a message from it arrived recently), not banned, not held down, and not unavailable on every one of its methods: withdrawn for room, or being wound down ([Settlement methods](#settlement-methods)).

- **Hold-down.** Each time a peer stops being advertised it is held down, for a time that doubles with each flap and resets after a long stable stretch, so a flapping peer does not churn routes across the network.
- **Restarts** do not drop neighbors: confirmation starts from the persisted time the peer was last heard from, without a hold-down.
- **Withdrawal for room** is per method: a method whose room stays short past the grace is withdrawn, its packets taking another method or another first hop, and the peer is withdrawn only once every method is ([settlement-methods](../decisions/settlement-methods.md)). Withdrawing an edge removes it both ways for the whole network, turning a temporary T04 into a final F02, so neither a failed delivery nor a peer waiting seconds for a routine settlement withdraws it. A peer whose room in our books has stayed below one of the largest packets for the grace, without settling, is stuck: settling, not traffic, restores room, and a creditor asks over the peer protocol, which needs no route ([peering-lifecycle](../decisions/peering-lifecycle.md)). It is withdrawn like a flap: still peered and asked to settle, but no packet crosses the edge either way until its room is back and its hold-down is over. The grace lets two requests to settle go unanswered and still gives the third a request's timeout to be answered, and its settlement time to be booked. A request that surely never reached the peer costs none of it: it is asked again at the next check ([Settlement](settlement.md#asking-a-peer-to-settle)). A node counts only the room it gives a peer, never the room the peer gives it.
- **Downlinks owing nothing are not withdrawn.** A downlink is in no link state, so withdrawing it would only stop the payments to it, which are what raise its room when it owes nothing. One whose debt in our books is zero is never withdrawn or ended for room, however short its room; one that owes and does not settle is, as any peer.
- **Counting the time short.** Each settlement booked from the peer starts the grace again. The time short is a total, grown only while the node can ask (its scheme sees its ledger), by at most two check intervals per check, so neither the node's downtime, a stall of its host, nor an outage of its own ledger counts against the peer. Only the part of it during which the peer could be reached ends the peering: time during which the node's last request to settle surely never reached the peer still withdraws it, since the link carries nothing, but does not count toward ending it for room, as the peer had no chance to settle ([peering-lifecycle](../decisions/peering-lifecycle.md)). Nor does time during which no settlement from the peer could reach us, as while an issuer froze our line deep: it withdraws the peer, never ends it ([Settlement](settlement.md#when-peers-cannot-pay-us)). Both are persisted with the peering, so a restart neither forgives them nor starts them again.

### Termination

Termination starts when the owner asks, when the owner bans the node, when the peer has not been heard from for a long time (counted from the later of its last message and the node's start, so our own downtime ends nothing), when its room on a method has stayed short, without a settlement, for as long while it could be reached ([Advertised peers](#advertised-peers)), or when the node runs the scheme of none of the peering's methods, as ones disabled or of the other realm ([Settlement](settlement.md#schemes-and-ledgers)); a method on a scheme it does not run, beside others, is only dropped ([Settlement methods](#settlement-methods)). A peer cut off from the node is ended for its silence, if at all, never for room. A peering on a scheme the node does not run collects nothing, since no settlement on that scheme could be booked: the node tells the peer at once, as in step 3, giving no reason, so no cooldown follows; a peering it was already ending keeps the reason it had.

The node that ends a peering collects first, and tells the peer only then, unless its owner banned the peer or the node does not run the peering's scheme ([ending-a-peering](../decisions/ending-a-peering.md)):

1. **It decides privately.** Nothing the peer can see changes: a peer it advertised stays advertised, and our own Prepares still go to it. Its owner sees it terminating. Its new Prepares are refused, as for want of liquidity ([Connector](connector.md#responses-and-expiry)), and its requests to settle are answered as ones that settle nothing.
2. **It waits for its own settlements to the peer under way,** so the peer counts them; then asks the peer to settle, once. The answer says what the peer has on its way ([Settlement](settlement.md#settling-on-request)), and the node waits until that is booked. Each wait lasts at most a time a settlement takes to reach the ledger and be announced (`depeer_wait_ms`). A peer that does not answer is waited out.
3. **Then it tells the peer:** it stops advertising it, takes no new Prepares to or from it, and sends `peeringTermination` until it is acknowledged or times out. Responses still flow.
4. **The other side ends at once** when the message arrives, as the node does that is told first when both decided: it stops advertising and routing to the peer, takes no new Prepares and settles nothing.
5. Once the exchange is over, no packet is in flight with the peer and no response to it waits to be sent again, the peering ends. Neither side settles anything for the end ([Settlement](settlement.md#settling-at-a-peerings-end)): what the books show stays owed, for a later peering to settle.
6. After an owner's termination, or one for room, the two do not peer again for a while: neither asks the other, and each refuses the other's requests meanwhile ([ended-for-room](../decisions/ended-for-room.md)). A node collecting for its owner, or for room, keeps its reason when the peer tells it first. That cooldown does not survive a restart; a ban is the lasting way. After any other end, asking again waits only a backoff.

**Termination ends a peering, not a relationship.** The peer's accounts stay, with their balances, as the record of what is owed, and so does the settlement channel with its sequence, open until it has been idle for as long as a silent peer is kept, then closed to disk ([Settlement channels](#settlement-channels)). A settlement that arrives after the peering ended is still credited once, and a later peering with the node reuses both without posting trust twice. The channel also remembers that the node ended a peering for room, so a later one raises the peer no credit ([Settlement](settlement.md#credit)). A termination under way survives a restart, and so does a decision to end a peering; its steps start again after it.

### One-sided peerings

A node that holds no peering with a sender, and is not asking for one, answers any request from it that presumes a peering with a `peeringTermination` of reason "not peered", at most once per termination timeout per node. The request itself gets the answer it would get anyway, a refusal for not being peered, so no status changes meaning. The other side then ends its peering at once, as the node being ended does ([Termination](#termination)).

This repairs a peering whose `peeringTermination` never arrived while it was sent, as when the two were cut off for the whole termination timeout. The side left over would otherwise keep it until the peer had been silent for as long as a silent peer is kept, and, if the peer is short of room in its books, ask it to settle at every check, since a refusal for not being peered is also what a peer that has not taken in our acceptance yet answers ([peering-lifecycle](../decisions/peering-lifecycle.md)).

- **What presumes a peering:** a Prepare, a request to add or drop a method, a request to settle, another node's link state forwarded to us, since floods go only to peers, a core node's own link state that lists us as a neighbor, and a periphery node's own link state. A core node's own link state that does not list us presumes nothing: it also sends it to the bootstrap nodes it is not peered with ([How link states spread](#how-link-states-spread)), even to one it is asking for a peering. A periphery node's lists nobody, but it sends it only to its uplinks, in heartbeats and when it issues a new one; to a node it asks, it goes inside the peering request.
- **A former downlink is told too.** A downlink leaves the table when its peering ends ([Downlinks](#downlinks)), so the node tells it through the settlement channel it keeps with it, open for as long as the periphery node would keep a silent uplink ([Settlement channels](#settlement-channels)). Otherwise a periphery node whose uplink ended their peering while the two were cut off would keep it, unconfirmed, until the uplink had been silent for as long as a silent peer is kept, and never ask it again meanwhile. Who was told lately is a bounded list.
- **Not while asking.** A node whose own peering request is under way answers nothing: the peer may have accepted it, and hold the peering before the acceptance arrives.

### Bans

- Bans are a bounded list the owner keeps. Only the owner bans; a node never bans a peer for what it cost ([own-fulfills](../decisions/own-fulfills.md)).
- A banned node is never asked, is refused, and its messages do not confirm it as a peer. A ban ends a peering as the owner's termination does, with its cooldown, but collects nothing: the node withdraws the peer from its link state and tells it at once (step 3 of [Termination](#termination)), without waiting for its own settlements or asking the peer to settle. What the peer owes stays on the books. A ban is the owner's emphatic word, often about misbehaviour, and a peer being banned has little reason to settle. Its link states still flood: a ban is one node's choice, and other nodes route by both ends' word.
- A ban is a list, not a peering state, since a node can be banned while its peering is still terminating.

## Settlement channels

Every peer gets a settlement channel, which belongs to the pair of nodes and outlives the peering ([Settlement](settlement.md#settlement-channels)). Its settlements are taken even with no peering. Open channels are bounded in number; once all are taken, a node without one is no candidate and its peering requests are refused for capacity. A channel idle for as long as a silent peer is kept after its peering ended closes: it leaves memory and frees its place, and what stays of it on disk still takes the node's settlements once and opens again with its next peering ([closing-channels](../decisions/closing-channels.md)).

## Periphery nodes

A node without a public address joins as a periphery node ([core-and-periphery](../decisions/core-and-periphery.md)): it connects only to core nodes, its uplinks, is reached only over the connections it opened to them, and forwards nothing. What else the [design](../designs/periphery.md) holds is not built yet ([roadmap](../roadmap.md#periphery)).

- **Who is one.** A node without a hostname, so without a URL, or one whose QUIC endpoint a host that embeds it put apart from its HTTPS listener's port ([Node](node.md#runtimes)). A node with a URL is a core node, and takes downlinks. The owner's hostname must make a URL peers take, with any port, so a node never turns periphery by a hostname too long ([Node](node.md#configuration)).
- **Where UDP is blocked,** it reaches core nodes over a WebSocket on their HTTPS listeners, which every node serves, with the same QUIC connections inside: it dials over UDP first, and the tunnel too after a head start ([Peer protocol](peer-protocol.md#quic-over-websocket)). A core node dials over UDP only.
- **Changing kind.** A core node that loses its URL ends the peerings with its downlinks, since a periphery node takes none, and asks for uplinks. A peer whose link state turns from core to periphery, or back, is a peer of the other kind, with another address and other bounds: the peering made as the old kind ends, and it may ask anew.
- **Its link state** has no URL and the periphery extension ([Peer protocol](peer-protocol.md#link-states)), and lists no neighbors: only core nodes list theirs, since routing needs both ends of an edge and no node routes to a periphery node ([periphery-lists-no-neighbors](../decisions/periphery-lists-no-neighbors.md)). So its size does not grow with its uplinks. Only its uplinks see it, in its peering requests and heartbeats: it is never forwarded or served, nor registered, so it is in no node list, and in no table but its uplinks'.
- **Peering.** It asks core nodes from the node list, as junior ([Roles](#roles)), until it has the usual target of confirmed peers, or only the nodes it is pinned to ([below](#pinned-uplinks)). It accepts no peering request, and is never asked: no core node asks a periphery node. It seeks no bridge.
- **Routes** go through its uplinks, which never list it: it reaches whatever they reach.
- **Its addresses** lie beneath its uplinks', and it forwards nothing ([Connector](connector.md#a-periphery-node)).

### Pinned uplinks

An owner may pin a periphery node's uplinks, by node ID (`env.rs`), when it must reach the network through particular core nodes: a market maker's nodes trade through the core node whose rates they watch, and a node that peered with any other would route some of its payments elsewhere.

- **Only those are asked,** each still under every rule of [Looking for peers](#looking-for-peers): fresh, not banned, not in backoff. A pinned node the node does not know, or cannot ask, is waited for; no other is asked meanwhile, so a pin that names no reachable core node leaves the node without an uplink rather than with one the owner did not choose.
- **The target is as many as it names,** and only peerings with them count toward it. A peering made before with another node stays, as one on a scheme left out does, until the owner ends it: it is not counted, and takes none of the places for peerings the node starts. Its routes still serve, so an owner who wants every payment through the pinned nodes ends it.
- **Slots of their own.** A pinned node starts as many peerings as it pins, rather than the configured cap, still one attempt at a time, so every pinned node can be asked however many there are. Its core peers together, the pinned ones and those made before, stay within the larger of `MAX_UPLINKS` and the configured total; only a node pinned to nearly that many, with peerings from before, waits for the owner to end one before it asks the last. That bound is what every node's tables are sized for: its connector's addresses and packet table, its ledger and its settlement channels (`check_bounds` in `crates/dassie-node/src/engine/core/mod.rs`). An unpinned node, and every core node, keeps the configured slots.
- **Bounded** by `MAX_UPLINKS` in `crates/dassie-peer/src/node/mod.rs`, high enough that a market maker's node can trade through many core nodes: a longer list stops the node at start ([Node](node.md#startup)).
- **Only a periphery node uses the list.** A core node finds its peers itself, and warns at start that it ignores the list; one that turns periphery later uses it from then on, as a periphery node that turns core stops.

### Downlinks

A core node keeps its downlinks, the periphery nodes peered with it, apart from its peerings with core nodes.

- **Taken without a probe.** A periphery node's peering request is checked as any other's, but its URL is not probed: it has none, and the connection its request came on shows it is there. It is in no node list, so it enters the table by asking.
- **A bound of their own** (`max_downlinks` in `crates/dassie-peer/src/config.rs`) on their places in the table, their peerings and their settlement channels, apart from the core peering slots, the table's other nodes and the channels with core nodes. A channel closes once idle after its peering ended ([Settlement channels](#settlement-channels)), so it bounds the downlinks peered with, or not long ago. Past it, a new downlink is refused for capacity. So is one whose accounts would not fit the downlinks' share of the peers' accounts, which stay when its peering ends: downlinks' accounts never take the room peering with core nodes needs, nor theirs the downlinks' ([account-budgets](../decisions/account-budgets.md)). A downlink's accounts open only once value first moves with it, and the share keeps room for them meanwhile, while its channel is open: one that never moves value leaves nothing behind ([lazy-downlink-accounts](../decisions/lazy-downlink-accounts.md)). A downlink took no place among the table's other nodes, so one that is refused, or whose peering ends, stays in the table only if it gets such a place: within their bound, or, if another reason keeps it, in place of a weaker node. Otherwise it leaves at once, and with it the wait before it may ask again after a termination; its channel stays. An owner who wants it kept away bans it.
- **Free receivers hold at most half of the places** (`Config::max_free_downlinks`), so keys made for nothing never keep out the downlinks that paid us ([free-receivers-half](../decisions/free-receivers-half.md)). A free receiver is a downlink that never paid us: its channel, open or closed, carries no mark of a settlement of at least one largest packet that our books took from it, on any ledger, and once marked it stays so. A place is an open channel with a downlink. Once free receivers hold half, a new downlink that never paid us is refused for capacity; one that paid us is bounded by `max_downlinks` alone. The rule only refuses: a downlink whose channel is open holds its place and gets in, and nothing is ever ended or displaced by it.
- **A newcomer may pay to enter** ([pay-to-enter](../decisions/pay-to-enter.md)). A downlink whose request's scheme holds an entry payment from it, a payment of at least one largest packet that reached us on the ledger before it asked, bound to it and to the address its request names, gets in past a full free half, under every other bound; as it peers, the payment is booked as its settlement, which marks it as a downlink that paid us. Past a full free half, with room left among the downlinks, one that has not paid is refused with `PayToEnter` on a scheme that takes entry payments, and for capacity on one that takes none ([XRPL](xrpl.md#entry-payments)).
- **In nobody's routes.** A downlink is never listed in our link state, so no route leads to it: its child address lies beneath ours, which the rest of the network routes to us, and the connector passes it on ([Connector](connector.md#addresses-and-endpoints)).
- **Reached only over its connection** ([Peer protocol](peer-protocol.md#quic)), each with its own bound on requests in flight rather than one for all nodes without a URL, and never withdrawn for room while it owes nothing ([Advertised peers](#advertised-peers)).
- **Places of their own for its connections.** A downlink's QUIC connections hold places among the downlinks', which have room for every downlink within the bound, apart from core peers' and everyone else's: however many downlinks a node keeps, its core peers and relayed streams keep their room ([Peer protocol](peer-protocol.md#quic)).

## Routing

Routing runs a breadth-first search from this node over edges that both ends advertise and whose link states are fresh.

- An edge counts only if both ends list each other, so no node can claim a link the other end does not confirm, and a node whose state went stale drops out.
- Each reachable node's address gets a few first hops on shortest paths. There is no route for the node's own address: destinations under it go only to its own endpoints. Prefix matching, first-hop choice and never sending a packet back where it came from are the connector's ([Connector](connector.md#routing)).
- **The cut.** Where more first hops reach a node than a route keeps (`MAX_FIRST_HOPS`), it keeps those that rank lowest by an HMAC of their node IDs under the node's route key, a secret derived from its node key ([Identity](identity.md#seed-paths)). Each node keeps its own few, the same after a restart, and no node can grind its ID to be kept by every node, as it could to come first by ID ([weighted-next-hops](../decisions/weighted-next-hops.md)). A route lists the first hops it keeps by node ID.
- Routes are recomputed when the graph may have changed, debounced, and periodically as states go stale.
- A periphery node routes through its advertised uplinks, whatever they list, and recomputes its routes when one is withdrawn or comes back; no route leads to a periphery node ([Periphery nodes](#periphery-nodes)).

## Persistence

The peer node's state is written in the same transaction as the ledger, on every change (`crates/dassie-peer/src/persist.rs`, `crates/dassie-node/src/store/peer.rs`). What survives a restart is chosen so that a restart neither drops a peer nor forgives one: peerings with their methods, when each was last heard from and how long the room on each method has been short, peerings being ended (decided or told) and methods being wound down (decided), the own sequence, the majority, settlement channels (with whether a peering with the node was ended for room), open or closed, bans, at a registrar its log's head, the commitments in its log with their unsealings, and its names ([Names](#names)), every node's view of who holds each name ([Holders](#holders)), and its own registrations of names, each with its salt ([The registrant](#the-registrant)). The node's store keeps a peering in one row and each of its methods in a row of its own, in the order the pair agreed them; a peering stored before methods had rows loads as its one method ([Node](node.md#persistence)). Only open channels are loaded at start; a closed one is read when it is needed. Link states were verified when received and are not verified again.

What is lost is either fetched again (the bootstrap nodes' node and name lists) or only paces the node's own attempts: backoffs, a method's drop not yet told, flood counters, hold-downs, the cooldown after a termination, how long each channel has been idle, a registrar's bucket of new commitments, how long each name it lists has been split, and how a registration of the node's stands with each registrar, whose receipts and answers it asks for again. A peering attempt cut short by a restart is dropped.

## Tests

The `peer` simulation (`dassie_peer::sim::chaos`) runs this protocol on a rough network with crashes, partitions, terminations and bans, nodes that run a second scheme and stop and start either, and Prepares on each method, and checks that link states and routes converge, peerings are two-sided with the same methods on both ends, one on each scheme both run, every Prepare is taken on the method it was sent on, every termination finishes, and each settlement is applied exactly once ([Testing](testing.md#the-simulations)). The `names` simulation (`dassie_peer::sim::names`) has nodes register names on four registrars, one of them perhaps faulty, through chaos and a calm, and holds them to the guarantees of [Names](#names) ([Testing](testing.md#names)).

A registrar takes commitments, unsealings and renewals over the protocol on the same simulated network in `crates/dassie-peer/tests/names_registrar.rs`: the commitment logged first wins, a receipted commitment survives a crash, names expire unless renewed, and commitments are throttled. In `crates/dassie-peer/tests/names_holders.rs`, nodes take holders from four or five registrars: a view freezes without a quorum of fresh lists, across a restart too; a faulty registrar that shows nodes different lists after an honest split never gives a name two holders, nor after a release and a new grant to a node that kept a list from before the release; a split of two to two is released at all four, and no sooner than the wait; and neither a holder with a quorum, with one registrar faulty or out of reach, nor a registration whose lists are merely late, is released. In `crates/dassie-peer/tests/names_registrant.rs`, nodes register names themselves: a node at four registrars, a registrar at itself and a periphery node each hold the name on every node; a registration survives a crash right after it started; one that a registrar cannot be reached for is abandoned before any registrar learns the name; a node that commits after seeing the name unsealed, on a rough network, never holds it; and a name is renewed before it expires, at a registrar cut off past its expiry in its grace period. In `crates/dassie-node/tests/names.rs`, a periphery daemon registers a name over QUIC at four bootstrap daemons, as its owner asks over RPC; every daemon takes it as the holder, the node answers Open Payments under the name from then on, and each registrar's client, sending its request as it sends any to another wallet, with a nonce of its own, takes that answer passed on by a front door as the holder's (and before the name is held, neither asks under it nor fetches the key set of a client that claims a wallet address there), and refuses one replayed from another request, one a front door makes up, and the holder's answer read as another node's. In `crates/dassie-node/tests/front_door.rs`, a front door reads the lists of four bootstrap daemons: a name a periphery daemon registered reaches it through the front door, signed by it, with the front door's page about it at the name's root; a name nobody holds finds nothing; the name keeps resolving with one registrar gone, and stops once the remaining three no longer list it.

Periphery nodes peer with their uplinks on the same simulated network in `crates/dassie-peer/tests/periphery.rs`, pinned ones too, to more uplinks than a link state could list, and free receivers stop at half of an uplink's downlinks while one that paid comes back past them; `crates/dassie-node/tests/periphery.rs` has a periphery daemon peer with a core daemon over QUIC and get paid beneath it, one pinned to a core node ask only that one, and one pinned to two get paid beneath each, as its owner names it.

## Decisions

- [peer-protocol-v1](../decisions/peer-protocol-v1.md): v1 instead of v0: senders proved by their connections, peering requests that carry the signed node info, termination.
- [membership-economics](../decisions/membership-economics.md): removal and expiry, automatic registration, the served list, the membership freeze, authenticated lists, and the limits on free registration until fees.
- [peering-lifecycle](../decisions/peering-lifecycle.md): the peering lifecycle, confirmed peers, the bridge rule, slot caps, repeats and crossings, the advertise flag and withdrawal for room, termination, bans as a list, the channel limit, and why child peers wait.
- [bootstrap-network](../decisions/bootstrap-network.md): the testnet's bootstrap nodes as the default list.
- [earned-trust](../decisions/earned-trust.md): junior and senior.
- [own-fulfills](../decisions/own-fulfills.md): only the owner bans.
- [synced-before-peering](../decisions/synced-before-peering.md): no peering on a scheme before its first sync.
- [ended-for-room](../decisions/ended-for-room.md): a pair parted for room stays apart for the cooldown, and earns no credit back.
- [closing-channels](../decisions/closing-channels.md): a settlement channel left idle closes to disk, freeing its place.
- [core-and-periphery](../decisions/core-and-periphery.md): core and periphery; why periphery nodes are in no node list and no link state.
- [places-by-proved-key](../decisions/places-by-proved-key.md): downlinks' connections hold places of their own.
- [quic-over-websocket](../decisions/quic-over-websocket.md): a periphery node reaches core nodes over a WebSocket where UDP is blocked.
- [free-receivers-half](../decisions/free-receivers-half.md): downlinks that never paid us hold at most half of the downlinks' places, and none is ended or displaced for it.
- [account-budgets](../decisions/account-budgets.md): downlinks' accounts in a share of their own.
- [lazy-downlink-accounts](../decisions/lazy-downlink-accounts.md): a downlink's accounts open once value moves with it.
- [periphery-lists-no-neighbors](../decisions/periphery-lists-no-neighbors.md): a periphery node's link state lists no neighbors, so it may keep many uplinks.
- [settlement-methods](../decisions/settlement-methods.md): a peering settling on every hub both nodes are in, each a method of it.
- [names-by-earliest-commitment](../decisions/names-by-earliest-commitment.md): a name goes to its earliest sealed commitment at each registrar, and is held by a quorum of their lists.
