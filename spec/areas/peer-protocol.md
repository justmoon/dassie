# Peer protocol

Dassie nodes talk to each other with the peer protocol v1: OER messages sent over QUIC, each the message of the node whose key its connection proved. This document covers what the protocol guarantees, what a node trusts from whom, and what must stay compatible. What the messages are used for (the node table, membership, peering, routing) is in [Network](network.md).

**Paths:** `crates/dassie-peer/src/wire/` (layouts), `crates/dassie-peer/src/names/` (names and their commitments), `crates/dassie-peer/src/node/inbound.rs` (handlers and statuses), `crates/dassie-node/src/quic/`, `crates/dassie-node/src/peer_server.rs`, `crates/dassie-node/src/outbound.rs`, `crates/dassie-node-core/src/address.rs`, and for the hub's stream `crates/dassie-node/src/hub/transport.rs`, `crates/dassie-node/src/quic/hub.rs`, `crates/dassie-hub/src/founding/wire.rs`
**Read with:** [Network](network.md), [Identity](identity.md), [Encoding](encoding.md), [Settlement](settlement.md), [Connector](connector.md)

## Versions

- v1 keeps v0's message set (less `settlementMessage`), and adds senders proved by their connections and new messages. It keeps v0's OER layouts but where v0 sent what the recipient has already, and adds the SLH-DSA key a node ID commits to: a link state carries no node ID, since its two keys derive it; `interledgerPacket` is flat, as `methodPacket` is, without the length v0 wrapped its fields in; and a peering's or a method's acceptance carries nothing, since what the requester needs of the responder's scheme it has from the peering info. Every node ID it does carry is its 24 bytes ([Identity](identity.md#node-id)). It carries them over QUIC ([quic-only](../decisions/quic-only.md)), so v1 and v0 nodes do not interoperate ([peer-protocol-v1](../decisions/peer-protocol-v1.md)).
- **The QUIC connection's ALPN is the version:** `dassie/N` names the layouts of every message on the connection, so no message carries a version ([protocol-upgrades](../decisions/protocol-upgrades.md)). A node offers and accepts the versions it speaks, newest first (`VERSIONS` in `crates/dassie-node/src/quic/mod.rs`), and the two speak the newest they share. A release that brings a version speaks the one before too, for a release cycle. Nodes that share none fail the handshake, before a message is read, so nodes whose layouts differ never take each other's bytes for their own. Version 2, `dassie/2`, is spoken alone.
- **`dassie/2` numbers its own.** Its message tags (0 to 18, `Kind` in `crates/dassie-peer/src/wire/mod.rs`), refusal reasons (0 to 8, `RefusalReason` in `crates/dassie-peer/src/wire/response.rs`), link-state entry tags (a neighbor 0, an extension 1) and extension types (1 to 3, the `EXTENSION_` constants) each run from the first without gaps, numbered afresh rather than kept from `dassie/1`, whose numbers stay as its releases have them. A number in one version says nothing of the other: the connection's ALPN says which applies, and each version's link states are signed under an OID of their own. Once a release speaks a version, a number it gave is never given another meaning: a message, reason or type that goes leaves its number unused.
- A link state is signed under an OID of its layout's (`…1399.1.6`), so a node info signed under v0's (`…1399.1.2`), under the layout that sent the node ID beside the key (`…1399.1.3`), or under the layout with the Ed25519 key alone (`…1399.1.5`), is never a link state.
- **Nothing is said of credit.** A node knows only the credit it extends, never the credit extended to it, so no message carries any ([own-fulfills](../decisions/own-fulfills.md)).
- **`settlementRequest`** asks a peer to settle, and its answer is the amount on its way ([ending-a-peering](../decisions/ending-a-peering.md)).
- **No scheme versions.** What a settlement scheme's messages and ledger transactions mean is versioned twice already: by the scheme's ID, which a new meaning takes anew, and by this protocol's version. So a peering names its scheme alone, and nothing in it negotiates a version of the scheme ([mainnet-schemes](../decisions/mainnet-schemes.md)).
- **Names** need no version of their own: their messages have tags of their own (11 to 15), and a node that does not know a tag refuses its message as malformed with 400, one of the statuses that say a message was not acted upon ([Statuses](#statuses)). A registrant takes that as a refusal, as from a registrar that withholds its receipt ([Names](#names)).
- **Settlement methods are part of version 2** ([settlement-methods](../decisions/settlement-methods.md)): every node that speaks it has them, so nothing says so and nothing is negotiated. Their messages have tags 16 to 18 ([Message set](#message-set)). Every Prepare between peers travels on a method, in a `methodPacket`, the one over a hub with its commitment; `interledgerPacket` carries only Fulfills and Rejects.
- **A refusal reason a node does not know** reads as unspecified, and the asker backs off as from any refusal.
- **QUIC** is the only transport: every node takes it, at its URL's host and port, so nothing in a link state says so ([quic-only](../decisions/quic-only.md)).
- **Settlement offers are part of version 2** ([settlement-offers](../decisions/settlement-offers.md)): a link state offers the schemes a node takes peers on in one list of its own, each with what the scheme says of itself ([Settlement offers](#settlement-offers)). Nothing else in a link state names a scheme or a hub.
- **Post-quantum.** A link state carries the node's SLH-DSA key beside its Ed25519 key, the two its ID commits to; nothing signs with the SLH-DSA key yet. Link-state extension type 1 is kept for the post-quantum signing key the SLH-DSA key is to vouch for, once Ed25519 is trusted no longer ([post-quantum-node-id](../decisions/post-quantum-node-id.md)).

The layouts are pinned by golden vectors ([Test vectors](#test-vectors)). Once a release speaks a version, a change to any of its layouts is a new protocol version, under a new ALPN name; until then no released node speaks it, so its layouts may still move under the same name. Version 2 is in no release yet (the releases speak `dassie/1`): the SLH-DSA key joined its link state under it ([post-quantum-node-id](../decisions/post-quantum-node-id.md)).

## Transport

Requests travel over QUIC, the only transport ([quic-only](../decisions/quic-only.md)). The transport checks only the client's rate and the body's size; the peer node decides everything else, and answers only once what the request changed is on disk ([core-and-periphery](../decisions/core-and-periphery.md) chose QUIC: peer traffic is heavy, and one HTTP request per packet costs).

- Requests that fail are rate-limited per key their connection proved, not per address, so one node's failures never cost another behind the same address; a client that makes new keys to escape it needs a connection for each, which holds a place by its address ([QUIC](#quic)).
- The number of requests waiting on the node is bounded, in all and per client address; past it the node answers 503. Each client address has a share of them, since one connection carries many requests at once, so that one address cannot take every place. A body that is too large, broken or too slow is charged like a failed request, so a client cannot hold places over and over (`crates/dassie-node/src/peer_server.rs`).

### QUIC

- **One endpoint per node on UDP,** at its URL's host and port: 443 under systemd, the HTTPS listener's port number when standalone ([Node](node.md#runtimes)). It both takes and makes connections. A node does not run without its endpoint at its URL's port ([Node](node.md#runtimes)), so every node with a URL takes QUIC there, and no link state says so. Where UDP does not get through, a periphery node reaches it over a WebSocket on the same host and port instead, into a second endpoint whose socket is the node's tunnels ([QUIC over WebSocket](#quic-over-websocket)); a node with a URL dials over UDP only. Places, one connection per pair of nodes and the connection standing by span both endpoints: a connection over a tunnel holds a place, is kept, replaced and stands by as one over UDP.
- **Keys, not certificates.** Each side presents a self-signed certificate for its Ed25519 node key, not of small order, with its SLH-DSA key in an extension of its own (`…1399.1.7`, an OCTET STRING of the key; `crates/dassie-node/src/quic/keys.rs`): a certificate without exactly one is no node's. A dialler refuses a server whose two keys do not hash to the node it asked for; a server takes any client that proves a key, and learns its node ID from its two keys. The handshake proves the Ed25519 key, and the ID binds the SLH-DSA key to it, so a certificate that names another SLH-DSA key names another node. That identity is who sends every request on the connection, and who answers ([Authentication](#authentication)). TLS 1.3 only, with the versions as ALPN names ([Versions](#versions)), and no connection without one both sides speak. No certificate authority is involved, so a node needs no certificate for its hostname to be reached over QUIC. TLS signs with a context string of its own, so a handshake signature never passes for a link state's (`crates/dassie-node/src/quic/keys.rs`).
- **Every bidirectional stream starts with a kind byte** (`StreamKind` in `crates/dassie-node/src/quic/mod.rs`): a peer request, a relay request or a relayed stream ([Relayed streams](#relayed-streams)), or a settlement hub's message, state or founding ([The hub's stream](#the-hubs-stream)). A stream of a kind the node does not know is reset.
- **Streams are read in order, never out of order.** A stream is read in order for its kind byte, and quinn-proto miscounts a stream that then switches to reading out of order while a retransmitted copy of its start is still buffered: it never sees the stream's end, and underflows when the stream is dropped, which with overflow checks on ([Engineering](../engineering.md#requirements-on-every-crate)) aborts the node. So the node reads the rest in order too (`read_in_order` in `crates/dassie-node/src/quic/mod.rs`), and clippy denies quinn's `read_to_end`, which reads out of order.
- **A peer request** is its content (`PeerMessageContent`), then the stream's end; the answer is the status as two bytes, big-endian, then the body ([Statuses](#statuses)). The ALPN names what the bytes are, so nothing else does.
- **One connection per pair of nodes, used both ways.** A node sends on a connection another opened to it; when both dialled, the one the lower node ID opened is kept. A connection unused for a while closes, which peers' heartbeats prevent. A connection that is open but not the one used stands by, and takes over when the one used closes, so that a connection the other node keeps open for its own sake ([A chosen relay](node.md#a-chosen-relay)) is never lost behind one that goes idle.
- **A periphery node is reached only over the connections it opened** ([Network](network.md#periphery-nodes)). It has no URL, so a peer request to it goes on the connection it opened, or on one it opened since that stands by, or fails as not delivered: it is never dialled. The connections it dials for requests keep themselves alive as the one to a chosen relay does, well within the idle timeout, since they are the only way its uplinks reach it, and a NAT drops a mapping that goes quiet.
- **A crash ends connections at once.** The keys for stateless resets and for connection IDs derive from the node key ([Identity](identity.md#seed-paths)), so they are the same after a restart: a node that crashed, closing nothing, still knows the connection IDs it handed out as its own, and tells peers sending on them that their old connections are gone, and they connect again at once, as over TCP, instead of waiting out the idle timeout. Both keys are needed: an endpoint sends a reset only for an ID it knows as its own, and quinn's default key for IDs is new at every start, so the node back would drop such packets unanswered. An ID is a random nonce and an HMAC of it under that key (`crates/dassie-node/src/quic/ids.rs`), not quinn's hash, which two IDs give away: with a key that outlives the node's run, whoever had it could tell the node's IDs apart from everyone's for good, across restarts and networks.
- **Backing off.** A request to a node whose QUIC cannot be reached (UDP filtered, a restart, a new address), or that has no room for us, is not delivered, and the node is not dialled for peer requests for a while: a second after a first failure, twice the last wait after each that follows, up to a minute. A connection it keeps ends the wait: one it opened to us, or one of ours a request got through on. A dial alone does not, since a node without room closes only after the handshake. So a peer that comes back and dials us is asked again at once, and one that keeps refusing for room is dialled ever less often. Making a connection takes at most the request's time, the name's addresses tried in turn, so a request that cannot be sent fails as not delivered within it. Only a peer request's dial that had time enough to judge, or its connection refused for want of room, counts: a relayed stream or a hub's message that cannot reach its node backs off nothing, and dials whatever the wait. A periphery node's dial fails only when both UDP and the tunnel failed ([QUIC over WebSocket](#quic-over-websocket)), and has time enough to judge only when the tunnel had it too, after UDP's head start.
- **Bootstrap nodes** known only from the configuration are dialled at the configured URL, pinned to the configured ID, before their link state arrives.
- **Endpoints, read once.** What a node dials is an endpoint, a host and a port (`Endpoint` in `crates/dassie-peer/src/wire/url.rs`), read once from where it comes from: a peer's from the URL in its link state, a bootstrap node's or the relay's from the URL of its configured entry, a hub validator's from the `host:port` its acceptance names, which is how an endpoint is written. A periphery node has none: a request without one goes on the connection the node opened, never an empty URL standing for it.
- **Bounds:** a client's requests open on one connection no more than its share, bounded windows, and a bounded time to write an answer a client does not read.
- **A connection holds a place by who opened it** ([places-by-proved-key](../decisions/places-by-proved-key.md), `crates/dassie-node/src/quic/places.rs`). While it is set up, it holds one among the connections being set up, in all and per client address, for at most the time to connect; once those run short, a client must show it receives at its address before it holds one. Once the handshake has proved its key, it holds a place in its class, by our own peerings with that key: a core peer's, a downlink's, or anyone else's (relay clients, nodes that chose us as their relay, registrants, nodes asking to peer). Anyone else's are bounded in all and per client address; core peers and downlinks have room for as many nodes as the peer node keeps of each, and a small share per node. So downlinks never take the room of core peers or of relayed streams' clients, and nobody takes the core peers' room. A tunnel holds these places for the connection it carries, by its TCP connection's address ([QUIC over WebSocket](#quic-over-websocket)).
  - **The class follows the peerings.** When a peering begins or ends, its node's connections move to their new class, or close if it has no room.
  - **Nothing a node says** decides its class: not its link state, nor the sender of its messages. Only the key it proved, which it cannot borrow, and our peerings; a node that opens connections under other keys is anyone else, under anyone's bounds.
  - **No room is said with a close code of its own** (`NO_ROOM` in `crates/dassie-node/src/quic/mod.rs`), which a connection refused once its key is known closes with, before any stream on it is read. A client takes it as a connection refused outright: nothing it sent was delivered, it backs off from the node, and a relayed stream finds the relay busy. Every other close, at shutdown, for a newer connection or for a class without room, uses 0, since requests may have been read; a node that does not know the code reads it so too.
  - **A node past its share** replaces its own oldest connection, by when each was made, not anyone else's: the one it made last is the one it uses. An older connection does not replace a newer one, and closes instead.
- **At shutdown** the endpoint stops taking connections, lets the requests in progress finish for a bounded time, and only then closes, as the HTTPS listener does ([Node](node.md#shutdown)).

### QUIC over WebSocket

Where UDP does not get through, a periphery node carries the same QUIC packets over a WebSocket at `/quic` on the core node's HTTPS listener ([quic-over-websocket](../decisions/quic-over-websocket.md), `crates/dassie-node/src/quic/tunnel.rs`). The connection inside is an ordinary QUIC connection, with the handshake, streams, places, `NO_ROOM`, keep-alives and relayed streams it has over UDP: only the path beneath it differs, so nothing above the connection knows.

- **One packet per binary message,** under the subprotocol `dassie-quic/1`. A text message, or one larger than a tunnel's packet, ends the tunnel. Nothing fragments a packet there, so packets are larger than over UDP, from the first, with MTU discovery off.
- **A second endpoint,** with keys for stateless resets and connection IDs of its own, derived from the node key at paths apart from the UDP endpoint's ([Identity](identity.md#seed-paths)), so that neither endpoint takes the other's connection IDs for its own or can give away the other's reset tokens, and whose socket is the node's tunnels, each at an address of its own. It serves into the same table of connections as the UDP endpoint, so a connection over a tunnel is kept, sent on and relayed through as one over UDP: an uplink sends on the connection its downlink opened, and relays to it. A tunnel a node takes has its TCP connection's address, so places per client address count it as over UDP; one it dials has the server's address, with a port of its own.
- **Every node serves it** on its HTTPS listener ([HTTP](http.md#listeners)), so a core node's URL names where: no link state says so. A node of an earlier release answers 404, which a client takes as a failed dial. A front door serves it too, at the URL nodes dial it at as their relay ([HTTP](http.md#front-doors)).
- **Only a node without a URL dials it, racing UDP.** It dials over UDP, and the tunnel too once UDP has had a head start (`TUNNEL_HEAD_START` in `crates/dassie-node/src/quic/mod.rs`, well within the time to connect) without a connection; the first connection to prove the key it asked for is kept, and the other dropped. This holds for every dial: its uplinks, its chosen relay, bootstrap nodes and hub validators. A node with a URL dials over UDP only, so that a core node whose UDP is blocked is seen to be unreachable rather than hidden. Nothing remembers that UDP was blocked: the next dial tries UDP first again.
- **The outer TLS is not checked.** The client names the URL's host, with ALPN `http/1.1`, and takes any certificate: the QUIC handshake inside pins the node key, so whoever holds the outer TLS, a proxy that intercepts it included, sees only QUIC's ciphertext.
- **Through an HTTP proxy where one is set,** for networks that let nothing out but through one (`crates/dassie-node/src/quic/proxy.rs`). The node reads `https_proxy`, else `HTTPS_PROXY`, an `http://` URL whose user and password, if any, go as Basic auth, and `no_proxy`, else `NO_PROXY`: `*`, names (each with every name beneath it), IP addresses and networks, which it dials directly. Both are read at start, and what the node cannot use of them is warned of and left out ([Node](node.md#startup)). A tunnel then sends the proxy `CONNECT` with the URL's host and port, by name, so a proxy that lets only some names out judges the name, and runs its TLS and WebSocket over the stream once the proxy answers 2xx. The answer is bounded in size and in the dial's time, and anything else is a failed dial. The proxy's own troubles, which its owner may have to set right, are warned of: a proxy that cannot be reached or does not answer, a refusal with a 4xx (407 for credentials it does not take, 403 for a host it does not let out) and an answer that is not HTTP's, each at most once in a while (`WARN_EVERY` in `crates/dassie-node/src/quic/proxy.rs`), since otherwise they show only as failed dials. Only tunnels go through it, since QUIC over UDP cannot. The node still resolves the name first, for UDP and for the guard on private addresses ([Outbound requests](#outbound-requests)), so a network whose DNS does not resolve outside names is not served. The proxy resolves the name again for itself, so the guard does not bind it: a name that also resolves to a private address, or resolves to one later, may reach a private host the proxy can reach. What a proxy reaches is its network's to limit, and the node sends there only a TLS handshake and a WebSocket upgrade for `/quic`, fixed but for the host name, and reads back only whether a QUIC handshake proves the key.
- **One connection per tunnel, and they end together.** A tunnel carries the first connection that arrives on it; another is refused, and a tunnel whose connection has not proved a key within the time to connect, from its upgrade, ends, as does one that has carried no packet within a round trip's bound (`FIRST_PACKET_TIMEOUT` in `crates/dassie-node/src/quic/tunnel.rs`), since a node's client sends its first packet as soon as the upgrade completes. A tunnel that ends closes its connection at once, rather than after the idle timeout, so a node that changes networks dials again at once; a connection that closes ends its tunnel once its close has gone out, so a client sees `NO_ROOM` over a tunnel as over UDP.
- **No Retry:** TCP has already shown that the client receives at its address.
- **A tunnel holds the place of the connection it carries** ([places-by-proved-key](../decisions/places-by-proved-key.md)), and has none of its own. Until its upgrade, its TCP connection holds one of the HTTPS listener's places ([HTTP](http.md#listeners)); once upgraded, it holds one among the QUIC connections being set up, by its TCP connection's address, which its connection takes over, for at most the time to connect and its close; once the connection has proved its key, only the connection's place in its class: a core peer's, a downlink's or anyone else's. So a tunnel without a connection holds nothing for long, a stranger's tunnels count against anyone else's places, and downlinks behind one NAT are bounded per node, as over UDP. A tunnel whose connection is done lingers a moment, so that its close goes out, and gives way to a new tunnel once the tunnels the node took are as many as its places, of every kind: no other bound on tunnels ever binds first.
- **Only nodes take tunnels, not browsers.** A request for a tunnel that carries an `Origin` header is refused with 403 before it holds anything ([HTTP](http.md#route-table)): a browser sends one with every WebSocket handshake, to any host and with any subprotocol a page asks for, and a node never does. Without the refusal any page could have each of its visitors, each from an address of its own, hold a place among the connections being set up, renewed as each ends, and a popular page could keep the node from taking any new connection, over UDP or a tunnel.
- **Bounds on what a tunnel holds.** A tunnel queues a bounded number of packets to send and drops past them, as UDP does, so QUIC's congestion control slows down and the endpoint never waits for a client that does not read; the packets received wait in one bounded queue, and a tunnel that finds it full reads no more until there is room, which TCP passes back to the sender. Its WebSocket buffers about two packets each way, rather than tungstenite's defaults, sized for throughput. A tunnel that ends stays among the node's tunnels, and one whose connection never arrived keeps its place among those being set up, until its close has gone out, which takes a bounded time: so tunnels a client ends and does not let close count too.
- **At shutdown** the endpoint over tunnels closes with the UDP endpoint, and the tunnels end after it, within a bounded time.

### Relayed streams

How a client reaches a node it cannot dial, such as a node behind a NAT ([core-and-periphery](../decisions/core-and-periphery.md), [the design](../designs/periphery.md#5-reaching-a-periphery-node)): through a relay, a node the destination keeps a QUIC connection to. Every QUIC endpoint relays for the nodes connected to it. Relayed traffic is light, Open Payments and owner apps, never peer traffic. `crates/dassie-node/src/quic/relay.rs` has the layouts and bounds.

- **The relay request** is sent to the relay by any QUIC client, which proves a key of its own as every client does: the destination's node ID, in the peer protocol's OER, and a purpose byte. The relay answers with one byte (`Outcome`): joined, unknown destination, busy or refused. Once joined, it copies bytes both ways until both sides end.
- **A relay never dials.** It reaches only a node it holds an open connection to, whoever opened it, and otherwise answers unknown destination. A relay that dialled could be made to connect anywhere.
- **The relayed stream** is what the relay opens to the destination on that connection, naming the purpose and the client's node ID. The destination answers with the same byte, whether it takes the purpose, and the relay passes the answer on. The relay passes the purpose on without reading it, so a new purpose needs only clients and destinations that know it.
- **TLS end to end.** Inside a joined stream the client runs TLS 1.3 with the destination, pinned to the destination's node key and presenting its own, with an ALPN for the purpose. The destination takes it only if the key proven is the client's the relay named. So the relay sees only ciphertext and its size, cannot pass one node's stream off as another's, and cannot put a client's name on a stream of its own.
- **Relay and client in one.** An endpoint may open a relayed stream itself, on a connection it holds to the destination, naming its own ID as the client (`Quic::open_held`), or on a connection it dials to the destination (`Quic::open_direct`); nothing on the wire differs. A [front door](http.md#front-doors) reaches nodes so, and refuses relay requests from others, with the refused outcome; an owner app reaches a node it can dial so.
- **Purposes.** `payments` (ALPN `dassie-pay/1`) carries HTTP/1.1 with Open Payments' routes only ([HTTP](http.md#relayed-streams)), answered under [the node's names](payments.md#the-nodes-names) and [signed](payments.md#signed-responses) as over HTTPS: this is how a [front door](http.md#front-doors) passes requests on. `owner` (`dassie-owner/1`) carries the RPC contract for a paired owner app, framed as on the IPC socket, with the client's key as the device key ([RPC](rpc.md#paired-devices)). The wallet and the owner's HTTP endpoints are never served through a relay.
- **Bounds.** A relay bounds the streams it carries per destination, per client address to each destination, per client address in all, and in all. A client address's share of a destination is smaller than the destination's, so that one client cannot take all of a destination's relayed streams; it is per destination because a front door reaches every node it serves from one address, and its share in all is larger, but smaller than the relay's. A destination bounds the streams it takes per relay address and in all, the share again smaller than the whole. A destination's share at a relay, and a relay's at a destination, is at most half of a connection's streams, so peer requests on the same connection always have room. A stream that carries nothing for a while, or outlives a bound, is reset, and each direction's copy holds a bounded buffer.
- **A chosen relay.** A node can keep a connection to a relay it chooses, which reaches it without any peering ([Node](node.md#a-chosen-relay)).
- **Uplinks relay for their downlinks.** A periphery node holds a connection to each of its uplinks ([Network](network.md#periphery-nodes)), and a relay reaches any node it holds a connection to, so every uplink is a relay for its downlinks, with nothing more to set up.

How a client learns which relays reach a node, the design's records and home nodes, is not built ([roadmap](../roadmap.md#periphery)).

### The hub's stream

How validators and members of a [settlement hub](hubs.md#the-validator-in-the-node) exchange the hub's messages ([settlement-hubs](../decisions/settlement-hubs.md): they prove themselves, so they need no peer protocol envelope, and a member need not be known to the validators). `crates/dassie-node/src/hub/transport.rs` has the bytes and bounds.

- **One exchange per stream:** the request is the hub's ID and one hub message, then the stream's end; the reply is a status byte (taken, no such hub, busy, malformed) and, when taken, the messages the validator sent back while it handled the request, each with its length ahead of it. Nothing else travels: a validator reaches a member only in the reply to its request.
- **Who sent it** is the node whose key the connection proved, and the validator answers that node's requests as one asker's, whoever it is; a validator of the hub has a queue of its own, which members cannot fill, and only a validator is served catch-up. The dialler pins the validator's node ID, of the two keys its acceptance names, at the endpoint the hub's state names, as for a peer request.
- **Over QUIC alone,** for validators and members alike ([quic-only](../decisions/quic-only.md)), and a dial that fails backs off nothing for the peer protocol: a validator that is back is reached at once, its peers back off from it by themselves, until they hear from it again, and a member's account asks again on its own interval.
- **Bounded before it is read:** a request names its hub first; over QUIC the node reads those 32 bytes, resets the stream unless it validates that hub, then takes a place among the hub requests waiting node-wide (members' and validators' apart, and of the members' at most a share per key, so a key anyone can make never holds them all), and only then reads the message: up to the largest message from a validator of the hub, and up to a member's largest request, a submitted claim with the most commitments any rules allow, from anyone else. No place, and the request is answered busy, nothing read. A reply carries a bounded number of messages and bytes, the rest left for the next request; a validator's queue is bounded, and a request past it is answered busy, nothing taken.
- **The state stream,** a stream kind of its own, carries a validator's request for the state after one of the hub's final blocks, by height, and the state back with a status: found, no such hub, not kept, refused, or busy: a node serves at most a couple of states at once (`MAX_STATE_SERVES`), each read off the async runtime and holding its place until written. It serves only the hub's validators, by the key the connection proved, over QUIC alone, and has a bound of its own, the largest state the node stores, since a state can be far larger than a message. The asker checks the state against the block's root before it takes it.
- **The founding stream,** a stream kind of its own, carries a sponsor's request while it founds a hub, and the validator's answer, each `dassie_hub::founding`'s in canonical OER, up to a bound of their own: the terms to accept, the rules whose genesis to sign, the genesis certificate to run, and whether a quorum checked the escrow ([Settlement hubs](hubs.md#founding-a-hub), [hub-founding](../decisions/hub-founding.md)). There is no hub ID yet, so it names none. Over QUIC alone, pinned to the validator's node key; the validator takes the key the connection proved as the asker. **Nothing is read before the asker is known:** a stream from a node the validator file does not list, or to a node without one, is reset after its kind byte, as one of an unknown kind; a listed sponsor's takes one of a few places node-wide first, which bound the requests read and decided at once, and is answered busy, unread, when none is free. The validator then answers only the sponsor the terms name.
- **A member's `Payout` request** on the hub's stream asks for the payout set the validator signed, from a place in it on, and is answered with a page of it, or nothing while the hub runs ([Settlement hubs](hubs.md#payout-bundles)).

### Statuses

The status is part of the protocol, and senders depend on one property of it: **400, 404, 408, 409, 413, 429 and 503 mean the message was not acted upon.** Only these, or a request that surely never left, let a sender treat a message as undelivered: the connector rejects a Prepare at once on them, with T05 on a 429 and T01 on the rest, and leaves every other failure to expiry ([Connector](connector.md#responses-and-expiry)). A peering refusal is therefore a 200 with `refused`, since the responder did act on the request.

- **The peer node's refusals** are 400, 409, and 429 or 503 for a rate or a table that is full, each before it changes anything; their causes are in `crates/dassie-peer/src/node/inbound.rs`.
- **The transport's** come before the peer node sees the body ([Transport](#transport)): 429 while the sender's failed requests are over their rate, 503 with no place among the requests waiting, and 413, 408 or 400 for a body too large, too slow or broken. They are what a node under load answers most, so a sender that waited them out would hold what its Prepares carry until they expire.
- **A 503 also answers a request whose engine stopped** before what it changed was on disk: the engine restarts from its last good commit, without it ([Node](node.md#the-engine)).
- **A front door** answers every peer request 404, since it handles none ([HTTP](http.md#front-doors)).

Every other status may follow a request that was acted upon. A node never answers one of the set after acting, and a status joins the set only if no node, of any release, gives it after acting. An answer that ends before its two bytes of status is no status: it was cut short, and its request's outcome is unknown ([Outbound requests](#outbound-requests)). The set is `not_acted_upon` in `crates/dassie-peer/src/io.rs`.

## Encoding

Messages are canonical OER as [Encoding](encoding.md) describes it, read strictly: an unknown CHOICE tag, a value that does not fill its container, or trailing bytes are malformed. The layouts are in `crates/dassie-peer/src/wire/`.

A 200 response body has no tag of its own: its type follows from the request's kind.

## Authentication

A request is the request of the node whose key its QUIC connection proved, and of no other ([peer-protocol-v1](../decisions/peer-protocol-v1.md)). Nothing in its bytes names its sender: the transport hands the peer node the key with the body (`PeerNode::handle_inbound`).

- **Every request is authenticated,** since every client proves a key in the handshake, and every answer comes from the key the dialler pinned. Reading needs no relationship: anyone may ask for link states, node lists, name lists and peering info, under a key of its own making. Everything else is taken only from a node the recipient holds the right thing with, as that node's own: a Prepare from a peer, a settlement from a node with a settlement channel, a renewal from a registered node or a name's holder. A request from the node's own key is refused.
- **Nothing a request carries is believed of its sender:** a link state in a registration or a peering request must verify and name the key that sent it ([Message set](#message-set)). So someone who sees a node's request and sends it again sends it as its own, under its key, where it gets what that key may have: a copy of a peer's Prepare, settlement or registration from anyone else is refused as a stranger's.
- **No replay protection beside TLS's.** QUIC runs TLS 1.3 without 0-RTT, so a connection's keys are its own and a captured packet does not play on another; what a sender sends again itself, after a lost answer, is told from a copy by the request ID of a packet and the sequence of a settlement ([Message set](#message-set)), which every message that moves money carries. So nothing about replays is kept or persisted, and a restart refuses nothing for its age.
- **Peer requests are never relayed.** A relayed stream carries only the purposes of [Relayed streams](#relayed-streams), so a connection's key is always the sender's, never a relay's.
- **A message from a peer, or an answer to one of our requests,** marks the peer as heard from ([Network](network.md#advertised-peers)).

## Link states

A node's link state ("node info") is its signed description of itself: its URL, alias, its two keys, the schemes it takes peers on and the peers it advertises. How it is issued, spread and refreshed is in [Network](network.md#link-states). The signature is pure Ed25519 over the signed bytes as received.

- **Only a core node lists neighbors.** A periphery node's link state lists none, however many uplinks it keeps ([periphery-lists-no-neighbors](../decisions/periphery-lists-no-neighbors.md)). Nothing in the protocol changes: a node that reads one listing its uplinks, from an older periphery node, routes no differently.
- **Every node decodes the same bounds:** at most `MAX_ENTRIES` entries, its neighbors and extensions, `MAX_OFFERS` settlement offers of at most `MAX_OFFER_DETAILS` bytes of details each, and `MAX_NODE_INFO_BYTES` of signed bytes (`crates/dassie-peer/src/wire/mod.rs`). A state past them is refused by all, so they are protocol, and a node checks its own against them before it signs it ([Network](network.md#the-own-link-state)).

- **Extensions** of unknown type are kept, since the signature covers them, and otherwise ignored. That is how later versions add fields. Type 2, with an empty value, says it is a periphery node, which has no URL ([Network](network.md#periphery-nodes)); type 3, a `UInt16` that is not 0, is the UDP port of the node's [rate feed](rate-feed.md#finding-a-feed) at its URL's host, which only a node with a URL names; type 1 is kept for a post-quantum key ([Versions](#versions)). A node that reads an extension of a known type that breaks its rule, a feed port of another length, say, takes it as absent and still keeps and forwards the link state, as it would one of an unknown type; so adding a type never needs a new protocol version.
- The alias is an unverified display name.

### Settlement offers

A link state offers each settlement scheme the node takes peers on in one list, `settlement`, after its key, in the node's order of preference ([settlement-offers](../decisions/settlement-offers.md), `SettlementOffer` in `crates/dassie-peer/src/wire/node_info.rs`).

- **An offer is a scheme and its details:** the scheme's ID, and an octet string the scheme defines, its details in their canonical OER. Over a settlement hub, they are the hub's ID, the hash of its rules, and the node's account in it, 0 while it has none, to be [paid in](../designs/settlement-hubs.md#5-joining) (`HubDetails`); the stub's are empty. They say what a node needs to know of a scheme before it asks to peer on it; the rest travels in the peering's own messages.
- **A scheme is offered exactly when the node takes peers on it:** a node asks for and accepts peerings and further methods only on the schemes it offers ([Network](network.md#asking-and-answering)). Nothing says that a node takes no new peers on a scheme it offers: one that wants none stops offering it. Its owner does so by removing the scheme, which winds down each method on it with `methodDrop` ([Network](network.md#settlement-methods)); a scheme the node leaves out for a while, before its first sync, while it cannot receive or once it stopped, keeps the peerings made on it ([Network](network.md#asking-and-answering)).
- **The node's own list** offers no scheme twice, no hub twice, and at most `MAX_OWN_HUBS` schemes over hubs, one per asset (`crates/dassie-peer/src/node/mod.rs`); the node checks it before it signs its link state.
- **The bounds are above what a node offers,** `MAX_OFFERS` above `MAX_SCHEMES` and `MAX_OFFER_DETAILS` above a hub's details, so that a later release may offer more schemes, or schemes with more to say, such as one that settles directly, without a new version.
- **A node reads only the offers of schemes it offers itself,** by its own offer's kind: the hub's details on a scheme it offers over a hub, and none on any other. An offer on a scheme it does not offer is kept and forwarded, since the signature covers it, and otherwise passed over: two nodes peer only on schemes both offer.
- **An offer that breaks the rules is taken as absent,** and the rest of the link state stands, as for an extension that breaks its rule: an offer whose scheme an earlier offer names, one whose details are not its scheme's canonical encoding, and one over a hub that an offer taken before it names. Which offers a node reads depends on the schemes it offers, so two nodes may read a broken list differently; each reading decides only that node's own peering with the list's node.
- **Which offers become methods** is the network's ([Network](network.md#settlement-methods)): each scheme both offer, over a hub only where both name the same hub and one of them at least has an account in it, in the asking node's order.

### Verification

A link state verifies when its URL has the node-URL syntax, or, in a periphery node's link state, is empty, its Ed25519 key is a valid point not of small order, and its signature verifies. Its node ID is not sent: a node takes it from the two keys. Every 32 bytes are an SLH-DSA key, so that key has nothing to verify. All nodes must agree on which states verify, or the network splits on them:

- **Signatures follow ZIP-215** (`ed25519-zebra`), as the original's verifier did. Being stricter could split the network on edge-case signatures. Small-order keys are refused because under ZIP-215 one signature verifies every message under such a key.
- **URL syntax is part of verification** for the same reason: an HTTPS origin with a lowercase hostname or IP literal and an optional port, nothing else (`crates/dassie-peer/src/wire/url.rs`). A node whose own URL does not fit publishes no link state.
- **An empty URL** verifies only with the periphery extension, and the extension only with an empty URL: a periphery link state with a URL would be taken for a downlink's, accepted without a probe and dialled at a URL nobody checked. A node that does not know the rule refuses such a state, which is harmless only because a periphery node's link state never floods: only its uplinks see it, in its peering requests and heartbeats, and only nodes that take downlinks need the rule.

## Message set

What a node trusts, and the rules a sender and a recipient rely on, by message. The handlers are in `crates/dassie-peer/src/node/inbound.rs`; "peered" means a peering that is `peered` or `terminating`, "active" means `peered` ([Network](network.md#lifecycle)).

- **Link states** (`linkStateUpdate`, `linkStateRequest`) are trusted by their signature, from anyone. A requester takes only the states of nodes it asked about, so a responder cannot stuff its table. An answer carries stored states as received, without verifying them again; the requester verifies.
- **Embedded node info** in `peeringRequest` and `registration` must verify and name the sender, and may not be far ahead of the recipient's clock.
- **Node lists** are trusted only from a configured bootstrap node, by the connection, pinned to its configured key ([Network](network.md#membership)). A list's hash is computed over the bytes received.
- **`peeringRequest`** names the scheme and carries its data. The responder probes the requester's URL, unless the requester is a periphery node, which has none, and records the peering before it answers ([Network](network.md#peering)).
- **`registration`** of a periphery node's link state is refused: a periphery node is in no node list.
- **`linkStateRequest`** is never answered with another node's periphery link state.
- **`interledgerPacket`** carries a Fulfill or Reject, the answer to a Prepare that came in a `methodPacket`, correlated with it by a request ID per peer; a Prepare in one is malformed (400). A Prepare and its answer are separate one-way messages. A Prepare needs an active peering, so no new packet enters a peering being ended. A Fulfill or Reject needs a peering, active or being ended: a peering ends only once nothing is in flight with the peer, so one from a node not peered answers nothing the node waits for, and gets 409. A Fulfill or Reject is sent again, for a bounded time, until a 200 arrives, or a 400 or 409, which says it will never be taken; a copy that arrives twice is dropped by the peer's connector. A Reject that never arrives has the effect of expiry; a Fulfill stays booked whether it arrives or not ([own-fulfills](../decisions/own-fulfills.md)). Once one of our packets to a peer surely did not arrive, the node takes no new Prepare from it until it answers a request of ours, since our Fulfill could not arrive either; the heartbeat and the Rejects sent again find out when it does ([unreachable-peers](../decisions/unreachable-peers.md)). The packet itself is the connector's ([Connector](connector.md)).
- **`methodPacket`** carries every Prepare between peers: the scheme of the [settlement method](../decisions/settlement-methods.md) it travels on, the Prepare and, on a method over a settlement hub, the payer's commitment in the same message, so the payee never sees a Prepare apart from its commitment ([the design](../designs/settlement-hubs.md#4-peering-over-a-hub)); on any other method the commitment is empty. The method's scheme says whether it is over a hub (`PeeringHooks::uses_commitments`). On a method over a hub a Prepare may also come without one, as it does while a side of the peering has no account in the hub ([joining by being paid](../designs/settlement-hubs.md#5-joining)): whether two peers promise is decided per peer by their schemes (`Commitments::commits_with`), each by its own answer, which can differ for a while, so the peer protocol hands a commitment on when there is one and leaves the rest to the node. A Prepare on a scheme the peering has no method on, or with a commitment where its method takes none, is refused with 409, as a Prepare from a node not peered is, so the sender rejects it at once. A node that refuses one for a method it does not hold, while it holds the peering, also tells the sender with a `methodDrop`, so a method only one side still holds, its drop lost with a restart, is repaired as a [one-sided peering](network.md#one-sided-peerings) is. Only a Prepare travels in a `methodPacket` (otherwise 400); its Fulfill or Reject goes back in an `interledgerPacket`, under the rules above.
- **`methodAdd`** asks to add a method to an active peering, with the scheme's data, as a `peeringRequest` asks for a peering's first, and is answered as one is, after the method is recorded; a repeat for a method the peering has is accepted again. **`methodDrop`** names a method the sender holds no more, after collecting on it where a settlement on it could still arrive ([Network](network.md#settlement-methods)): the recipient drops it at once and answers 200, also for a method it does not have, and a peering it leaves with none ends ([Network](network.md#settlement-methods)). Both need a peering, otherwise 409.
- **The reply to a Fulfill** is empty, and on a peering with a method over a hub, or for a Prepare that went on one dropped since, carries the payer's claim. It says nothing of what the recipient did with the Fulfill: each side books its own ([own-fulfills](../decisions/own-fulfills.md)). The node that sent the Fulfill hands a claim to the scheme, and takes an empty reply, as every other peering's is, as a Fulfill that arrived. The commitment and the claim are opaque to the peer protocol and bounded by it; the hub's scheme reads them.
- **`settlement`** is accepted from any node we hold a settlement channel with, peered or not, open or closed, so a settlement that arrives after the peering ended, or after the channel closed, is still credited. Its sequence belongs to the pair of nodes, not to a peering, and never resets: a closed channel keeps it on disk ([closing-channels](../decisions/closing-channels.md)). The sender sends one at a time, in order, again until a 200 arrives, across restarts, with a backoff. One whose last try got no answer also goes at once when the node next answers any request of ours, since it is reachable again, rather than waiting out the backoff. That early try is made once per silence, so a node that never answers it gets it at most twice as often as the backoff alone would send it; an answer gives it up, since a refusal or a busy node is not helped by going early. The recipient answers a sequence it already applied with 200 and does nothing; it applies only the next one. On a scheme whose messages book what they state, the stub's, it applies one only if its books can take it, checked before the scheme sees it (otherwise 400 and nothing changes); over a settlement hub the message is a bare notice, with no data, which books nothing and is taken whatever it states or carries ([Settlement](settlement.md#incoming-settlements)); one on a scheme it does not run, as one its owner removed, it acknowledges and books nothing, so that the channel goes on. So each settlement is credited exactly once ([Settlement](settlement.md#settlement-channels)).
- **`settlementRequest`** asks an active peer to settle on a scheme, leaving the amount to it ([Settlement](settlement.md#asking-a-peer-to-settle)). Its answer is what the peer then has on its way to the asker, in the scheme ledger's units, as eight bytes ([Settlement](settlement.md#settling-on-request)); an answer of any other length says nothing of the amount, and an end, or a method's winding down, waits it out as one that never came. A node ending the peering, and not yet saying so, answers 0 ([Network](network.md#termination)).
- **`peeringTermination`** is sent until a 200 or a 409 arrives, or the termination times out. A 409 means the recipient holds no peering with us, so there is nothing left to end ([Network](network.md#termination)).

### Names

The messages that register and hold a name ([the design](../designs/names.md), [names-by-earliest-commitment](../decisions/names-by-earliest-commitment.md)). A registrar, a node that is one of its own bootstrap nodes, takes them and decides by its own log ([Network](network.md#names)); any other node answers each with 409, the list requests too, so a registrant takes nothing as done. The layouts are in `crates/dassie-peer/src/wire/`, and what a name and a commitment are in `crates/dassie-peer/src/names/`.

- **A name** is a DNS label, so that a front door can serve it as `<name>.<domain>`: lowercase letters, digits and hyphens, not starting or ending with one, and without hyphens in its third and fourth places, which DNS keeps for encodings such as `xn--` (no internationalized names at first). It is shorter than a [node ID](identity.md#node-id), so no name is ever read as a node ID, nor a node ID as a name. Only lowercase, so that a name has one spelling, and so one commitment and one holder. Messages and lists read any name of that syntax; the names no owner may register are a list in the code (`RESERVED`) that only a registrar consults, so changing it changes no encoding.
- **The commitment** is SHA-256 over the canonical OER of a domain OID of its own ([Identity](identity.md#object-identifiers)), the name, the holder's node ID and a 32-byte salt, each field of fixed length or with its length ahead of it, so no two inputs hash the same bytes (`commitment.rs` has the layout, and `crates/dassie-peer/tests/wire.rs` a golden value). The holder inside it makes a copied commitment useless to anyone else, and the salt keeps a dictionary of likely names from opening it.
- **`nameCommit`** carries only the commitment, so it shows the registrar nothing of the name; it counts against the caps of its sender. Any node may send it: the holder is sealed inside the commitment, so only the holder can unseal it, and a registrant sends its own. Its answer is the receipt: the commitment's position in the registrar's log and when its window closes, by the registrar's clock. It is sent only once the commitment is on disk, and a commitment in the log already gets its receipt again. A registrar refuses one with 503 when its log or its names are full, 409 for a cap on the sender or its network, and 429 for its rate.
- **`nameUnseal`** carries the name and the salt; the holder is the sender, so a node can open only its own commitments. A valid unsealing is answered with an empty 200, whether it still contends for the name or has lost already, so the answer tells nothing of commitments still sealed, and again for a retry while its commitment is in the log; an invalid one, or one past the holder's cap on names, gets 409 ([The registrar](network.md#the-registrar)). **`nameRenew`** carries the name, and is answered with its expiry, as a registration is: a new one once its expiry is near, the one it has before; another node's renewal, or one of a name not held, gets 409.
- **`nameListHashRequest`** and **`nameListRequest`** read a registrar's name list as their counterparts read its node list, and only read: the names listed, with their holders and expiries. Every node polls them with the node lists, and takes a name's holder from a quorum of the lists ([Network](network.md#holders)). A list is sorted by name with each name once, or it is malformed, so a list has one encoding and one hash; it is bounded by `MAX_NAME_LIST`, which the transport's bound on a response holds (`crates/dassie-node/src/quic/mod.rs`).

## Outbound requests

The node's outbound connections are peer requests over QUIC, and, to servers that are not nodes, HTTPS requests (Open Payments to other wallets, exchange-rate sources: [Payments](payments.md), [Connector](connector.md#sources)) and WebSockets to ledgers' servers, in `crates/dassie-node/src/outbound.rs`. All of them resolve names through one `Resolver`, so one guard applies to all; QUIC needs nothing else of the outbound client, which trusts the platform's roots that QUIC, pinning each node's key, does not use. A peer or a registrant chooses the URL we connect to, so:

- Requests go only to `https` URLs, and redirects are never followed. A QUIC connection goes to the host and port of such a URL.
- Private, loopback, link-local and similar addresses are refused, both as IP literals and after DNS resolution (`crates/dassie-node-core/src/address.rs`). An IPv6 literal is read as the HTTP client reads it, and one the guard cannot read counts as private, so the guard and the client cannot disagree. `DASSIE_PEER_ALLOW_PRIVATE` lifts this for dev and tests.
- In-flight requests are bounded in total and each way apart. Peer requests are bounded per node, by its ID (`crates/dassie-node/src/quic/bounds.rs`), so nodes behind one host, or periphery nodes without a URL, each get a share; requests to other servers are bounded per host. Neither kind takes the other's places, so a burst of Open Payments cannot stall the peer protocol. ILP packets do not count, so their responses always get through.
- Every WebSocket URL is read by the same rules as an `https` one (`OutboundClient::websocket`): `wss://`, or `ws://` only where private addresses are allowed, with a host, no user info, and a port that is a number other than 0.
- **Failures** are of two kinds: *not delivered* (refused before sending, or the connection failed) and *unknown* (a timeout after sending, a broken response, or one too short to hold a status). Only the first, or a status that means not acted upon ([Statuses](#statuses)), says a request surely had no effect.

## Decisions

- [protocol-upgrades](../decisions/protocol-upgrades.md): the version is the connection's ALPN, offered as a list, and a release speaks the one before too.
- [peer-protocol-v1](../decisions/peer-protocol-v1.md): v1 instead of v0; the sender is the key the connection proved, with no MAC, sender field or replay state of its own.
- [membership-economics](../decisions/membership-economics.md): authenticated node lists and the limits on free registration.
- [peering-lifecycle](../decisions/peering-lifecycle.md): `peeringTermination`.
- [own-fulfills](../decisions/own-fulfills.md): `settlementRequest`, no credit on the wire, and no verdict on a Fulfill.
- [places-by-proved-key](../decisions/places-by-proved-key.md): QUIC connections hold places by the key they proved: core peers, downlinks and anyone else apart.
- [quic-over-websocket](../decisions/quic-over-websocket.md): QUIC's packets over a WebSocket where UDP is blocked, rather than a second stream transport; served by every node, dialled only by nodes without a URL, racing UDP.
- [unreachable-peers](../decisions/unreachable-peers.md): no Prepare taken from a peer our packets surely do not reach.
- [settlement-hubs](../decisions/settlement-hubs.md): the commitment with a Prepare and the claim in the reply to a Fulfill, for peerings over a hub.
- [names-by-earliest-commitment](../decisions/names-by-earliest-commitment.md): the name messages, a commitment sealed by its holder and salt.
- [settlement-methods](../decisions/settlement-methods.md): `methodPacket`, `methodAdd` and `methodDrop`, part of version 2.
- [settlement-offers](../decisions/settlement-offers.md): one list of the schemes a node takes peers on, each with its scheme's details, in place of scheme entries and hub extensions.
