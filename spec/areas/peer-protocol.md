# Peer protocol

Dassie nodes talk to each other with the peer protocol v1: OER messages sent over QUIC, authenticated by a MAC from the two nodes' static keys. This document covers what the protocol guarantees, what a node trusts from whom, and what must stay compatible. What the messages are used for (the node table, membership, peering, routing) is in [Network](network.md).

**Paths:** `crates/dassie-peer/src/wire/` (layouts), `crates/dassie-peer/src/names/` (names and their commitments), `crates/dassie-peer/src/auth/` (MACs, replay), `crates/dassie-peer/src/node/inbound.rs` (handlers and statuses), `crates/dassie-node/src/quic/`, `crates/dassie-node/src/peer_server.rs`, `crates/dassie-node/src/peer_client.rs`, `crates/dassie-node-core/src/address.rs`, and for the hub's stream `crates/dassie-node/src/hub/transport.rs`, `crates/dassie-node/src/quic/hub.rs`, `crates/dassie-hub/src/founding/wire.rs`
**Read with:** [Network](network.md), [Identity](identity.md), [Encoding](encoding.md), [Settlement](settlement.md), [Connector](connector.md)

## Versions

- v1 keeps v0's message set, OER layouts and OIDs, and adds sender authentication, replay protection, authenticated responses and new messages. It carries them over QUIC ([quic-only](../decisions/quic-only.md)). The envelope's version byte is `1`; anything else is refused, so v1 and v0 nodes do not interoperate ([peer-protocol-v1](../decisions/peer-protocol-v1.md)).
- A link state is signed under a new OID (`…1399.1.3`), so a node info signed under v0 is never a v1 link state.
- Some fields and replies exist only for nodes of 0.1, and must not change while such nodes may run:
  - `credit` in `peeringRequest` and its acceptance is sent as 0 and ignored: a node knows only the credit it extends, never the credit extended to it ([own-fulfills](../decisions/own-fulfills.md)). A later protocol version drops it.
  - The reply to a Fulfill starts with `01` ("accepted"), and is nothing more but on a peering over a settlement hub ([Message set](#message-set)), which nodes of 0.1 never make. Nodes of 0.1 read it as a verdict on whether the Fulfill counted; "accepted" tells them to keep their own books, as every node does.
  - A Fulfill or Reject is taken from any node we hold a settlement channel with, peered or not, since nodes of 0.1 ask for verdicts after a peering ended.
- `settlementRequest` is not in 0.1: a node of 0.1 refuses it with 400, never asks, and settles unasked, so nodes of 0.1 and 0.2 do not settle with each other ([versions-0-1-and-0-2](../decisions/versions-0-1-and-0-2.md)). Its answer carries the amount on its way ([ending-a-peering](../decisions/ending-a-peering.md)); an empty answer is still read, as saying nothing of the amount.
- **Names** came after v1 and need no new version: their messages take new tags (13 to 17), which a node that does not know them refuses as malformed with 400, one of the statuses that say a message was not acted upon ([Statuses](#statuses)). A registrant takes that as a refusal, as from a registrar that withholds its receipt ([Names](#names)).
- **`PayToEnter`,** a refusal reason, came after v1 and needs no new version: a node reads a reason it does not know as unspecified, and backs off from it as from capacity. An uplink gives it only to a downlink that an entry payment would get in ([pay-to-enter](../decisions/pay-to-enter.md)).
- **QUIC** came after v1 and needed no new version: the messages, MACs and statuses are those v1 had over HTTPS, and a node says it takes QUIC in its link state ([Transport](#transport)). Every node takes it, and QUIC is the only transport ([quic-only](../decisions/quic-only.md)).
- **Post-quantum.** Authentication tag `[2]` is parsed only to be refused: it is reserved for a scheme on the X-Wing hybrid KEM, whose key would travel as link-state extension type 1. Neither is built ([roadmap](../roadmap.md#smaller-open-points)).

The layouts are pinned by golden vectors ([Test vectors](#test-vectors)); a change to any of them is a new protocol version.

## Transport

Requests travel over QUIC, the only transport ([quic-only](../decisions/quic-only.md)). The transport checks only the client's rate and the body's size; the peer node decides everything else, and answers only once what the request changed is on disk ([core-and-periphery](../decisions/core-and-periphery.md) chose QUIC: peer traffic is heavy, and one HTTP request per packet costs).

- Unauthenticated requests, and requests that fail, are rate-limited per client address. Nodes authenticate every request, so this rations tools and failures, not peers.
- The number of requests waiting on the node is bounded, in all and per client address; past it the node answers 503. Each client address has a share of them, since one connection carries many requests at once, so that one address cannot take every place. A body that is too large, broken or too slow is charged like a failed request, so a client cannot hold places over and over (`crates/dassie-node/src/peer_server.rs`).

### QUIC

- **One endpoint per node on UDP,** at its URL's host and port: 443 under systemd, the HTTPS listener's port number when standalone ([Node](node.md#runtimes)). It both takes and makes connections. A link state says the node takes QUIC with extension type 2 ([Link states](#link-states)), which a node issues only when it has its UDP socket on its URL's port. A node does not run without its endpoint ([Node](node.md#runtimes)). Where UDP does not get through, a periphery node reaches it over a WebSocket on the same host and port instead, into a second endpoint whose socket is the node's tunnels ([QUIC over WebSocket](#quic-over-websocket)); a node with a URL dials over UDP only. Places, one connection per pair of nodes and the connection standing by span both endpoints: a connection over a tunnel holds a place, is kept, replaced and stands by as one over UDP.
- **Keys, not certificates.** Each side presents a self-signed certificate for its Ed25519 node key. A dialler refuses a server whose key is not that of the node it asked for; a server takes any client that proves a key, and learns its node ID from it. TLS 1.3 only, ALPN `dassie/1`. No certificate authority is involved, so a node needs no certificate for its hostname to be reached over QUIC. TLS signs with a context string of its own, so a handshake signature never passes for a link state's (`crates/dassie-node/src/quic/keys.rs`).
- **Every bidirectional stream starts with a kind byte** (`StreamKind` in `crates/dassie-node/src/quic/mod.rs`): a peer request, a relay request or a relayed stream ([Relayed streams](#relayed-streams)), or a settlement hub's message, state or founding ([The hub's stream](#the-hubs-stream)). A stream of a kind the node does not know is reset.
- **Streams are read in order, never out of order.** A stream is read in order for its kind byte, and quinn-proto miscounts a stream that then switches to reading out of order while a retransmitted copy of its start is still buffered: it never sees the stream's end, and underflows when the stream is dropped, which with overflow checks on ([Engineering](../engineering.md#requirements-on-every-crate)) aborts the node. So the node reads the rest in order too (`read_in_order` in `crates/dassie-node/src/quic/mod.rs`), and clippy denies quinn's `read_to_end`, which reads out of order.
- **A peer request** is the envelope, then the stream's end; the answer is the status as two bytes, big-endian, then the body ([Statuses](#statuses)). The ALPN names what the bytes are, so nothing else does.
- **One connection per pair of nodes, used both ways.** A node sends on a connection another opened to it; when both dialled, the one the lower node ID opened is kept. A connection unused for a while closes, which peers' heartbeats prevent. A connection that is open but not the one used stands by, and takes over when the one used closes, so that a connection the other node keeps open for its own sake ([A chosen relay](node.md#a-chosen-relay)) is never lost behind one that goes idle.
- **A periphery node is reached only over the connections it opened** ([Network](network.md#periphery-nodes)). It has no URL, so a peer request to it goes on the connection it opened, or on one it opened since that stands by, or fails as not delivered: it is never dialled. The connections it dials for requests keep themselves alive as the one to a chosen relay does, well within the idle timeout, since they are the only way its uplinks reach it, and a NAT drops a mapping that goes quiet.
- **A crash ends connections at once.** The key for stateless resets derives from the node key ([Identity](identity.md#seed-paths)), so it is the same after a restart: a node that crashed, closing nothing, still tells peers their old connections are gone, and they connect again at once, as over TCP, instead of waiting out the idle timeout.
- **Backing off.** A request to a node whose QUIC cannot be reached (UDP filtered, a restart, a new address), or that has no room for us, is not delivered, and the node is not dialled for peer requests for a while: a second after a first failure, twice the last wait after each that follows, up to a minute. A connection it keeps ends the wait: one it opened to us, or one of ours a request got through on. A dial alone does not, since a node without room closes only after the handshake. So a peer that comes back and dials us is asked again at once, and one that keeps refusing for room is dialled ever less often. Making a connection takes at most the request's time, the name's addresses tried in turn, so a request that cannot be sent fails as not delivered within it. Only a peer request's dial that had time enough to judge, or its connection refused for want of room, counts: a relayed stream or a hub's message that cannot reach its node backs off nothing, and dials whatever the wait. A periphery node's dial fails only when both UDP and the tunnel failed ([QUIC over WebSocket](#quic-over-websocket)), and has time enough to judge only when the tunnel had it too, after UDP's head start.
- **Bootstrap nodes** known only from the configuration are dialled at the configured URL, pinned to the configured ID, before their link state arrives.
- **Bounds:** a client's requests open on one connection no more than its share, bounded windows, and a bounded time to write an answer a client does not read.
- **A connection holds a place by who opened it** ([places-by-proved-key](../decisions/places-by-proved-key.md), `crates/dassie-node/src/quic/places.rs`). While it is set up, it holds one among the connections being set up, in all and per client address, for at most the time to connect; once those run short, a client must show it receives at its address before it holds one. Once the handshake has proved its key, it holds a place in its class, by our own peerings with that key: a core peer's, a downlink's, or anyone else's (relay clients, nodes that chose us as their relay, registrants, nodes asking to peer). Anyone else's are bounded in all and per client address; core peers and downlinks have room for as many nodes as the peer node keeps of each, and a small share per node. So downlinks never take the room of core peers or of relayed streams' clients, and nobody takes the core peers' room. A tunnel holds these places for the connection it carries, by its TCP connection's address ([QUIC over WebSocket](#quic-over-websocket)).
  - **The class follows the peerings.** When a peering begins or ends, its node's connections move to their new class, or close if it has no room.
  - **Nothing a node says** decides its class: not its link state, nor the sender of its messages. Only the key it proved, which it cannot borrow, and our peerings; a node that opens connections under other keys is anyone else, under anyone's bounds.
  - **No room is said with a close code of its own** (`NO_ROOM` in `crates/dassie-node/src/quic/mod.rs`), which a connection refused once its key is known closes with, before any stream on it is read. A client takes it as a connection refused outright: nothing it sent was delivered, it backs off from the node, and a relayed stream finds the relay busy. Every other close, at shutdown, for a newer connection or for a class without room, uses 0, since requests may have been read; a node that does not know the code reads it so too.
  - **A node past its share** replaces its own oldest connection, by when each was made, not anyone else's: the one it made last is the one it uses. An older connection does not replace a newer one, and closes instead.
- **At shutdown** the endpoint stops taking connections, lets the requests in progress finish for a bounded time, and only then closes, as the HTTPS listener does ([Node](node.md#shutdown)).

### QUIC over WebSocket

Where UDP does not get through, a periphery node carries the same QUIC packets over a WebSocket at `/quic` on the core node's HTTPS listener ([quic-over-websocket](../decisions/quic-over-websocket.md), `crates/dassie-node/src/quic/tunnel.rs`). The connection inside is an ordinary QUIC connection, with the handshake, streams, places, `NO_ROOM`, keep-alives and relayed streams it has over UDP: only the path beneath it differs, so nothing above the connection knows.

- **One packet per binary message,** under the subprotocol `dassie-quic/1`. A text message, or one larger than a tunnel's packet, ends the tunnel. Nothing fragments a packet there, so packets are larger than over UDP, from the first, with MTU discovery off.
- **A second endpoint,** with a key for stateless resets of its own, derived from the node key at a path apart from the UDP endpoint's ([Identity](identity.md#seed-paths)), so that neither endpoint can give away the other's reset tokens, and whose socket is the node's tunnels, each at an address of its own. It serves into the same table of connections as the UDP endpoint, so a connection over a tunnel is kept, sent on and relayed through as one over UDP: an uplink sends on the connection its downlink opened, and relays to it. A tunnel a node takes has its TCP connection's address, so places per client address count it as over UDP; one it dials has the server's address, with a port of its own.
- **Every node serves it** on its HTTPS listener ([HTTP](http.md#listeners)), so a core node's URL names where: no link state says so. A node of an earlier release answers 404, which a client takes as a failed dial. A front door serves it too, at the URL nodes dial it at as their relay ([HTTP](http.md#front-doors)).
- **Only a node without a URL dials it, racing UDP.** It dials over UDP, and the tunnel too once UDP has had a head start (`TUNNEL_HEAD_START` in `crates/dassie-node/src/quic/mod.rs`, well within the time to connect) without a connection; the first connection to prove the key it asked for is kept, and the other dropped. This holds for every dial: its uplinks, its chosen relay, bootstrap nodes and hub validators. A node with a URL dials over UDP only, so that a core node whose UDP is blocked is seen to be unreachable rather than hidden. Nothing remembers that UDP was blocked: the next dial tries UDP first again.
- **The outer TLS is not checked.** The client names the URL's host, with ALPN `http/1.1`, and takes any certificate: the QUIC handshake inside pins the node key, so whoever holds the outer TLS, a proxy that intercepts it included, sees only QUIC's ciphertext.
- **One connection per tunnel, and they end together.** A tunnel carries the first connection that arrives on it; another is refused, and a tunnel whose connection has not proved a key within the time to connect, from its upgrade, ends, as does one that has carried no packet within a round trip's bound (`FIRST_PACKET_TIMEOUT` in `crates/dassie-node/src/quic/tunnel.rs`), since a node's client sends its first packet as soon as the upgrade completes. A tunnel that ends closes its connection at once, rather than after the idle timeout, so a node that changes networks dials again at once; a connection that closes ends its tunnel once its close has gone out, so a client sees `NO_ROOM` over a tunnel as over UDP.
- **No Retry:** TCP has already shown that the client receives at its address.
- **A tunnel holds the place of the connection it carries** ([places-by-proved-key](../decisions/places-by-proved-key.md)), and has none of its own. Until its upgrade, its TCP connection holds one of the HTTPS listener's places ([HTTP](http.md#listeners)); once upgraded, it holds one among the QUIC connections being set up, by its TCP connection's address, which its connection takes over, for at most the time to connect and its close; once the connection has proved its key, only the connection's place in its class: a core peer's, a downlink's or anyone else's. So a tunnel without a connection holds nothing for long, a stranger's tunnels count against anyone else's places, and downlinks behind one NAT are bounded per node, as over UDP. A tunnel whose connection is done lingers a moment, so that its close goes out, and gives way to a new tunnel once the tunnels the node took are as many as its places, of every kind: no other bound on tunnels ever binds first.
- **Only nodes take tunnels, not browsers.** A request for a tunnel that carries an `Origin` header is refused with 403 before it holds anything ([HTTP](http.md#route-table)): a browser sends one with every WebSocket handshake, to any host and with any subprotocol a page asks for, and a node never does. Without the refusal any page could have each of its visitors, each from an address of its own, hold a place among the connections being set up, renewed as each ends, and a popular page could keep the node from taking any new connection, over UDP or a tunnel.
- **Bounds on what a tunnel holds.** A tunnel queues a bounded number of packets to send and drops past them, as UDP does, so QUIC's congestion control slows down and the endpoint never waits for a client that does not read; the packets received wait in one bounded queue, and a tunnel that finds it full reads no more until there is room, which TCP passes back to the sender. Its WebSocket buffers about two packets each way, rather than tungstenite's defaults, sized for throughput. A tunnel that ends stays among the node's tunnels, and one whose connection never arrived keeps its place among those being set up, until its close has gone out, which takes a bounded time: so tunnels a client ends and does not let close count too.
- **At shutdown** the endpoint over tunnels closes with the UDP endpoint, and the tunnels end after it, within a bounded time.

### Relayed streams

How a client reaches a node it cannot dial, such as a node behind a NAT ([core-and-periphery](../decisions/core-and-periphery.md), [the design](../designs/periphery.md#5-reaching-a-periphery-node)): through a relay, a node the destination keeps a QUIC connection to. Every QUIC endpoint relays for the nodes connected to it. Relayed traffic is light, Open Payments and owner apps, never peer traffic. `crates/dassie-node/src/quic/relay.rs` has the layouts and bounds.

- **The relay request** is sent to the relay by any QUIC client, which proves a key of its own as every client does: the destination's node ID, in the peer protocol's OER, and a purpose byte. The relay answers with one byte (`Outcome`): joined, unknown destination, busy or refused. Once joined, it copies bytes both ways until both sides end.
- **A relay never dials.** It reaches only a node it holds an open connection to, whoever opened it, and otherwise answers unknown destination. A relay that dialled could be made to connect anywhere.
- **The relayed stream** is what the relay opens to the destination on that connection, naming the purpose and the client's node ID. The destination answers with the same byte, whether it takes the purpose, and the relay passes the answer on. The relay passes the purpose on without reading it, so a new purpose needs only clients and destinations that know it.
- **TLS end to end.** Inside a joined stream the client runs TLS 1.3 with the destination, pinned to the destination's node key and presenting its own, with an ALPN for the purpose. The destination takes it only if the key proven is the client's the relay named. So the relay sees only ciphertext and its size, cannot pass one node's stream off as another's, and cannot put a client's name on a stream of its own.
- **Relay and client in one.** An endpoint may open a relayed stream itself, on a connection it holds to the destination, naming its own ID as the client (`Quic::open_held`), or on a connection it dials to the destination (`Quic::open_direct`); nothing on the wire differs. A [front door](http.md#front-doors) reaches nodes so, and refuses relay requests from others, with the refused outcome; an owner app reaches a node it can dial so.
- **Purposes.** `payments` (ALPN `dassie-pay/1`) carries HTTP/1.1 with Open Payments' routes only ([HTTP](http.md#relayed-streams)), answered under [the node's names](payments.md#the-nodes-names) and [signed](payments.md#signed-responses) as over HTTPS: this is how a [front door](http.md#front-doors) passes requests on. `owner` (`dassie-owner/1`) carries the RPC contract for a paired owner app, framed as on the IPC socket, with the client's key as the device key ([RPC](rpc.md#paired-devices)). The wallet and the owner's HTTP endpoints are never served through a relay.
- **Bounds.** A relay bounds the streams it carries per destination, per client address to each destination, per client address in all, and in all. A client address's share of a destination is smaller than the destination's, so that one client cannot take all of a destination's relayed streams; it is per destination because a front door reaches every node it serves from one address, and its share in all is larger, but smaller than the relay's. A destination bounds the streams it takes per relay address and in all, the share again smaller than the whole. A destination's share at a relay, and a relay's at a destination, is at most half of a connection's streams, so peer requests on the same connection always have room. A stream that carries nothing for a while, or outlives a bound, is reset, and each direction's copy holds a bounded buffer.
- **A chosen relay.** A node can keep a connection to a relay it chooses, which reaches it without any peering ([Node](node.md#a-chosen-relay)).
- **Uplinks relay for their downlinks.** A periphery node holds a connection to each of its uplinks ([Network](network.md#periphery-nodes)), and a relay reaches any node it holds a connection to, so every uplink is a relay for its downlinks, with nothing more to set up.

How a client learns which relays reach a node, the design's records and home nodes, is not built ([roadmap](../roadmap.md#periphery)).

### The hub's stream

How validators and members of a [settlement hub](hubs.md#the-validator-in-the-node) exchange the hub's messages ([settlement-hubs](../decisions/settlement-hubs.md): they prove themselves, so they need no peer protocol envelope, and a member need not be known to the validators). `crates/dassie-node/src/hub/transport.rs` has the bytes and bounds.

- **One exchange per stream:** the request is the hub's ID and one hub message, then the stream's end; the reply is a status byte (taken, no such hub, busy, malformed) and, when taken, the messages the validator sent back while it handled the request, each with its length ahead of it. Nothing else travels: a validator reaches a member only in the reply to its request.
- **Who sent it** is the node whose key the connection proved, and the validator answers that node's requests as one asker's, whoever it is; a validator of the hub has a queue of its own, which members cannot fill, and only a validator is served catch-up. The dialler pins the validator's node key from its acceptance, at the endpoint the hub's state names, as for a peer request.
- **Over QUIC alone,** for validators and members alike ([quic-only](../decisions/quic-only.md)), and a dial that fails backs off nothing for the peer protocol: a validator that is back is reached at once, its peers back off from it by themselves, and a member's account asks again on its own interval.
- **Bounded before it is read:** a request names its hub first; over QUIC the node reads those 32 bytes, resets the stream unless it validates that hub, then takes a place among the hub requests waiting node-wide (members' and validators' apart, and of the members' at most a share per key, so a key anyone can make never holds them all), and only then reads the message: up to the largest message from a validator of the hub, and up to a member's largest request, a submitted claim with the most commitments any rules allow, from anyone else. No place, and the request is answered busy, nothing read. A reply carries a bounded number of messages and bytes, the rest left for the next request; a validator's queue is bounded, and a request past it is answered busy, nothing taken.
- **The state stream,** a stream kind of its own, carries a validator's request for the state after one of the hub's final blocks, by height, and the state back with a status: found, no such hub, not kept, refused, or busy: a node serves at most a couple of states at once (`MAX_STATE_SERVES`), each read off the async runtime and holding its place until written. It serves only the hub's validators, by the key the connection proved, over QUIC alone, and has a bound of its own, the largest state the node stores, since a state can be far larger than a message. The asker checks the state against the block's root before it takes it.
- **The founding stream,** a stream kind of its own, carries a sponsor's request while it founds a hub, and the validator's answer, each `dassie_hub::founding`'s in canonical OER, up to a bound of their own: the terms to accept, the rules whose genesis to sign, the genesis certificate to run, and whether a quorum checked the escrow ([Settlement hubs](hubs.md#founding-a-hub), [hub-founding](../decisions/hub-founding.md)). There is no hub ID yet, so it names none. Over QUIC alone, pinned to the validator's node key; the validator takes the key the connection proved as the asker. **Nothing is read before the asker is known:** a stream from a node the validator file does not list, or to a node without one, is reset after its kind byte, as one of an unknown kind; a listed sponsor's takes one of a few places node-wide first, which bound the requests read and decided at once, and is answered busy, unread, when none is free. The validator then answers only the sponsor the terms name.
- **A member's `Payout` request** on the hub's stream asks for the payout set the validator signed, from a place in it on, and is answered with a page of it, or nothing while the hub runs ([Settlement hubs](hubs.md#payout-bundles)).

### Statuses

The status is part of the protocol, and senders depend on one property of it: **400, 401, 409 and 503 mean the message was not acted upon.** Only these, or a request that surely never left, let a sender treat a message as undelivered: the connector rejects a Prepare at once with T01 on them, and leaves every other failure to expiry ([Connector](connector.md#responses-and-expiry)). A peering refusal is therefore a 200 with `refused`, since the responder did act on the request. The statuses and their causes are in `crates/dassie-peer/src/node/inbound.rs`.

## Encoding

Messages are canonical OER as [Encoding](encoding.md) describes it, read strictly: an unknown CHOICE tag, a value that does not fill its container, or trailing bytes are malformed. The layouts are in `crates/dassie-peer/src/wire/`.

A 200 response body has no tag of its own: its type follows from the request's kind.

## Authentication

### Which messages need authentication

- Every message that changes state, or moves money, must be authenticated: peering, packets, settlements, scheme messages, registration, termination, settlement requests, and committing to, unsealing and renewing a name. Without it they get 401.
- Read-only gossip (link states, node lists, name lists, peering info) may be sent without it, so tools can query a node. A v1 node still authenticates every request it sends, since it only sends to nodes whose key it knows.
- A response is authenticated if and only if its request was. A sender refuses a response to an authenticated request that has no MAC or a wrong one, as if the request had failed. Authenticated responses are what make node lists, peering answers and registrations authentic end to end, not only by TLS.
- An authenticated message from a peer, or an authenticated response to one of our requests, marks the peer as heard from ([Network](network.md#advertised-peers)).

### Keys and MACs

Keys come from a static-static X25519 between the two nodes' Ed25519 keys, converted as [Identity](identity.md) describes, and HKDF-SHA256. The derivation is in `crates/dassie-peer/src/auth/keys.rs` and pinned by a MAC vector in `crates/dassie-peer/tests/auth.rs`. Its properties:

- **The sender's key travels in the envelope** and must hash to the claimed node ID, be a valid point and not of small order ([Identity](identity.md)). So a node can check a sender it does not know yet, such as a registrant. An all-zero shared secret is refused.
- **Direction binding.** Request and response keys are expanded under different labels, with the sender's and recipient's public keys in that order. A request MAC is valid from S to R only, so a message cannot be reflected back to its sender, and a response is keyed by the request's pair in the same order.
- **What a MAC covers.** A request MAC covers the version, sender, recipient, session, counter, timestamp and the content's exact bytes. A response MAC covers the request's MAC and the body, so a response is bound to its request.
- **No ephemeral key.** For a scheme that only MACs, an ephemeral adds neither forward secrecy nor protection against key-compromise impersonation, and it would let anyone force an X25519 operation per request ([peer-protocol-v1](../decisions/peer-protocol-v1.md)).
- Derived keys are cached per node, bounded; a key of a node that sent us a request is cached only after its MAC verified, so forged traffic cannot evict the keys of real peers.

### Replay protection

A sender keeps one session per destination, with a random ID and a counter, and starts a new one periodically. A recipient accepts an authenticated message only if its timestamp is within a window around its clock, above the sender's floor, and its `(sessionId, counter)` pair is new (a sliding window per session). The guarantees:

- **Checking changes nothing.** Replay state is recorded only once the MAC has verified, so forged messages cannot advance or poison it.
- **Evicting a session opens nothing.** The recipient keeps a few sessions per sender; a new one displaces the session used longest ago, and the sender's floor rises to that session's newest timestamp.
- **Across restarts, a message is accepted at most once.** For every sender whose replay state is kept for good (below), the newest accepted timestamp is persisted in the same transaction as the message's effects. After a restart, such a sender's floor is the later of that timestamp and the start time: the start time alone would let a message from a sender whose clock runs ahead through again. Every other sender's floor is the start time. That keeps the promise, since a stranger's request with effects makes it a sender kept for good in the same transaction (a registration, a peering, a commitment to a name), and a link state from a stranger is signed data that anyone may relay. A request that only reads moves no persisted floor, since a replayed read is harmless; a peer's read does, since its replay would mark the peer as heard from. A floor is kept until it is stale, even when its sender stops mattering, and goes once nothing it protects can arrive: when the sender is forgotten, or, if it sent again in between and took a place in the pool, when that place goes. Raising every sender's floor after a restart by the timestamp window instead would refuse every registration, settlement and Fulfill from a node that is not a peer for that long, and would still let a replay through after a restart that set the clock back. A peering that ends keeps its sender's floor while its channel is open, since the channel keeps the sender ([Network](network.md#settlement-channels)); once it closes, the floor goes as any let go, and the sequence that stays on disk still tells a late settlement from a copy. A message lost in a crash, whose effects were never committed, can be accepted once more, but never twice.
- **Floods of identities cannot crowd out the nodes that matter.** Peers, bootstrap nodes, nodes we hold a settlement channel with ([Network](network.md#settlement-channels)), nodes registered with us ([Network](network.md#registration)) and, at a registrar, nodes with a commitment in its log or a name held there ([Network](network.md#names)) keep their replay state for good, so a registered node's renewal gets through however long it was quiet. A node that stops mattering, such as one whose registration lapsed, keeps its state outside the pool until every message accepted from it is stale, and is then forgotten. Every other sender, a stranger, shares a bounded pool; a newcomer may take only the place of a sender whose newest message is already outside the timestamp window, so forgetting it opens nothing. If there is none, the newcomer gets 503.
- **One network holds only its share of the pool.** Strangers from one /24 (IPv4) or /48 (IPv6) of source addresses, grouped as for the registration cap ([Network](network.md#registration)), hold a bounded number of places; once a network has its share, a newcomer from it may take only the place of an idle sender from the same network. An IPv4 client seen by a dual-stack listener counts in its IPv4 network. Loopback is no network where private peers are allowed, as for the limits per client ([HTTP](http.md)), since dev and the tests run many nodes there. The bounds are `AuthConfig`'s (`crates/dassie-peer/src/auth/mod.rs`).
- **A request that only reads leaves nothing in the pool.** Requests for link states, node lists, name lists and peering info (`Kind::is_read_only`) change nothing at the recipient, and their answers are public, signed data or the recipient's own, which anyone may ask for unauthenticated. From a stranger, such a request is checked against the timestamp window and the sender's state, if it has any, and is not recorded, nor is its key cached: a replay gets the replayer only what asking would. Otherwise new identities could fill the pool, or keep a place fresh, with requests that are answered 200, which the transport does not charge ([Transport](#transport)). From a node whose state is kept, it is recorded like any other, so a replay cannot mark a peer as heard from.

## Link states

A node's link state ("node info") is its signed description of itself: its URL, alias, key, the peers it advertises and the schemes it settles with. How it is issued, spread and refreshed is in [Network](network.md#link-states). The signature is pure Ed25519 over the signed bytes as received.

- **Only a core node lists neighbors.** A periphery node's link state lists none, however many uplinks it keeps ([periphery-lists-no-neighbors](../decisions/periphery-lists-no-neighbors.md)). Nothing in the protocol changes: a node that reads one listing its uplinks, from an older periphery node, routes no differently.
- **Every node decodes the same bounds:** at most `MAX_ENTRIES` entries and `MAX_NODE_INFO_BYTES` of signed bytes (`crates/dassie-peer/src/wire/mod.rs`). A state past them is refused by all, so they are protocol, and a node checks its own against them before it signs it ([Network](network.md#the-own-link-state)).

- **Extensions** of unknown type are kept, since the signature covers them, and otherwise ignored. That is how later versions add fields. Type 2, with an empty value, says the node takes QUIC ([Transport](#quic)); type 3, with an empty value, says it is a periphery node, which has no URL ([Network](network.md#periphery-nodes)); type 4, a `UInt16` that is not 0, is the UDP port of the node's [rate feed](rate-feed.md#finding-a-feed) at its URL's host, which only a node with a URL names; type 5 names the [settlement hub](../designs/settlement-hubs.md#11-choosing-a-hub) the node is a member of, its account there and whether it takes new peers over it, as `HubMembership` in canonical OER (`crates/dassie-peer/src/wire/node_info.rs`); type 1 is kept for a post-quantum key ([Versions](#versions)). A node that reads an extension of a known type that breaks its rule, a feed port of another length, say, takes it as absent and still keeps and forwards the link state, as it would one of an unknown type; so adding a type never needs a new protocol version.
- The alias is an unverified display name.

### Verification

A link state verifies when its URL has the node-URL syntax, or, in a periphery node's link state, is empty, its key is a valid Ed25519 point not of small order, its node ID is that key's, and its signature verifies. All nodes must agree on which states verify, or the network splits on them:

- **Signatures follow ZIP-215** (`ed25519-zebra`), as the original's verifier did. Being stricter could split the network on edge-case signatures. Small-order keys are refused because under ZIP-215 one signature verifies every message under such a key.
- **URL syntax is part of verification** for the same reason: an HTTPS origin with a lowercase hostname or IP literal and an optional port, nothing else (`crates/dassie-peer/src/wire/url.rs`). A node whose own URL does not fit publishes no link state.
- **An empty URL** verifies only with the periphery extension, and the extension only with an empty URL: a periphery link state with a URL would be taken for a downlink's, accepted without a probe and dialled at a URL nobody checked. A node that does not know the rule refuses such a state, which is harmless only because a periphery node's link state never floods: only its uplinks see it, in its peering requests and heartbeats, and only nodes that take downlinks need the rule.

## Message set

What a node trusts, and the rules a sender and a recipient rely on, by message. The handlers are in `crates/dassie-peer/src/node/inbound.rs`; "peered" means a peering that is `peered` or `terminating`, "active" means `peered` ([Network](network.md#lifecycle)).

- **Link states** (`linkStateUpdate`, `linkStateRequest`) are trusted by their signature, from anyone. A requester takes only the states of nodes it asked about, so a responder cannot stuff its table. An answer carries stored states as received, without verifying them again; the requester verifies.
- **Embedded node info** in `peeringRequest` and `registration` must verify and name the sender, and may not be far ahead of the recipient's clock.
- **Node lists** are trusted only from a configured bootstrap node, by the response's MAC under its configured key ([Network](network.md#membership)). A list's hash is computed over the bytes received.
- **`peeringRequest`** carries the scheme versions the sender speaks; an acceptance names the highest common one, and a requester refuses one it does not speak. The responder probes the requester's URL, unless the requester is a periphery node, which has none, and records the peering before it answers ([Network](network.md#peering)).
- **`registration`** of a periphery node's link state is refused: a periphery node is in no node list.
- **`linkStateRequest`** is never answered with another node's periphery link state.
- **`interledgerPacket`.** A Prepare and its Fulfill or Reject are separate one-way messages, correlated by a request ID per peer. A Prepare needs an active peering, so no new packet enters a peering being ended. A Fulfill or Reject is sent again, for a bounded time, until a 200 arrives, or a 400 or 409, which says it will never be taken; a copy that arrives twice is dropped by the peer's connector. A 401 keeps it too: a node that just started refuses messages dated before its start, and the copy sent again is dated anew. Otherwise each Fulfill for a Prepare a node sent as it started, from a peer whose clock is behind, would be lost though booked, and every restart would drift the two books apart. Each copy refused is charged to the sender's address at the recipient's rate limit ([Transport](#transport)), so a restart can leave a busy link refused with 429 for about a refill, its Prepares left to expiry: a short spell, against books that drift for good. A Reject that never arrives has the effect of expiry; a Fulfill stays booked whether it arrives or not ([own-fulfills](../decisions/own-fulfills.md)). Once one of our packets to a peer surely did not arrive, the node takes no new Prepare from it until it answers a request of ours, since our Fulfill could not arrive either; the heartbeat and the Rejects sent again find out when it does ([unreachable-peers](../decisions/unreachable-peers.md)). The packet itself is the connector's ([Connector](connector.md)).
- **`hubPacket`** carries a Prepare and the payer's commitment in one message, on a peering over a settlement hub ([the design](../designs/settlement-hubs.md#4-peering-over-a-hub)), so the payee never sees a Prepare without its commitment. A peering's scheme says whether it is over a hub (`PeeringHooks::uses_commitments`). On such a peering a Prepare comes only in a `hubPacket`, and on any other only in an `interledgerPacket`: either one where the other belongs is refused with 409, as a Prepare from a node not peered is, so the sender rejects it at once. Only a Prepare travels in a `hubPacket` (otherwise 400); its Fulfill or Reject goes back in an `interledgerPacket`, under the rules above.
- **The reply to a Fulfill** on a peering over a hub carries the payer's claim after the verdict ([own-fulfills](../decisions/own-fulfills.md) still holds: the verdict is always "accepted"). The node that sent the Fulfill hands the bytes after the verdict to the scheme, and takes a reply of the verdict alone, as every other peering's is, as a Fulfill that arrived. The commitment and the claim are opaque to the peer protocol and bounded by it; the hub's scheme reads them.
- **`settlement`** is accepted from any node we hold a settlement channel with, peered or not, open or closed, so a settlement that arrives after the peering ended, or after the channel closed, is still credited. Its sequence belongs to the pair of nodes, not to a peering, and never resets: a closed channel keeps it on disk ([closing-channels](../decisions/closing-channels.md)). The sender sends one at a time, in order, again until a 200 arrives, across restarts, with a backoff. One whose last try got no answer also goes at once when the node next answers any request of ours, since it is reachable again, rather than waiting out the backoff. That early try is made once per silence, so a node that never answers it gets it at most twice as often as the backoff alone would send it; a 401 keeps it (a node that just started refuses messages dated before its start, and the early copy is dated anew), and any other answer gives it up, since a refusal or a busy node is not helped by going early. The recipient answers a sequence it already applied with 200 and does nothing; it applies only the next one, and only if its books can take it, checked before the scheme sees it (otherwise 400 and nothing changes). So each settlement is credited exactly once ([Settlement](settlement.md#settlement-channels)).
- **`settlementMessage`** is a scheme's own message to its counterpart, sent once; schemes do not depend on it arriving.
- **`settlementRequest`** asks an active peer to settle on a scheme, leaving the amount to it ([Settlement](settlement.md#asking-a-peer-to-settle)). Its answer is what the peer then has on its way to the asker, in the scheme ledger's units, as eight bytes ([Settlement](settlement.md#settling-on-request)). A node ending the peering, and not yet saying so, answers 0 ([Network](network.md#termination)).
- **`peeringTermination`** is sent until a 200 or a 409 arrives, or the termination times out. A 409 means the recipient holds no peering with us, so there is nothing left to end ([Network](network.md#termination)).

### Names

The messages that register and hold a name ([the design](../designs/names.md), [names-by-earliest-commitment](../decisions/names-by-earliest-commitment.md)). A registrar, a node that is one of its own bootstrap nodes, takes them and decides by its own log ([Network](network.md#names)); any other node answers each with 409, the list requests too, so a registrant takes nothing as done. The layouts are in `crates/dassie-peer/src/wire/`, and what a name and a commitment are in `crates/dassie-peer/src/names/`.

- **A name** is a DNS label, so that a front door can serve it as `<name>.<domain>`: lowercase letters, digits and hyphens, not starting or ending with one, and without hyphens in its third and fourth places, which DNS keeps for encodings such as `xn--` (no internationalized names at first). It is shorter than a [node label](identity.md#node-label), so no name is ever read as a label, nor a label as a name. Only lowercase, so that a name has one spelling, and so one commitment and one holder. Messages and lists read any name of that syntax; the names no owner may register are a list in the code (`RESERVED`) that only a registrar consults, so changing it changes no encoding.
- **The commitment** is SHA-256 over the canonical OER of a domain OID of its own ([Identity](identity.md#object-identifiers)), the name, the holder's node ID and a 32-byte salt, each field of fixed length or with its length ahead of it, so no two inputs hash the same bytes (`commitment.rs` has the layout, and `crates/dassie-peer/tests/wire.rs` a golden value). The holder inside it makes a copied commitment useless to anyone else, and the salt keeps a dictionary of likely names from opening it.
- **`nameCommit`** carries only the commitment, so it shows the registrar nothing of the name; it is authenticated by its sender, against whose caps it counts. Any node may send it: the holder is sealed inside the commitment, so only the holder can unseal it, and a registrant sends its own. Its answer is the receipt: the commitment's position in the registrar's log and when its window closes, by the registrar's clock. It is sent only once the commitment is on disk, and a commitment in the log already gets its receipt again. A registrar refuses one with 503 when its log or its names are full, 409 for a cap on the sender or its network, and 429 for its rate.
- **`nameUnseal`** carries the name and the salt; the holder is the sender, so a node can open only its own commitments. A valid unsealing is answered with an empty 200, whether it still contends for the name or has lost already, so the answer tells nothing of commitments still sealed, and again for a retry while its commitment is in the log; an invalid one, or one past the holder's cap on names, gets 409 ([The registrar](network.md#the-registrar)). **`nameRenew`** carries the name, and is answered with its expiry, as a registration is: a new one once its expiry is near, the one it has before; another node's renewal, or one of a name not held, gets 409. Both are authenticated.
- **`nameListHashRequest`** and **`nameListRequest`** read a registrar's name list as their counterparts read its node list, and only read: the names listed, with their holders and expiries. Every node polls them with the node lists, and takes a name's holder from a quorum of the lists ([Network](network.md#holders)). A list is sorted by name with each name once, or it is malformed, so a list has one encoding and one hash; it is bounded by `MAX_NAME_LIST`, which the transport's bound on a response holds (`crates/dassie-node/src/quic/mod.rs`).

## Outbound requests

The node's outbound requests (peer requests, and over HTTPS Open Payments to other wallets and exchange-rate sources: [Payments](payments.md), [Connector](connector.md#sources)) go through one client in `crates/dassie-node/src/peer_client.rs`, with one set of rules; QUIC connections resolve their addresses through it, so the same guard applies to them. A peer or a registrant chooses the URL we connect to, so:

- Requests go only to `https` URLs, and redirects are never followed. A QUIC connection goes to the host and port of such a URL.
- Private, loopback, link-local and similar addresses are refused, both as IP literals and after DNS resolution (`crates/dassie-node-core/src/address.rs`). An IPv6 literal is read as the HTTP client reads it, and one the guard cannot read counts as private, so the guard and the client cannot disagree. `DASSIE_PEER_ALLOW_PRIVATE` lifts this for dev and tests.
- In-flight requests are bounded, in total and per host, peer requests and the rest alike. ILP packets do not count, so their responses always get through.
- **Failures** are of two kinds: *not delivered* (refused before sending, or the connection failed) and *unknown* (a timeout after sending, or a broken response). Only the first, or a status that means not acted upon ([Statuses](#statuses)), says a request surely had no effect.

## Decisions

- [peer-protocol-v1](../decisions/peer-protocol-v1.md): v1 instead of v0; static-static X25519 MACs without an ephemeral key, direction binding, the sender key in the envelope, replay protection across restarts, authenticated responses, the reserved post-quantum tag.
- [membership-economics](../decisions/membership-economics.md): authenticated node lists and the limits on free registration.
- [peering-lifecycle](../decisions/peering-lifecycle.md): `peeringTermination`.
- [own-fulfills](../decisions/own-fulfills.md): `settlementRequest`, `credit` sent as 0, the Fulfill reply always "accepted".
- [places-by-proved-key](../decisions/places-by-proved-key.md): QUIC connections hold places by the key they proved: core peers, downlinks and anyone else apart.
- [quic-over-websocket](../decisions/quic-over-websocket.md): QUIC's packets over a WebSocket where UDP is blocked, rather than a second stream transport; served by every node, dialled only by nodes without a URL, racing UDP.
- [unreachable-peers](../decisions/unreachable-peers.md): no Prepare taken from a peer our packets surely do not reach.
- [settlement-hubs](../decisions/settlement-hubs.md): `hubPacket`, the claim after the verdict and the hub extension, for peerings over a hub.
- [names-by-earliest-commitment](../decisions/names-by-earliest-commitment.md): the name messages, a commitment sealed by its holder and salt.
