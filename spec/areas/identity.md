# Identity

Everything a node is derives from one recovery phrase: its Ed25519 node key, its SLH-DSA key and its node ID, its login secret, and the entropy its settlement schemes build wallets from. The owner keeps only the phrase, so the same phrase must always recover the same node and the same funds.

**Paths:** `crates/dassie-identity/`, `packages/wasm/`
**Read with:** [Encoding](encoding.md), [Peer protocol](peer-protocol.md), [HTTP](http.md), [XRPL](xrpl.md), [Node](node.md)

## Derivation chain

**The phrase** is 20 words of the BIP-39 English list that hold a kind, which names its layout and realm, the hour it was made, a 128-bit secret and six Reed–Solomon check words ([phrase-format](../decisions/phrase-format.md); `src/phrase.rs`, `src/reed_solomon.rs`). Reading it is the only way in: words by their first four letters in either case, only ASCII letters changing case, so a letter that only Unicode lowers to one, such as the Kelvin sign, matches no word; a word not on the list or marked unreadable as an erasure, 20 words only, a BIP-39 phrase refused as one. The code restores up to two wrong words, with unreadable ones while `2 × wrong + unreadable` is at most five, so one check word is always left to catch a mistake; past that the phrase is refused as too damaged. The kind, the realm the reader expects and the creation time are checked before a correction is returned: a phrase that says it was made more than a day after the reader's clock is refused, and the refusal names its date, since a phrase cannot be made in the future. The reader's clock is its caller's, as milliseconds since the Unix epoch, as the time a phrase is made is; the crate reads none. A correction gives up its phrase only once the caller confirms it: a reader with no one to confirm (`dassie setup`, the market maker) refuses it, naming the positions of the words, never the words, and reads only once its host's clock is synced, since no one is there to set it.

**The master seed** is HKDF-SHA256 of the secret, with `dassie phrase` as salt and the realm, `test` or `live`, as info. The derivation takes the realm its caller expects and refuses a phrase of the other, so one secret is a different node in each realm and no caller derives across realms by mistake. The kind does not enter, so a later layout, under a kind of its own, can carry the same secret to the same node; the creation time does not enter either.

From the master seed, every secret is a node of an HMAC-SHA256 tree of seed paths hanging off it (`src/seed.rs`; the chain is drawn in `src/lib.rs`). The node key is the path `node`; everything the node derives hangs below it, so a node holding only its node key derives the same `node/…` secrets the browser derives from the phrase.

The phrase's layout, the chain to the node key, its public key, its SLH-DSA key and node ID, and every frozen path below it, are a compatibility surface. No step, no algorithm parameter and no frozen path may change, or the same phrase would give a different node: a different node ID to its peers, a different XRPL account with the owner's funds in the old one, hub keys its rules no longer name. Only the phrase's kind leaves room for change: a new layout is a new kind, whose secret derives as before.

What pins it: **golden vectors** (`tests/data/phrase.json`, `chain.json`, `keys.json` and `paths.json`) from a generator of our own (`testdata/identity/`), which computes them with libraries independent of Dassie's code and its own Reed–Solomon code, written from the phrase format's decision alone; its SLH-DSA implementation is another than the node's, and must give NIST's known-answer vectors first. They pin phrases of both realms, their data and check words, how a reader reads phrases with wrong and unreadable words, of other lengths, kinds and realms, and made after its clock, and, from phrases of both realms, the master seed, node key, public key, SLH-DSA public key, node ID, login secret, the XRP Ledger accounts' entropy and wallets, and every path below the node key with its secret, with what a hub's rules and escrow name of a hub's keys. They run natively (`tests/vectors.rs`, and a hub's keys in `crates/dassie-hub/tests/keys.rs`) and through the WASM build (`tests/interop/identity_wasm_test.ts`), so the browser derives exactly what the node derives. NIST's known-answer vectors for the SLH-DSA key generation (`tests/data/slh_dsa_keygen.json`, run by `tests/slh_dsa.rs`) pin the library the node uses.

## Seed paths

Every secret below the node key is a variant of `NodeSecret` (`src/paths.rs`): it takes typed arguments and writes its path itself, and no other crate writes one, so no two uses meet at a path. A new secret is a new variant at a new path, never a new meaning for an existing one. `NodeSecret::is_frozen` says which paths may never change: those whose secret something outside the release depends on. They are the XRP Ledger accounts' keys and a hub's keys, which hold funds and which a hub's rules name; the seeds of the SLH-DSA key, which the node ID commits to ([Node ID](#node-id)); the Open Payments key, which other wallets know the node by; and the STREAM receivers' secrets, whose credentials other wallets hold. Not frozen: the login secret, since the wallet and `dassie setup`, which derive the proof, ship in the release of the node that checks it ([HTTP](http.md#login-and-logout)); and the QUIC endpoints' keys for stateless resets and connection IDs, each endpoint its own, since a changed one only makes peers wait out the idle timeout once, for connections a crash left behind ([Peer protocol](peer-protocol.md#quic)); and the route key, since a changed one only keeps other first hops ([Network](network.md#routing)).

- **A STREAM receiver's secret** names its ledger by the ledger's ID, the name its books have, not by the slug its addresses show, so the secret follows the books rather than a display name ([STREAM](stream.md#credentials-and-tokens)).
- **The SLH-DSA key's three seeds,** `SK.seed`, `SK.prf` and `PK.seed`, are the first 16 bytes of the secrets at `node/slh-dsa-sha2-128s/sk-seed`, `…/sk-prf` and `…/pk-seed`, which name the parameter set, so that no seed ever serves two ([post-quantum-node-id](../decisions/post-quantum-node-id.md)).
- **A hub's keys** name the hub's network and nonce, `node/hub/<network ID>/nonce/<nonce>/<key>`, since a transaction on the testnet or mainnet names no network; a member's key names the hub ID, `node/hub/member/<hub ID>/account`, which names the network already ([hub-keys-by-network](../decisions/hub-keys-by-network.md)).

Nothing but the node key hangs off the master seed directly, and the node never has the master seed: only the browser holds the phrase and the master seed, during setup and login ([HTTP](http.md)), or, for an owner who keeps the phrase on the node's host, `dassie setup` and the market maker, which wipe them once they have the node key ([headless-setup](../decisions/headless-setup.md)).

Users of the tree: the login secret ([HTTP](http.md)), the node's XRP Ledger accounts at `node/xrpl/<network ID>/account/<index>`, which every scheme on an account settles through ([XRPL](xrpl.md#the-wallet)), the STREAM receivers ([Payments](payments.md#receiving)), the Open Payments key ([Payments](payments.md#wallet-addresses)), the QUIC endpoints' keys ([Peer protocol](peer-protocol.md#quic)), the route key that ranks first hops for routing's cut ([Network](network.md#routing)), and a settlement hub's keys: a validator's consensus, escrow and payout keys, a sponsor's escrow master key, and a member's account key ([Settlement hubs](hubs.md#the-escrow)).

## Node key

Signing is pure Ed25519. **Verification follows ZIP-215** (`ed25519-zebra`), not `ed25519-dalek`'s cofactorless `verify`: ZIP-215's rules are exact, so every implementation agrees on every signature, edge cases included, and being stricter than the original could split the network on edge-case signatures.

The price is **small-order keys**: under ZIP-215 a signature with `s = 0` and a small-order `R` verifies every message under a small-order public key. So every place where a key must prove something refuses weak keys (`PublicKey::is_weak`): link states and the senders of authenticated peer messages ([Peer protocol](peer-protocol.md)), rate feeds ([Rate feed](rate-feed.md#signing)), Open Payments client keys ([Payments](payments.md)) and the release key ([Release](release.md)). Keys derived from a seed are never weak.

Ed25519 signs everything a node signs. Beside it, every node has an **SLH-DSA key** (FIPS 205, SLH-DSA-SHA2-128s, `src/slh_dsa.rs`), generated by the standard's `slh_keygen_internal` from seeds below the node key ([Seed paths](#seed-paths)), which signs nothing yet: the node ID commits to it, so that once Ed25519 can be trusted no longer, a node can prove with it that it is the node of its ID ([post-quantum-node-id](../decisions/post-quantum-node-id.md)). Generating it costs about a thousand Ed25519 keys, so a node computes it once, when it gets its key, and keeps it with the key (`IdentityKey`); `NodeKey` has no node ID of its own, so that no caller pays for a key generation each time it asks.

## Node ID

The node ID is the short, self-certifying name of a node (`src/node_id.rs`): the first 24 bytes of a SHA-256 of its two public keys, the Ed25519 key and the SLH-DSA key, under a versioned OID. The two keys are the node's identity (`NodeIdentity`), and only the two together name a node.

- **Its text** is those bytes in lowercase base32 (RFC 4648, no padding): 39 characters of `[a-z2-7]`, one form wherever a person or a protocol reads it. It is the node's segment in ILP addresses, its DNS label at a front door, `<node ID>.<domain>` ([Payments](payments.md#the-nodes-names)), what logs and the wallet show, and what configuration names. Text is read in either case, since DNS ignores case, and its three unused last bits must be zero, so that each ID has one text. Base32 rather than base64url so that one form serves DNS too; 24 bytes so that it fits a DNS label, 63 characters, with room to spare.
- **On the wire** it is its 24 bytes, through the one encoding `NodeId` gives (`Encode` and `Decode`), which every wire format uses: fixed in length, so no format carries an ID's length or bounds it, and every 24 bytes are an ID.

The ID is frozen with the [derivation chain](#derivation-chain): DNS names, clients' records and the bootstrap node lists are built from it, and a client checks the key a node signs with against the ID its host names ([Payments](payments.md#signed-responses)).

An ID received from elsewhere is only a name until checked: it must equal the ID computed from the two keys it comes with, and a link state, peering request or authenticated message whose ID and keys disagree is refused ([Peer protocol](peer-protocol.md)). So wherever an ID is checked against a key, the SLH-DSA key travels beside the Ed25519 key: in link states and the QUIC certificate ([Peer protocol](peer-protocol.md#quic)), a hub's rules ([Settlement hubs](hubs.md#the-rules)), signed responses' `keyid` ([Payments](payments.md#signed-responses)), configured bootstrap nodes and relays, and the discovery document. A checker that holds a node's identity already, as a feed's subscriber does, compares the Ed25519 key a message is signed with to the identity's ([Rate feed](rate-feed.md#signing)).

## Object identifiers

Dassie's OIDs sit under the private arc `1.3.6.1.4.1.54392.5.1399`: `.1` for the peer protocol, `.2` for node fingerprints, `.3` for the [rate feed](rate-feed.md#signing). Under `.1`, `.1.6` signs link states, `.1.5` signed them in the layout with the Ed25519 key alone, `.1.3` in the layout that sent the node ID beside the key, `.1.4` is the domain of a name's commitment ([Peer protocol](peer-protocol.md#names)), and `.1.7` the QUIC certificate's extension that carries the SLH-DSA key ([Peer protocol](peer-protocol.md#quic)). Under `.2`, `.2.2` is hashed into node IDs over both keys, and `.2.1` hashed the Ed25519 key alone. They are hashed into node IDs and signed into link states and feeds, so an arc is never reassigned, including `.1.1`, which the original defined and nothing uses. A new version of a signed structure takes a new OID, so a signature over the old one cannot pass as the new ([Peer protocol](peer-protocol.md)).

## Handling of secrets

Secrets (master seed, node key, derived secrets) are wiped on drop, are not `Copy`, print redacted and compare in constant time. Errors never carry a secret, so they may be logged and shown. A mistyped phrase is corrected only with the owner's confirmation or refused, never silently a different node. The node stores its key as the raw seed ([Node](node.md), [secrets-at-rest](../decisions/secrets-at-rest.md)).

## In the browser and in scripts

`dassie-identity` and `dassie-stream` (with `dassie-ilp`'s codecs) are built to WASM (`node --run build:wasm`) and published as `@dassie/wasm`, so the wallet derives keys with exactly the code the node runs. Their bindings are one crate of their own, `dassie-wasm`, so the core crates carry no wasm-bindgen and never touch the platform's randomness: that edge is the bindings'. Each of its features is a module of its own, `dassie_identity` and `dassie_stream`, so the wallet loads identity without STREAM. One `web` build serves browsers and Node ([node-and-pnpm](../decisions/node-and-pnpm.md)): `.` for scripts and tests, `./web` for browsers. Development-only functions (`sign`, `phraseFromSecret`, and `deriveNodeKey`, which refuses any correction) are left out of `./web`.

The bindings keep the reading's rules: the caller passes the realm it expects and its clock, a reading shows a correction's words and the positions that changed and gives up its phrase only through `confirm()`, and a phrase derives its node key only in the realm its caller names. A refusal is thrown as an `Error` with a `code` and what it names, a count, a kind, a realm, a date or positions, never a word, so a page words each one. Making a phrase takes the realm and the clock too, and, at setup, the node's clock: no phrase is made while the two are more than a day apart. `phraseWords` says what each word of a text reads as, split and matched as a reading splits and matches them, so a page can show it while the owner types. A node ID takes both public keys, `nodeId(publicKey, slhDsaPublicKey)`, and `slhDsaPublicKey` generates the key, which takes a while in WASM, so a page computes it once.

## Decisions

- [peer-protocol-v1](../decisions/peer-protocol-v1.md): a peer is the node key its QUIC connection proved.
- [database-continuity](../decisions/database-continuity.md): a v0 database is not migrated, since nobody ran the original.
- [secrets-at-rest](../decisions/secrets-at-rest.md): the node key stays plaintext at rest.
- [tigerstyle](../decisions/tigerstyle.md): deterministic, bounded, no OS randomness in the core.
- [node-and-pnpm](../decisions/node-and-pnpm.md): one `web` build of the WASM modules for browsers and Node.
- [hub-keys-by-network](../decisions/hub-keys-by-network.md): a hub's keys name its network.
- [phrase-format](../decisions/phrase-format.md): a phrase of 20 words that says its realm and when it was made, corrects its own errors, and keys the master seed by its realm, in place of BIP-39.
- [post-quantum-node-id](../decisions/post-quantum-node-id.md): the node ID commits to an SLH-DSA key beside the Ed25519 key, so that a node can prove it is itself once Ed25519 falls.
