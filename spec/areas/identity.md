# Identity

Everything a node is derives from one BIP-39 recovery phrase: its Ed25519 node key and node ID, its login secret, its X25519 key for peer authentication, and the entropy its settlement schemes build wallets from. The owner keeps only the phrase, so the same phrase must always recover the same node and the same funds.

**Paths:** `crates/dassie-identity/`, `packages/identity-wasm/`
**Read with:** [Encoding](encoding.md), [Peer protocol](peer-protocol.md), [HTTP](http.md), [XRPL](xrpl.md), [Node](node.md)

## Derivation chain

The phrase gives a master seed, and every secret is a node of an HMAC-SHA256 tree of seed paths hanging off it (`src/seed.rs`; the chain is drawn in `src/lib.rs`). The node key is the path `node`; everything the node derives hangs below it, so a node holding only its node key derives the same `node/…` secrets the browser derives from the phrase.

Every byte of this chain is a compatibility surface. No step, no algorithm parameter and no path in use may change, or the same phrase would give a different node: a different node ID to its peers, a different login, a different XRPL account with the owner's funds in the old one. There is no versioning to migrate through; a change is a new node.

What pins it:

- **Golden vectors from the original** (`tests/data/chain.json`, `tests/data/keys.json`, generated by `testdata/original/`) pin the phrase, master seed, node key, public key, node ID, login secret, development session token, settlement entropy and XRPL wallets, the X25519 conversion and a shared secret. They run natively (`tests/vectors.rs`) and through the WASM build (`tests/interop/identity_wasm_test.ts`), so the browser derives exactly what the node derives.
- **The paths the rewrite added** have no vector, only their constants, which must not change:
  - `node/stream-server/<ledger slug>` (`crates/dassie-node/src/engine/core/packets.rs`) keys the STREAM receivers; changing it voids every credential the node has handed out for incoming payments ([STREAM](stream.md#credentials-and-tokens));
  - `node/open-payments-client` (`crates/dassie-node/src/open_payments/keys.rs`) is the key the node signs Open Payments requests with; changing it changes the key other wallets know the node by ([Payments](payments.md#wallet-addresses));
  - `node/hub/<nonce>/{consensus,escrow,payout,escrow-master}` (`crates/dassie-hub/src/escrow/keys.rs`) are a validator's keys for a settlement hub and the sponsor's escrow master key; changing them changes the keys a hub's rules name, and where a sponsor makes its escrow again after a reset ([Settlement hubs](hubs.md#the-escrow)). A test pins one public key of each.

A new secret takes a new path below `node`, never a new meaning for an existing one.

## Seed paths

A path is resolved from the node key only if it is `node` or starts with `node/`. Any other path hangs off the master seed, which the node never has: only the browser holds the phrase and the master seed, during setup and login ([HTTP](http.md)), or, for an owner who keeps the phrase on the node's host, `dassie setup` and the market maker, which wipe them once they have the node key ([headless-setup](../decisions/headless-setup.md)). `dev/session` is such a sibling of `node`, so only a holder of the phrase derives a development session token.

Users of the tree: the login secret ([HTTP](http.md)), settlement entropy at `node/settlement-module/<scheme>/<path>` ([XRPL](xrpl.md#the-wallet)), the STREAM receivers ([Payments](payments.md#receiving)), the Open Payments key ([Payments](payments.md#wallet-addresses)), the QUIC endpoint's key for stateless resets ([Peer protocol](peer-protocol.md#quic)), and a settlement hub's keys at `node/hub/<nonce>/<name>`: a validator's consensus, escrow and payout keys, and a sponsor's escrow master key ([Settlement hubs](hubs.md#the-escrow)).

## Node key

Signing is pure Ed25519. **Verification follows ZIP-215** (`ed25519-zebra`), not `ed25519-dalek`'s cofactorless `verify`: ZIP-215's rules are exact, so every implementation agrees on every signature, edge cases included, and being stricter than the original could split the network on edge-case signatures.

The price is **small-order keys**: under ZIP-215 a signature with `s = 0` and a small-order `R` verifies every message under a small-order public key. So every place where a key must prove something refuses weak keys (`PublicKey::is_weak`): link states and the senders of authenticated peer messages ([Peer protocol](peer-protocol.md)), rate feeds ([Rate feed](rate-feed.md#signing)), Open Payments client keys ([Payments](payments.md)) and the release key ([Release](release.md)). Keys derived from a seed are never weak.

Node keys, signatures and node IDs stay Ed25519 for good, since the chain to the node ID is fixed; post-quantum protection would cover only the peer protocol's key agreement ([roadmap](../roadmap.md#smaller-open-points)).

## Node ID

The node ID is the short, self-certifying name of a node: a truncated SHA-256 of the public key under a versioned OID, base64url, prefixed with `d` (`src/node_id.rs`). It strips trailing `A` characters, a quirk of the original kept because node IDs must not change.

An ID received from elsewhere is only a name until checked: it must equal the ID computed from the key it comes with, and a link state, peering request or authenticated message whose ID and key disagree is refused ([Peer protocol](peer-protocol.md)).

## Node label

A node ID cannot be a hostname as it is: DNS ignores case, and base64url depends on it. So a node is named in DNS by its label (`src/label.rs`): the lowercase base32 (RFC 4648, no padding) of the 24 digest bytes the ID names, which are its characters after `d`, padded back to 32 with the `A`s the ID stripped, then decoded. That is 39 characters, within DNS's 63. Front doors serve a node without a hostname as `<label>.<domain>` ([Payments](payments.md#the-nodes-names)), and a client checks the key a node signs with against the ID the label names ([Payments](payments.md#signed-responses)).

The mapping is one to one. A label is read in either case, but its unused last bits must be zero; an ID that ends in `A`, which no key gives, has no label, since it would share one with another ID. The label is a compatibility surface like the ID: names in DNS and in clients' records are built from it.

## Object identifiers

Dassie's OIDs sit under the private arc `1.3.6.1.4.1.54392.5.1399`: `.1` for the peer protocol, `.2` for node fingerprints, `.3` for the [rate feed](rate-feed.md#signing). Under `.1`, `.1.3` signs link states and `.1.4` is the domain of a name's commitment ([Peer protocol](peer-protocol.md#names)). They are hashed into node IDs and signed into link states and feeds, so an arc is never reassigned, including `.1.1`, which the original defined and nothing uses. A new version of a signed structure takes a new OID, so a signature over the old one cannot pass as the new ([Peer protocol](peer-protocol.md)).

## X25519 key

Peer messages are authenticated with a key agreed by static-static X25519 between the two node keys ([peer-protocol-v1](../decisions/peer-protocol-v1.md)). The Ed25519-to-X25519 conversions are libsodium's, so a node's X25519 key follows from its node key alone and peers need no second key. An all-zero shared secret is refused, so a peer cannot force a secret it knows with a small-order key. How the secret keys the MACs is the peer protocol's.

## Handling of secrets

Secrets (master seed, node key, derived secrets, X25519 and shared secrets) are wiped on drop, are not `Copy`, print redacted and compare in constant time. Errors never carry a secret, so they may be logged and shown. A mistyped phrase is an error, never silently a different node. The node stores its key as the raw seed ([Node](node.md), [secrets-at-rest](../decisions/secrets-at-rest.md)).

## In the browser and in scripts

`dassie-identity` and `dassie-stream` (with `dassie-ilp`'s codecs) are built to WASM (`node --run build:wasm`) and published as `@dassie/identity-wasm`, so the wallet derives keys with exactly the code the node runs. One `web` build serves browsers and Node ([node-and-pnpm](../decisions/node-and-pnpm.md)): `.` for scripts and tests, `./web` for browsers. Development-only functions (`devSessionToken`, `sign`, `mnemonicFromEntropy`) are left out of `./web`, and so are node labels (`nodeLabel`, `nodeIdFromLabel`), which only scripts use so far.

## Decisions

- [peer-protocol-v1](../decisions/peer-protocol-v1.md): peer authentication by static-static X25519 between node keys.
- [database-continuity](../decisions/database-continuity.md): an owner recovers by entering the phrase again, which gives the same node ID and accounts.
- [secrets-at-rest](../decisions/secrets-at-rest.md): the node key stays plaintext at rest.
- [tigerstyle](../decisions/tigerstyle.md): deterministic, bounded, no OS randomness in the core.
- [node-and-pnpm](../decisions/node-and-pnpm.md): one `web` build of the WASM modules for browsers and Node.
