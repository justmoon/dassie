# Checking the XRP Ledger's validators

An XRPL account that takes its server's word on which ledgers are validated and what they hold trusts the server with the node's money. Acting only on what is newer than the newest ledger seen protects against a server that lags, not one that lies: a dishonest server can have a scheme book a settlement that never arrived, cancel one that applied, or claim a testnet reset that writes off the node's balance. With real money, that would let a server's operator take a node's money.

This design has the node check the XRP Ledger's validators itself, on both networks, so that **nothing is booked, cancelled or written off on a server's word**. Every answer the node acts on proves itself against a ledger its own UNL validated, so a server is relied on to answer, never trusted. The proofs come from rippled servers patched with three public methods (§3); the patch and the servers that run it are an open area of their own ([roadmap](../roadmap.md#proof-servers)). The reasons are [verified-ledgers](../decisions/verified-ledgers.md); it is built in the account but for what the [roadmap](../roadmap.md#checking-xrp-ledger-validators) lists ([XRPL](../areas/xrpl.md#following-the-account)). The mainnet schemes ([mainnet-schemes](../decisions/mainnet-schemes.md)) and the dollar token's peg guard ([issued-assets](../decisions/issued-assets.md)) build on it. Every bound named below is a constant of the code; the design gives only the reason for each.

## 1. The rule

- **A ledger counts as validated** only when a quorum of the node's own UNL signed its hash. The node **anchors** on a validated ledger only while those signatures are fresh by its own clock, so no server can pass an old ledger off as the newest.
- **An older ledger** counts once the skip list of an anchor proves its hash (§4).
- **A transaction counts** only when its bytes and its metadata are a leaf whose branch leads to the transaction root of a proven ledger.
- **State counts** (a balance, a sequence, a trust line, an issuer's flags, the reserve, a pool) only when the object is a leaf whose branch leads to the state root of a proven ledger. It is the state as of that ledger, and current as of the anchor when proven at the anchor.
- **An absence counts** only when proven: an object's by a branch that shows its key is not in the state tree, a transaction's by the state of its account (§4).
- **Everything else a server says is a hint:** which ledger is newest, the fee to offer, `submit` results, the account's history and its stream. A hint may steer what the node asks for, signs or waits for. It never reaches the books.

## 2. Trust model

- **Trusted:** the list publishers' keys, built in per network or set by the owner (§5); the UNL, the validators enough of the publishers' signed lists name, as rippled's defaults combine them (§5), each with its current signing key from manifests its listed master key signed; and the cryptography. Each publisher is trusted as a default rippled trusts it: with mainnet's two, either one's key alone can add validators to the UNL.
- **Assumed:** a quorum of the UNL is honest and signs one chain. This is the XRP Ledger's own assumption; the node adds none.
- **Relied on to answer, never trusted:** the proof server, the path to it (TLS authenticates only the server), and the list sites. A proof server that lies fails the first check its answer meets; one that is silent or refuses stalls the account, which never falls back to its word. A list site cannot forge a list, but it can serve an old one that has not expired (§5).
- **What binds the network** is the UNL, not a server's network ID. A validation signs no network ID, and the mainnet and testnet UNLs share no key. So an account's network is a constant of the account, and so is whether it resets ([ledger-resets](../decisions/ledger-resets.md)). The server's network ID stays a cheap first check, which catches a misconfigured server at once ([real-money](../decisions/real-money.md)).

## 3. The proof API

The node is built against three public methods of a patched rippled, on the WebSocket API it already speaks. Their names and shapes are the contract between the node and every proof server; when they change, this section and the fake ledger change with them.

- **`validations`** `{ledger_hash, untrusted?}` → `{ledger_hash, validations, truncated?}`: the validations the server holds for that ledger from the validators it trusts, full or partial, each the hex of a serialized `STValidation`; the node filters them by its own UNL. With `untrusted`, the answer also holds those from keys the server does not trust: a bounded number, the server's trusted ones first, so that validations from keys nobody trusts cannot crowd out the published UNL's, and a cut answer says so (`truncated`), so that the node can tell it from too few of its validators signing. The node asks without `untrusted`, since with the network's publishers its UNL is the one the server follows. It asks with `untrusted` when its publishers are the owner's (§10), and before it takes an answer short of quorum as a lie, since the server's lists may lag the node's. rippled holds a ledger's validations for about ten minutes, so a server serves recent ledgers only: the node asks only for the ledger it anchors on, whose validations are fresh by then, and reaches older ones through the skip list (§4). A ledger it holds none for gives an empty list.
- **`tx_proof`** `{tx_hash, ledger_index | ledger_hash?}` → `{ledger_index, ledger_hash, ledger_header, validated, path}`: its ledger's binary header, and its branch in that ledger's transaction tree from the inner node above its leaf up to the root. The node builds the leaf itself from the transaction and its metadata, which it reads in binary from `tx` or `account_tx`: those are the bytes the tree hashes, so the proof does not send them again. Without a ledger, the server finds which one holds the transaction.
- **`state_proof`** `{keys, ledger_index | ledger_hash}` → `{ledger_index, ledger_hash, ledger_header, validated, entries: [{key, path}]}`: one closed ledger's binary header, the server's newest validated one when the request names none, and for each key its branch in the state tree. When the tree holds the key, the branch starts at its leaf, which holds the object's binary form; the object is sent once, there. For a key the tree does not hold, the branch is a **proof of absence**: it ends at the empty slot where the key would hang, or at the leaf of another key that hangs there. A request names distinct keys, at most the patch's `kMaxProofKeys`, and the answer shares one header among them.

**Branches.** A `path` lists the nodes from the deepest one reached up to the root (for `tx_proof`, from the one above the leaf the node builds), each the hex of the node as rippled hashes it, prefix included: the node hashes each with SHA-512Half and checks that its parent names that hash at the key's nibble, up to the header's root. The deepest node is the key's leaf, another key's leaf, or an inner node whose slot for the key is empty; the two last prove the key absent, since a leaf hangs at the shallowest depth at which its key is unique. An empty tree gives an empty path, whose root in the header is zero.

The byte formats are rippled's own, so the node recomputes every hash itself: the header with its `LWR` prefix (`ledger_header` is the header without it), inner nodes with `MIN` and sixteen child hashes, transaction leaves with `SND` over the transaction, its metadata, each with its length, and its hash, state leaves with `MLN` over the object and its key. `ledger_index`, `ledger_hash` and `validated` are hints. A server answers `lgrNotFound` for a ledger beyond its history. A proof server keeps at least the history bound (§6) of ledgers; one that keeps less serves a node that was away for a while no better than a stock server.

A stock rippled lacks these methods. An account pointed at one stalls, and says that its server serves no proofs.

## 4. What is proven, and how

| What | Proven by | What a lying server can at worst cause |
|---|---|---|
| **The anchor** | A `state_proof` that names no ledger, so at the server's newest validated one, gives a header, which the node hashes; `validations` for that hash must give a quorum of the UNL, each validation full and fully canonical, signed by its master's current signing key, with a fresh signing time. | A stall, or an anchor as old as the freshness bound plus the node's clock error, never older than the newest anchor kept (§6, §7). |
| **An older ledger** | The skip list: a `state_proof` at the anchor of the `LedgerHashes` object of recent ledgers proves each of their hashes at once. The lists that keep every flag ledger's hash reach further back, so any ledger is at most two state proofs from the anchor, and one proof covers a whole run of history. | A stall. |
| **A transaction** | Its binary transaction and metadata from `tx` or `account_tx`, which the node builds the leaf from, under the hash it computes from the transaction itself, and `tx_proof`'s branch from that leaf to the transaction root of a header whose hash is proven. The record the schemes read is decoded from these blobs, never from JSON; its ledger is the proven one. Blobs that are not the ledger's fail the branch. | Withholding it: a stall, or beyond the history bound, history the server does not have (§6). |
| **Our account, our lines, their issuers, the reserve** | One `state_proof` at the anchor of the account root, each line a scheme follows, each such line's issuer's account root (its global freeze and transfer rate), and the `FeeSettings` object (the reserve and the base fee). | A stall, or a state as old as an anchor may be. |
| **A pool,** for the peg guard | The pool's account cannot be derived from its asset pair: the `AMM` object, keyed by the pair, names it. So a first `state_proof` of the `AMM` object gives the account, which the node keeps. Each reading then proves, in one `state_proof` at one ledger, the `AMM` object, that account's root (the pool's XRP) and its line to the issuer (the token), and reads the account again if the proven `AMM` object names another. | A reading as old as an anchor may be (§7). |
| **A transaction's absence** | A `state_proof` of its account's root at the transaction's last ledger, or any later one: a `Sequence` not yet past the transaction's own. Where the sequence moved on, the transaction that took the number is proven instead. | A stall. A settlement that applied is never cancelled. |
| **An account's absence** | A proof of absence of its root at the anchor. | A stall. |
| **The history** | Each object the account follows, proven at the anchor (its root and each line a scheme follows), names the newest transaction that changed it, and each proven transaction's metadata the one before; each is proven by `tx_proof` (§6). `account_tx` and the account's stream are hints that name the same hashes sooner. | A delay, until the next anchor. |
| **The server's state, the ledger stream, the fee to offer, `submit`** | Hints. The fee offered is bounded by the fee ceiling, and the fee booked is the proven transaction's. | A stall, or a fee up to the ceiling. |
| **The faucet's answer** | A hint to read the account again. | A wasted request. |

**Proving an absence.** A leaf's hash commits to its key, and a leaf hangs at the shallowest depth at which its key is unique among the tree's keys. So a branch along the missing key's path that ends at an empty slot, or at the leaf of another key, proves the key absent: had it been there, an inner node would stand in that place.

**A transaction's absence by its sequence.** An account's transactions take its sequence numbers one at a time, and a transaction can apply only up to its last ledger. So once the account root, proven at that last ledger or any later one, holds a `Sequence` at or below the transaction's own, nothing took that number in time, and the transaction never applied and never will. Where the root holds a higher one, something used the number up: the transaction itself, which `tx_proof` then proves; another with the same number; or a `TicketCreate` whose tickets span it. Each of the last two changed the root, so the walk of the root's history (§6) finds and proves it, and either proves that the transaction can never apply. The node itself signs with sequence numbers only, never with tickets. Only an account deleted and made again, which skips the numbers between, can leave no transaction that took the number: the settlement then stays pending for the owner, never cancelled, and is counted. Each of these cases means someone else signed for the account, such as the owner with its seed in another wallet. A settlement that applied is still never cancelled: an account can be deleted only once its sequence is well below the ledger's index, so a root made again never shows a sequence at or below a number that applied. No ledger is scanned, and nothing about when the transaction was signed needs keeping.

## 5. The UNL from its publishers

- **Signed lists over HTTPS,** from each publisher's own site: on mainnet, the two publishers rippled's default configuration names; on the testnet, its own. Their master keys and sites are built in per network, and the owner can replace them (§10). The proof server never relays a list.
- **A list counts** when the publisher's manifest verifies under the configured master key, the list's signature under the publisher's current signing key, its sequence is not below the highest the node has seen (also after a restart), and it has not expired. A list that takes effect later waits until then. A validator's manifest in a list applies only to a master the list names.
- **Newer manifests.** Validators rotate their signing keys, and the manifests in the lists lag behind. For a validator of the UNL whose validation did not count, the node asks the server's `manifest` method for its master's newest manifest, and takes the answer only when it verifies under a listed master key. The highest sequence wins, a revocation removes the key, and a signing key serves one master only, never one a list names as a master. Asking by master keeps the questions to the UNL, while a mainnet server relays the validations of many validators not on it.
- **The lists combine as rippled's defaults combine them** ([verified-ledgers](../decisions/verified-ledgers.md)), so the node counts the UNL and the quorum that the network's servers count from the same lists. A validator is on the UNL when at least rippled's default threshold of the publishers' current lists name it: one list with fewer than three publishers, which makes mainnet's two a union, and a majority with more; a validator whose master revoked its key is not. There is no UNL while as many publishers have no list in effect as could keep off a validator that would otherwise be on it, or as leave too few lists for any validator to reach the threshold, whichever is fewer: with one or two publishers, any one; with mainnet's two, either list unavailable stalls the node, as it stalls rippled. Lists that name no validator often enough give none either. Mainnet's two lists name the same validators today.
- **UNL-blocked, as rippled is.** Once a list in effect expires, or the lists name no validator, as at a fresh start before any list came, there is no UNL until every publisher has a list in effect again, however few lists the threshold needs. So with three or four publishers, one publisher's expired or never-fetched list cannot leave the UNL to what the others share, which either of them could then shrink to a single validator. A publisher that revokes its key does not block, as in rippled: the others' lists then make the UNL ([verified-ledgers](../decisions/verified-ledgers.md) accepts this). The block is kept with the account's state (§10), where rippled's lasts until it restarts, so a restart never lifts it.
- **Quorum is rippled's:** four fifths of the UNL's effective validators, those not on a negative UNL, and never fewer than three fifths of the whole, each rounded up as rippled reckons it in single-precision floating point, which makes three fifths of some sizes one more than the exact fraction. The node reckons it in whole numbers to the same result for every UNL it can hold. **No negative UNL at launch:** every validator is effective, so a ledger is never accepted with fewer signatures than rippled requires when no validator is marked unreliable.
- **Nothing of the node's own.** There is no floor on the UNL, and the node does not offer what rippled lets its operator set instead of the defaults: a threshold, a quorum, or validators named without a publisher (§10).
- **Never trust instead.** A list counts until its expiry, whether or not its site answers; an expired one makes its publisher unavailable. There is no fallback to the server, to an expired list, or to the validators last seen. Lists are kept with the account's state, so a restart does not need the sites first. A list is fetched again periodically, more often near its expiry, at once when quorum is lost, and from a publisher's second site when the first fails.

## 6. The account on proofs

- **Anchoring.** The account anchors when it connects, before it signs, when a hint says something it waits for may have happened (a transaction of ours, a peer's settlement, a guard's reading), and periodically so that its anchor stays fresh. Each anchoring is one round: a state proof at the server's validated ledger of every object the account follows, and of the skip list that holds the kept anchor's flag ledger (§7), then that ledger's validations. There is no validations subscription. The newest anchor (index, close time, hash, and the hash of the newest flag ledger below it) is kept with the account's state.
- **An older anchor is never current.** An anchor below the newest kept on the same chain, with a lower index and an earlier close time, is never taken as current state: the account waits for a newer one. So a server that serves an old ledger with its old validations can stall the account, never move its balances, its sequence or a guard's reading back.
- **Validated ledgers move only with anchors:** the newest ledger, expiry and the schemes' news of closed ledgers. A transaction's last ledger is the anchor's index plus a bound, so a lie can neither expire a transaction at once nor keep it valid for good. The account signs only from an anchor younger than another bound, so that a last ledger is never already past.
- **The history, complete.** Each object the account follows, its own root and each line a scheme follows, names in the state proven at the anchor the newest transaction that changed it (`PreviousTxnID`) and that transaction's ledger (`PreviousTxnLgrSeq`); a proven transaction's metadata names, for each of these objects it changed, the one that changed it before, and its ledger. The account walks each object's chain back to the transactions the schemes have booked, proving each by `tx_proof` at the ledger so named, and the schemes book them in ledger order as today. The lines are walked as well as the root, since a transaction that only changes a line (a token's settlement, a clawback) leaves the account root as it was. So a transaction a server leaves out of the history, at the newest end or in the middle, is found by its hash and proven by the next anchor; `account_tx` and the stream only name the same hashes sooner. The walk finds hashes and nothing else: state is never taken from it ([verified-ledgers](../decisions/verified-ledgers.md)). Each round takes at most a bound of steps, and the walk carries on at the next. Once walked, the proven root and lines must be what the proven transactions leave; a mismatch is a lie. The issuers' roots, `FeeSettings` and a pool are read as proven, and checked against no history.
- **Expiry.** Past its last ledger, by an anchor, an executed transaction is proven applied by `tx_proof`, or proven absent by its account's sequence (§4), and only then cancelled. Until one of the two, it stays in flight.
- **The history bound.** A ledger older than the history bound, which every proof server keeps at least (§3), is beyond it. Whether a transaction is beyond it is judged only on a proven ledger index: the `PreviousTxnLgrSeq` of an object proven at the anchor or of a proven transaction's metadata, and for a transaction of ours, also the last ledger it was signed with. Never on the index a hint names: a hash only the history names, whose ledger is not proven this way, is within the bound. A transaction beyond the bound that the server answers `lgrNotFound` for is history the server does not have, as for a server without history today: the books are matched to the proven state through suspense, a peer's settlement in the gap is booked as the owner's deposit, and a settlement of ours stays pending for the owner, never cancelled; it is logged as a warning and counted. Within the bound, a server that refuses or does not answer stalls the account: it connects anew, and waits with the reason shown. A server that answers `lgrNotFound` within the bound keeps too short a history, and the reason says so, so an owner who named it knows to name another.
- **A lie is a reconnect.** A header that hashes wrong, a branch that does not reach its root, a leaf of another key, validations short of quorum, an absence that the history proves wrong: the account counts it by kind and connects anew, as for a request left unanswered. Validations short of quorum in an answer the server says it cut (§3) are no lie the account can tell: it connects anew a while later all the same, and says why, without counting one.
- **A fork,** two validated ledgers of one index, or a skip list that names another hash for a proven ledger, means the UNL validated two chains: on a network that never resets, the account stops as failed. Under the trust assumption it cannot happen. On a network that resets, a later anchor off the kept chain is a reset (§7).
- **Phases and reasons.** Connecting becomes: the server's state, the subscriptions (the account and the ledger stream, as hints), a UNL ready, an anchor, the state proven, the history proven in order, then synced. Each step that waits shows why, such as waiting for the validator lists, a UNL blocked until every publisher has a list again, lists that name no validator often enough, no quorum of validators, a server that cut its validations short of one, a server that serves no proofs, a server whose history is too short, or answers that do not prove, so the owner sees why a scheme stands still.
- **Signing and submitting** need a proven balance, a proven sequence and a fresh anchor. Executed transactions are submitted again on each connection, proven or not: submitting books nothing.

## 7. Resets under a UNL

- **A reset is a chain the testnet's UNL validates that the kept anchor is not on.** Index and close time alone cannot tell: a node down across a reset may meet the new chain already past the kept anchor's index. Ancestry can. Each anchor keeps the hash of the newest flag ledger below it, from its own skip list. A later anchor is on the same chain when its skip lists hold that same hash for that ledger; one more key in the anchor's state proof shows it, with no old history needed. Only an anchor below its chain's first flag ledger keeps its own hash instead, which a later anchor proves through that flag ledger's skip list (§4). On a network that resets, an anchor with a lower index and a later close time, or a higher one that closed later whose skip lists hold another hash for the kept ledger, or none, is a reset: the account writes off and follows the new chain. A server that shows a lower ledger is only a hint to anchor ([ledger-resets](../decisions/ledger-resets.md)).
- **Along one chain both index and close time grow.** So a validated ledger with a higher index but an earlier close time is on no chain the kept anchor is on. On a network that resets, it is on an older chain and is ignored, and the close times are compared before ancestry is judged: judged first, it would be off the kept chain and so a reset, and validations of the old chain served after a reset would flip the account back. Freshness already stops them; this keeps the rule right on its own. A network that never resets has no older chain, so there the same ledger is a fork (below).
- **After a restart,** the first anchor is judged against the kept one by the same rule, so a reset that happened while the node was down is seen however far the new chain has grown. The UNL decides both.
- **New validator keys.** A reset that also re-keys the testnet's validators leaves no quorum until the new list is fetched; the fetch on lost quorum finds it, then the reset is seen.
- **On a network that never resets,** a lower validated ledger that closed later, or a higher one that closed earlier or is off the kept chain, means the validators went back or forked: the account stops as failed, as today. Nothing is ignored as an older chain here, since the UNL validated no other.
- **The clock.** Fresh signatures need the node's clock within the window. A clock that runs ahead sees no validation as fresh, and stalls the account with its reason. One that runs behind makes older validations look fresh, so an anchor may be as old as the freshness bound plus the clock's error; never older than the newest anchor kept, since an older anchor is never current (§6). A wrong clock can hold the account's view still, never move it back.

## 8. The verifier

New sans-IO modules in `dassie-xrpl`, under the crate's rules ([tigerstyle](../decisions/tigerstyle.md)): time is an input, nothing recurses, every queue and walk has a named bound, no float (a quorum is integer arithmetic), and untrusted bytes get an error value, never a panic.

- **A generic codec walker** reads any canonical serialization field by field, knowing only the types: strictly ascending fields, lengths by type, objects and arrays nested within a bound. So what it reads writes back to the bytes it came in, and a validation's and a manifest's signed bytes are their fields written again without the signatures. The strict codec for what the node signs stays as it is.
- **Binary records and objects.** A binary transaction and its metadata decode into the record the schemes read today, so the schemes and the hub read it unchanged; a binary account root, line, issuer's root, `FeeSettings`, `AMM` object, signer list and skip list decode into what their readers need. A record carries a mark that only the verifier sets.
- **The header** parses and hashes.
- **One branch check for both trees,** `verify(root, key, leaf, branch)`, iterative: each level must name the one below at the key's nibble, up to the root. A transaction leaf, a state leaf and an absence differ only in the leaf.
- **Skip lists** decode from their proven objects; a hash taken from one is a proven ledger's.
- **Manifests, lists and the UNL** (§5).
- **Validations and quorum.** A validation counts only if its key is a listed master's current signing key, it is full and fully canonical, its signing time is fresh, and its signature checks. A master that signs two hashes for one index counts for neither. The cheapest checks come first, so a flood costs at most two signature checks per master and anchor: its validation of the ledger, and, for a master that counted, one of another ledger of the index.

## 9. IO

- **Requests** added beside the account's: the three methods (§3), `manifest`, and `tx` and `account_tx` in binary for the transactions to prove, at the API version the account already pins. The streams of the account and of closed ledgers stay, as hints. No validations or manifests stream.
- **The lists over HTTPS,** through a new pair beside the faucet's in the external-asset interface: the account asks for a fetch, the node carries it out and hands back the body, or nothing on any failure. No redirects are followed, so a built-in site is the address that serves the list. Public addresses only, but where private ones are allowed (dev, tests).

## 10. Configuration and state

- **Per network,** built in: the network ID the first check expects, whether it resets, its list publishers (each a master key and the sites that serve its list), and its default proof server.
- **The owner's override.** The account's config may name the list publishers, each by its key and its sites, which then replace the network's defaults entirely: an owner who trusts one publisher only, or runs their own. Their lists combine as any publishers' do (§5). The config may also name the server, which must be a proof server that keeps at least the history bound (§3). With the owner's publishers, the node asks for validations with `untrusted` (§3), since the server follows another UNL. A static list of validators without a publisher is not offered. Like the server and the faucet, the publishers are the account's config, which the scheme that activates it names.
- **Kept with the account's state:** the newest anchor with its hash and its flag ledger's; each publisher's current list and a pending one, as received; each listed validator's newest manifest, so that a restart never hands its signing back to a key it rotated away from; and whether the UNL is blocked (§5), which holds only under the same publishers.
- **At load,** lists and manifests are verified again. One that no longer verifies, because the owner changed the publishers, or that expired, is dropped and fetched again: a config change, not an impossible state. Refused as impossible: two current lists for one publisher, more manifests than the UNL's bound, or two for one master.
- **A state written before verification** has a newest ledger without a hash. It is kept as a hint; the first anchor replaces it by the chain rule, and one that would stop the account as having gone back replaces it instead, since only the old hint can have been wrong.

## 11. The fake ledger, the lying server and the simulation

- **The fake serves the three methods,** `manifest`, and `tx` and `account_tx` in binary, in the shapes of the patch on the live proof servers, so the node cannot pass against the fake with a shape no server sends. Each closed ledger has a real header with real transaction and state roots: every object in rippled's binary form under its key, the skip lists and `FeeSettings` as rippled keeps them, and every applied transaction with its binary metadata. A test checks, for every kind of object and transaction the fake writes, that the binary decoder gives what the fake's JSON says. Fixtures captured from mainnet pin its trees against rippled's (§13), so the fake and the node cannot agree on a wrong tree.
- **Validators and a publisher.** A few validators, enough that one can be withheld and the network still validates, each with a master key, a signing key and a manifest, sign every ledger; the fake keeps their validations for `validations`. A publisher signs their list, served in-process and by `fake_ledger` beside its faucet; the node names it as an owner's publisher (§10). Tests can rotate a validator's key, publish a new list, let one expire and revoke. In mainnet mode the fake has validators of its own, so the two networks' UNLs share no key, as live.
- **A reset** starts the chain again with a later close time, and the same validators validate it; optionally with new keys and a new list.
- **A lying server.** A connection can be made dishonest, in-process and through `fake_ledger`, with each kind of lie: a transaction no ledger holds, an altered object, a proof of absence for an object that exists, the branch of another key, an old anchor with its old validations, forged or replayed validations, a header that hashes wrong, a skip list of another chain, history left out (at the newest end and in the middle, of the root and of a line), a hint naming an old ledger for a recent transaction followed by `lgrNotFound`, refusals within the history bound, an old anchor after a newer one, and a reset with a made-up header.
- **Validation signatures in the simulation.** The `node` simulation closes ledgers fast for long simulated stretches, and checking every anchor's signatures, and the fake signing them, would cost much of its time. So validation signatures alone sit behind a narrow interface, as [engineering](../engineering.md#pragmatic-tigerstyle) asks of costly crypto: the node's checks the real signature; the simulation's has each fake validator sign with a keyed hash under a secret only the fake and the checker hold, which only the testing build can pass in. A lying server holds no secret, so it can withhold or replay, never forge. Everything else is checked for real.
- **The node simulation's fault.** A linked node's connection drops and comes back to a lying server of a drawn kind, for a time drawn from the production timings that end a connection; the next connection is honest. Beside the per-node checks against the fake's truth: nothing booked that the fake did not apply, no settlement cancelled that it applied, no write-off without a reset of the fake, and settling as before after the heal. Scripted runs set up each kind once, and a real reset under the UNL, one while a node is down until the new chain has passed its anchor, a key rotation, an expired list and a withheld quorum.
- **Coverage.** Each run counts every kind of lie, rotations, lists fetched, anchors, proofs and absences proven; CI asserts a minimum of each over the fixed seeds, and that every XRPL node anchored, so a change that quietly bypasses the verifier fails. A transaction proven never to apply needs a submission lost and the link down past its last ledger, which no drawn fault holds that long, so a scripted run sets it up and asserts it. The check against the fake's truth has a test of its own that it fires: XRP moved into an account in no transaction, which the fake can do and no real ledger does, fails the run under that check.
- **Where the real path runs:** the golden tests, the account's unit tests against an in-process fake with real signatures, and the end-to-end tests, whose `fake_ledger` signs for real.

## 12. Who else uses it

- **The peg guard** reads its pool through the account, as one state proof (§4), on whatever network its token is on ([issued-assets](../decisions/issued-assets.md)).
- **Hub validators** ([settlement hubs](settlement-hubs.md#6-deposits-and-withdrawals)) each run the same verifier, with the UNL of the escrow's network, and attest only what it proved: deposits and the outcomes of the escrow's transactions by `tx_proof`, and the escrow's setup by one state proof of its account root and signer list at an anchor. A validator can run the patched rippled itself, which gives it a proof server of its own, and any node another to name.
- **The market maker** keeps trusting its server: it trades its own money, by its operator's choice.

## 13. What pins it

Golden fixtures captured from mainnet and the testnet, trimmed and committed under `crates/dassie-xrpl/tests/data/`, with the scripts that captured them under `testdata/xrpl/`: ledger headers, one ledger's validations by the whole UNL, the publishers' lists and the validators' manifests, a ledger's transaction set with its root and a branch, ledger objects in binary as rippled stores them, skip lists, and both pools; and the live proof servers' answers of each method, with `tx` in binary and proofs of absence both ways, which prove end to end against each network's real UNL, and on which an account anchors as it would on the live server. One ledger is also captured as JSON, so the binary decoder is checked against rippled's JSON field by field.

The fixtures are to settle what rests on reading rippled rather than on what was captured: how the delivered amount is derived (the metadata's `DeliveredAmount`, else a Payment's `Amount`), the order of the two assets in an AMM's key, and the full set of serialized types the walker must know.
