# A node ID commits to an SLH-DSA key beside the Ed25519 key, so that a node can prove it is itself once Ed25519 falls

**Areas:** [Identity](../areas/identity.md#node-id), [Peer protocol](../areas/peer-protocol.md#versions), [Settlement hubs](../areas/hubs.md#the-rules), [Payments](../areas/payments.md#signed-responses), [Rate feed](../areas/rate-feed.md#signing), [Network](../areas/network.md#bootstrap-nodes), [overview](../overview.md#frozen-surfaces). Built: the key, the ID over both keys, and the key beside the Ed25519 key wherever an ID is checked. Not built: signing with it, and moving to a post-quantum signing key ([below](#later-proving-continuity)).

## Facts

- **The node ID is the most frozen surface.** Names point at it, front doors serve `<node ID>.<domain>`, a name's commitment seals its holder's ID, peers keep tables by it, a hub's rules name its validators, ILP addresses are `<scheme>.das.<node ID>`, and the default bootstrap list and relay pin it ([overview](../overview.md#frozen-surfaces)).
- **A hash of the Ed25519 key alone cannot outlast Ed25519.** A quantum computer that runs Shor's algorithm finds an Ed25519 key's scalar from its public key, which every link state publishes. From then on it signs as any node, under that node's own ID, and every check of an ID against a key passes it. Nothing in the ID lets the real node prove that it is the real one: its only key is the broken one.
- **Shor finds the scalar, not the seed.** An Ed25519 key's scalar is half of SHA-512 of its 32-byte seed, and every secret below the node key derives from that seed by HMAC-SHA256 ([Identity](../areas/identity.md#seed-paths)). Breaking Ed25519 reveals neither the seed nor anything derived from it; only a preimage of SHA-512 or of HMAC-SHA256 would.
- **SLH-DSA (FIPS 205) rests on the hash function alone,** as the ID and the seed tree do already. Its public key is 32 bytes at its smallest security category, its key generation from three seeds is a function the standard defines (`slh_keygen_internal`), and a signature is large: 7,856 bytes for SLH-DSA-SHA2-128s, 17,088 for -128f.
- **The phrase holds a 128-bit secret** ([phrase-format](phrase-format.md)), so nothing derived from it is stronger than 128 bits, against a classical or a quantum attacker.
- **The testnet is reset now:** every phrase, and so every node ID, changes anyway ([phrase-format](phrase-format.md)), and nobody runs the original ([peer-protocol-v1](peer-protocol-v1.md)). After the reset the ID freezes again, so this is the last time a change to what an ID commits to costs no one a migration.
- **Key generation is costly for the sets of small signatures.** SLH-DSA-SHA2-128s builds a tree of 512 one-time keys: about 15 ms of optimized native code, a thousand times an Ed25519 key's, and about 55 ms in the wallet's WASM. -128f builds 8: under a millisecond.

## Decision

**Every node has an SLH-DSA-SHA2-128s key, and its node ID commits to it.**

- **The key** is generated by FIPS 205's `slh_keygen_internal` from three seeds, `SK.seed`, `SK.prf` and `PK.seed`, each the first 16 bytes of the secret at its path below the node key: `node/slh-dsa-sha2-128s/sk-seed`, `…/sk-prf` and `…/pk-seed` (`NodeSecret::SlhDsa`). The paths are frozen, and name the parameter set, so that no seed ever serves two. The node, which holds only its node key, derives it as the browser does from the phrase; it computes the public key once, when it gets its key, and keeps it (`IdentityKey`), so nothing pays for a key generation twice.
- **The node ID** is the first 24 bytes of SHA-256 over the canonical OER of the fingerprint OID `…1399.2.2`, the Ed25519 public key and the SLH-DSA public key, each with its length ahead of it. `…1399.2.1`, the fingerprint of the Ed25519 key alone, is never reassigned. The ID keeps its length and its text.
- **A node's identity is the two public keys,** and wherever an ID is checked against a key, the SLH-DSA key travels beside the Ed25519 key, so that the checker hashes both:
  - **Link states** carry it as a field after the Ed25519 key, under the link-state OID `…1399.1.6`. The layout moved within peer protocol version 2 (`dassie/2`) before a release spoke it, so it needed no new version ([Peer protocol](../areas/peer-protocol.md#versions)).
  - **The QUIC certificate** carries it in an extension of its own, `…1399.1.7`, an OCTET STRING of its 32 bytes. The handshake proves the Ed25519 key, and the ID binds the SLH-DSA key to it: a certificate that names another SLH-DSA key names another node. So the identity a connection proved is what the peer protocol, places, relays, the hub's streams and paired devices take a sender by.
  - **Hub rules** name the sponsor and each validator by both keys, which an acceptance signs, so that a member dials a validator by the ID its rules give. The layout moved within hub protocol version 1 before a release carried it, so its vectors moved under it ([Settlement hubs](../areas/hubs.md#golden-vectors)).
  - **Signed responses** name both keys in their `keyid` ([Payments](../areas/payments.md#signed-responses)), configured bootstrap nodes and relays name both beside their ID, as do the discovery document and the list of mainnet validators.
  - **A snapshot** names no key: its reader already has the node's identity from the peering or from where it learned of the node, checked against the ID, and verifies under its Ed25519 key ([Rate feed](../areas/rate-feed.md#signing)).
- **Nothing signs with the SLH-DSA key.** Ed25519 signs everything, as before.

### Later: proving continuity

Not built; it is how the key is to be used, and what the layout above leaves room for. When Ed25519 is to be trusted no longer, a node makes a post-quantum signing key for its daily signatures, at a path of its own below `node`, and signs with its SLH-DSA key a statement, under a Dassie OID of its own as the signature's context, that names its node ID and the new key. Anyone verifies the statement against the SLH-DSA key the ID commits to, so the node keeps its ID, its names, its place in hub rules and its peers' tables, and a forger who broke Ed25519 holds no statement. The statement travels where a node's identity travels: link-state extension type 1 is kept for the new key, and the statement, larger than a link state's bound, goes in a version of its own or is fetched once per node and kept. From that version on, an ID is checked against the SLH-DSA key, the statement and the new key, and the Ed25519 key proves nothing.

## Accepted

- **Every node ID changes, once, with the testnet's reset.** The default bootstrap nodes and the default relay are named again by the IDs and keys of their new identities: each entry is left out until its node has its new identity, and a node runs without it meanwhile. The new layouts changed no released version: they moved under `dassie/2` and hub version 1 before a release spoke them, and the first release that does came with the testnet's reset.
- **32 more bytes wherever a node is named by its keys:** in each link state, certificate, signed response, bootstrap entry, and in a hub's rules for the sponsor and each validator.
- **A key generation per start.** The node, `dassie setup`, the front door and the wallet each generate the key once, from the node key or the phrase; tests and simulations keep the keys of their fixed seeds once made. Every build compiles the key generation optimized, `dassie-identity` included, where `slh-dsa`'s generic code is instantiated, or a debug node, and every test in CI, would take most of a second a key; and the node makes a key off its async runtime.
- **A release candidate of `slh-dsa` (RustCrypto),** pinned exactly, because its stable release is of an older generation of the hash and signature crates than the workspace uses. NIST's known-answer vectors pin its key generation (`crates/dassie-identity/tests/data/slh_dsa_keygen.json`), and an implementation apart from it, `@noble/post-quantum`, computes the identity vectors. It is `no_std` without `alloc`, wipes its seeds on drop, and needs no randomness to generate a key from seeds, so `dassie-identity` stays deterministic.
- **The seeds come from a KDF, not from a random bit generator** as FIPS 205's `slh_keygen` asks. The internal function it defines takes them as given; a validated module is not a goal.
- **The SLH-DSA key is as safe as the node key's seed.** Whoever steals the seed holds both keys, as they hold the node's funds, which derive from the seed too. A post-quantum identity guards against a broken signature scheme, not a stolen key.
- **Nothing proves possession of the SLH-DSA key today.** A node could name a key it does not hold; then its ID is a hash of a key nobody can sign with, and it can never prove continuity: its loss alone.

## Rejected

- *SLH-DSA-SHA2-128f:* its key generation is sixty times faster, but its signature is 17,088 bytes rather than 7,856. Key generation happens once per start; the continuity statement is made once per node but sent to, checked and kept by every node that knows it, so the smaller signature wins.
- *The SHAKE sets:* as standard, but several times slower here, with no hardware support for SHA-3, and they bring a second hash family into the ID's chain, which is SHA-256 throughout.
- *A 192- or 256-bit set:* the phrase's 128-bit secret bounds everything derived from it, so a larger key would be larger for nothing.
- *ML-DSA (FIPS 204) as the committed key:* smaller signatures and fast key generation, but security on lattice assumptions that are younger than the hash functions everything else already relies on. The committed key must outlast every other choice; a daily post-quantum key may well be ML-DSA, vouched for by the SLH-DSA key.
- *Committing to a hash of a key made later:* the ID would have to fix the later key's derivation now anyway, and a hash of a public key is no shorter than an SLH-DSA public key.
- *The key in a link-state extension rather than a field:* without it the ID cannot be read, so it is no extension a node may ignore. Extension type 1 stays kept for the key the statement will vouch for.
- *An SLH-DSA key in the link state, signed by Ed25519, and the ID left as it is:* once Ed25519 falls, the forger signs a link state with an SLH-DSA key of its own. Only the ID can bind the key.
- *The key below the master seed, beside `node`, so that only the phrase could prove continuity:* the node could not migrate itself, and the nodes that run without an owner at hand, bootstrap nodes and market makers, would need their phrases again; and a stolen node key loses the node's funds whatever the identity does.
- *Pinning a hub's validators by their Ed25519 key, to leave the hub's rules as they were:* the transport keys connections by node ID, and a hub's validators would be the one place a node's identity could not move past Ed25519.
- *Keeping the IDs of the default bootstrap nodes and relay until the reset:* their checks would fail at every start; an empty default fails nothing and says what it is.
- *New versions, `dassie/3` and hub version 2:* a version names what released nodes must agree on, and neither `dassie/2` nor hub version 1 is in a release. A new name would only retire one nothing outside `main` speaks, and leave every layout change after it a version of its own until the first release.
