# The node books only what ledgers its own UNL validated prove

**Areas:** [Checking the XRP Ledger's validators](../designs/xrpl-validation.md), [XRPL](../areas/xrpl.md#following-the-account), [Settlement hubs](../designs/settlement-hubs.md#6-deposits-and-withdrawals). A design, built in the account but for what the [roadmap](../roadmap.md#checking-xrp-ledger-validators) lists; its proof servers are an open area of their own ([roadmap](../roadmap.md#proof-servers)).

## Facts

- An XRPL account takes its server's word on which ledgers are validated and what they hold. A server that lies can have a scheme book a settlement that never arrived, cancel one that applied (so the node pays again), or claim a testnet reset that writes off the balance. With real money, a server's operator could take a node's money that way.
- A ledger is validated when a quorum of a UNL signed its hash. A ledger's header holds the roots of two trees: its transactions with their metadata, and its state, every object under its key. A leaf's hash commits to its key, so a branch from a leaf to a root proves that leaf, and a branch that ends where a key would hang proves the key absent. A ledger object, the skip list, holds the hashes of earlier ledgers.
- rippled's public API serves headers, whole binary transaction sets, binary transactions, manifests and a live stream of validations, but no past validations and no branch of either tree. Without branches, a transaction is proven only by fetching its ledger's whole set, tens to hundreds of kilobytes on mainnet, and an object only through the transaction that last changed it, which shows a state as of that transaction, not that it is current; an issuer's account is changed so often that even that is impractical. rippled computes branches already, for the peers in its own network, and keeps recent validations in memory.
- Validator lists are published, signed by their publishers, over HTTPS. Mainnet has two publishers that rippled's default configuration names, and the testnet one of its own. Validators rotate their signing keys with manifests, and the lists' manifests lag behind: several mainnet validators' current keys are only in newer manifests.
- A validation signs no network ID. The mainnet and testnet UNLs share no key.
- An account's transactions take its sequence numbers one at a time, and a transaction applies only up to its last ledger.
- Each ledger object names the transaction that last changed it and that transaction's ledger (`PreviousTxnID`, `PreviousTxnLgrSeq`), and a transaction's metadata names, for each object it changed, the one that changed it before. A transaction that changes a trust line names the line, and leaves its owners' account roots as they were.
- rippled combines several publishers' lists by a threshold: a validator is trusted when that many lists name it. By default the threshold is one with fewer than three publishers and a majority with more, and rippled has no quorum while as many publishers are unavailable as could keep off a validator that would otherwise be trusted. Beside that, rippled becomes UNL-blocked, and stops serving validated data, once a list in effect expires or it finds no validator to trust, and stays so until every publisher has a list in effect again; a publisher that revokes its key, or whose list never came after a restart from cached lists, does not block it. Its default configuration names mainnet's two publishers, so it trusts the union, and stops validating when either list is unavailable. The two lists name the same validators today. The network's validators are run, and its lists published, for these defaults.

## Decision

- **Nothing is booked, cancelled or written off on a server's word,** on either network ([the design](../designs/xrpl-validation.md#1-the-rule)). A ledger counts once a quorum of the node's own UNL signed its hash, and the node anchors only on one whose signatures are fresh; an older ledger once an anchor's skip list proves it; a transaction, and any state, once its branch reaches the root of a proven ledger; an absence only when proven.
- **Proofs from a patched rippled,** with three public methods: `validations` for a ledger, `tx_proof` for a transaction, and `state_proof` for objects, with proofs of absence ([the design](../designs/xrpl-validation.md#3-the-proof-api)). Their shapes are the contract the node is built against. Every answer proves itself, so a proof server is relied on to answer, never trusted. The project runs one public proof server per network to start, named in the defaults; an owner can name another patched server; and the patch is offered upstream, so that any rippled may serve proofs one day. There is no fallback to a stock server: an account whose server serves no proofs stalls, and says so.
- **State is proven directly,** by its branch in the state tree, at an anchor: the account's balance and sequence, its lines, their issuers' flags, the reserve, a pool. A transaction's absence is proven by its account's sequence at its last ledger, an account's by a proof of absence. Nothing is scanned, and no state is derived from the transaction that last changed an object.
- **The history is found from the state** ([the design](../designs/xrpl-validation.md#6-the-account-on-proofs)). The account's root and each line it follows, proven at an anchor, name the newest transaction that changed them, and each proven transaction's metadata the one before; the node walks these back to find any transaction of the account a server left out of its history. A walk finds at most a bound of transactions; what lies beyond it is a gap, as history beyond the history bound is: matched through suspense, counted and warned of. `PreviousTxnID` serves only to find a hash: what the node books comes from the transaction proven under it, and state only from state proofs.
- **An older anchor is never current.** State proven at an anchor below the newest kept on the same chain never replaces what is current, so an old ledger can stall an account, never move it back.
- **Anchors on demand.** The node keeps no validations subscription; it asks `validations` for the ledger it anchors on, and only then.
- **The UNL comes from signed lists** fetched over HTTPS from their publishers. Publisher keys and sites are built in per network, and the owner can replace them. The node verifies each list's signature, sequence and expiry, and the manifests in it, and takes a newer manifest from any source when it verifies under a listed master key. The proof server never relays a list. **The lists combine as rippled's defaults combine them** ([the design](../designs/xrpl-validation.md#5-the-unl-from-its-publishers)): the UNL is the validators that rippled's default threshold of the lists in effect name, the union with mainnet's two publishers; there is none while as many publishers are unavailable as stop rippled's quorum, any one of mainnet's two, nor while the node is UNL-blocked as rippled would be, which the node keeps across a restart; and quorum is rippled's, reckoned as rippled reckons it. The node keeps no rule of its own beside them: no floor, and no threshold or quorum the owner sets. No negative UNL at launch: quorum counts the whole UNL.
- **When a list expires,** or its site cannot be reached past the expiry, the account stalls and says why. It never falls back to trusting its server.
- **Both networks verify.** The testnet schemes too, and a testnet reset counts only once the testnet's UNL validates the new chain ([ledger-resets](ledger-resets.md)).
- **A server that does not answer stalls the scheme.** Every proof server keeps at least the history bound. Only a ledger beyond that bound, which the server says it no longer has, is history the server does not have, as for a server without history today: logged as a warning and counted. Whether a ledger is beyond it is judged only on a ledger index the node proved, never on one a hint names. A server that says it no longer has a ledger within the bound stalls the account, which tells its owner that the server's history is too short.
- **A reset is told by ancestry,** not by index alone: each anchor keeps the hash of the newest flag ledger below it, and a later anchor whose skip lists do not hold it is off the chain, a reset on the testnet and a failure elsewhere ([ledger-resets](ledger-resets.md)).
- **In the simulation,** validation signatures alone sit behind a narrow interface, so a simulated day does not spend its time on secp256k1; everything else is verified for real.

## Accepted

- **Availability rests on the proof servers.** With one per network at first, an outage of it stalls every node on that network that has no other: nothing settles, and nothing is booked wrong, until it returns or the owner names another. Hub validators that run the patch, and the patch upstream, add servers.
- **The project carries the patch** onto each rippled release until upstream takes it.
- **An anchor may be as old as the freshness bound plus the node's clock error.** A server can delay what came after it for that long, and show the peg guard a reading that old ([issued-assets](issued-assets.md)); never one older than the newest anchor the node kept.
- **Beyond the history bound, a server can shortchange a peer** by saying it no longer has a ledger: a peer's settlement there becomes the owner's deposit. Since the bound is judged on proven ledger indexes only, only a node that was away longer than the bound meets it, and it never costs the node.
- **Anyone can force a gap in the history,** cheaply: a walk finds at most a bound of transactions (`MAX_WALKED`), and a stranger can change the account that many times with one-drop payments while the node is not anchoring, as while it is down or reconnecting, for well under an XRP in fees. A gap books what it missed through suspense rather than as a deposit or a withdrawal, to the same balance. Once peers settle only over hubs ([hubs-only](hubs-only.md)), the schemes on the XRP Ledger keep only the owner's books, so no peer's settlement is attributed on them, and the owner's own transactions, deposits into a hub included, are settled even behind the cursor. Until then, a peer's settlement in such a gap is the owner's deposit, as beyond the history bound.
- **An account deleted and made again** skips sequence numbers, so a settlement of ours whose number was skipped can be proven neither applied nor absent: it stays pending for the owner and is counted. Only someone else signing for the account, such as the owner with its seed in another wallet, can cause it.
- **Liveness follows the lists.** With mainnet's two publishers, either list expired or unreachable past its expiry stalls every proof, as it stalls rippled in its default configuration. With more publishers, any one list that expires stalls every proof until every publisher has a list in effect again, as rippled's UNL-blocked state does, however few lists the threshold needs; and so does a publisher whose list never came since the node first started. So does a fifth of the UNL offline at once, which rippled rides out through its negative UNL.
- **A publisher's key alone can add validators to the UNL,** the same trust a default rippled places in its publishers. With mainnet's two, someone holding either publisher's key could list validators of their own until they hold quorum, and forge validated ledgers with their keys. A server of the network itself that runs the defaults would follow the same forged list, so the node trusts the publishers no further than the network's own servers do.
- **With three or four publishers, which only an owner names, a publisher that revokes its key leaves the UNL to the others,** as in rippled: the threshold then needs every remaining list, so either remaining publisher's key alone can shrink the UNL to what the two share, down to one validator. A revocation is its publisher's own act, rare, and seen by every rippled that trusts it; the expiry or absence of a list, which an attacker can more easily cause, blocks instead. The built-in configs of one and two publishers stall on any publisher without a list.
- **A list site can serve an old list.** It can delay a node's view of a list update up to the expiry of the list the node holds, and give a node that has never seen a newer one an older list that has not expired; the kept highest sequence stops it going back further. rippled has the same exposure.
- **A clock that runs ahead stalls the account,** since it sees no validation as fresh. **One that runs behind** lets a server pass off an anchor older by the clock's error, never older than the newest anchor kept.
- **The fee to offer stays a hint,** since it follows the load of the server's own queue; a lie costs at most the fee ceiling, and the fee booked is the proven transaction's.

## Rejected

- *The intersection of the publishers' lists,* so that no one publisher's key could add a validator: it is a rule of the node's own beside rippled's, while the network's validators are run and its lists published for rippled's defaults. Whenever the lists differ, the node would count another UNL and another quorum than the servers it proves against, and the publishers would have to curate their lists for a second rule. And either publisher could shrink it to any subset of the other's list, down to one validator, which is then a quorum by itself, so it needs a floor to be safe at all.
- *A floor on the UNL's size:* lists that shrink honestly below it stall every node that follows them until a release lowers it, and the node would hold a number per network that no one who runs the network keeps. With one rule shared with rippled, the lists that shrink rippled's UNL shrink the node's alike.
- *A bound on how far the UNL may shrink from the last one seen:* a new node has seen none, a list can shrink in steps that each stay within the bound, and the bound would rest on kept state, which an owner who changes the publishers drops.
- *Rebuilding transaction sets over a stock server's public API:* every ledger with a transaction of ours costs its whole set, state shows only as of the transaction that last changed it, so a server could pass an old state off as current, a busy issuer's account cannot practically be followed at all, and an absence takes a scan of every ledger the transaction could have applied in.
- *That rebuilding as a fallback, where no proof server answers:* a second path to the same guarantees, weaker in every case above, that runs rarely, so its faults would surface with real money; and any server could force the weaker path by refusing proofs.
- *State taken from the transaction that last changed it (`PreviousTxnID`), with a chain per object as its source:* a tie proves a state as of its transaction, not that it is current, so a server could hide a clawback or a spend behind a real but old state. A state proof at an anchor is current by construction. The field still finds the hashes of transactions a server left out of the history; it is never a source of state.
- *Carrying an unfinished walk across rounds,* so that the bound limits a round's work rather than what is attributed: no new anchor is taken until a walk is done, so a stranger who changes the account faster than the node proves transactions would keep it from anchoring at all, which stalls it. *Raising the bound* only moves the threshold.
- *A reset told by index and close time alone:* a node down across a reset, while the new chain grows past its anchor, would take the new chain for the old one, and match its old books against it.
- *The validations stream,* always on or on demand: a mainnet server streams every validation it hears, gigabytes a day into each node, which a desktop node on a metered line should not pay for, and a node on demand must wait for live validations of a new ledger. `validations` gives exactly the anchor's.
- *Proofs from rippled's peer network* (`TMProofPathRequest`): every node would speak rippled's peer protocol and need to be let into its network, and servers serve those proofs only with ledger replay turned on. The patch serves the same branches over the API the account already speaks.
- *A proof service apart from rippled:* it would keep its own copy of the ledger, and a codebase that must follow every amendment; rippled holds the trees and computes the branches already.
- *Several servers that agree:* they may share an operator, and agreement is not validation. A quorum of the UNL is what the XRP Ledger means by validated.
- *Validator lists pinned in releases:* a list expires and validators rotate keys on their own schedule, so pinned nodes would stall until they updated, and a node that never updates would stall for good. Publishers' signed lists move with the network; their keys are what releases pin.
- *A static list of validators without a publisher:* the same, by the owner's hand.
- *Lists relayed by the proof server:* it could not forge one, but it could choose which unexpired list a new node starts from, and one server would stand behind both what the node proves and what it proves against. Fetched from the publishers, the lists do not depend on the proof server.
- *The server's network ID as the network:* validations do not sign it; the UNL binds the network.
- *Stopping beyond the history bound:* a node away longer than the proof servers keep history could never sync again.
- *Verifying only on mainnet:* the testnet, dev and the simulations would run code that real money does not, and the verifier would meet its first lying server with real money.
