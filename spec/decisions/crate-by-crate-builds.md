# CI builds the Rust workspace crate by crate

**Areas:** [Engineering](../engineering.md#ci-rebuilds-only-what-changed), [Testing](../areas/testing.md#levels)

## Facts

- The flake's checks run on a shared Nix builder, which keeps every derivation it built by its inputs. A check whose inputs did not change costs nothing; one whose inputs changed runs in full, however little changed.
- With crane, the workspace's tests and clippy were each one derivation over every crate's source. Only the dependencies were kept apart (`buildDepsOnly`), so an edit to any line compiled all twenty crates again, twice, and ran every test, about two minutes of compiling before a test ran, on every push.
- Most pull requests touch one or two crates, and most crates sit below few others: an edit to `dassie-node` concerns only what is built on it.
- crate2nix describes the workspace as one buildRustCrate derivation per crate, from Cargo's own resolution (`Cargo.lock`, features, targets). Vorstand's own repository builds this way.
- A derivation is keyed by everything it is built from. A crate built with other features, or on another build of one of its dependencies, or by clippy-driver rather than rustc, is another derivation, compiled again on the same builder at the same time.

## Decision

- **Each crate builds in a derivation of its own,** from its own directory and the files outside it that it reads (`nix/rust/default.nix`), so an edit compiles the crate edited and those built on it, and nothing else. `nix/rust/Cargo.nix` is crate2nix's output, committed, and a check (`cargo-nix-current`) fails while it differs from what `nix run .#cargo-nix` makes of the manifests and the lockfile.
- **Every crate builds once:** with the features the whole workspace asks of it, its members' tests included, as `cargo test --workspace` unifies them, and the workspace's own crates with clippy-driver, so that building one lints it, its build script too. Everything else links those builds: each member's tests, the end-to-end binaries, the desktop app. The only second build is the CLI's own, for its tests, with the test key that no other binary may trust.
- **Each member has one check,** its tests (`crate-<name>-test`), which builds and so lints its library, binaries, tests and examples. A change runs the tests of the crates it reached, and every other check is kept.
- **A crate's tests build target by target:** its unit tests, and each file in `tests/` and each example in a derivation of its own, from the library built with the features its tests turn on. An edit to one test file compiles that file; the crate's library source leaves out `tests/` and `examples/`, so editing them rebuilds no crate above.
- **The tests still run under nextest,** each in its own process, from the binaries built ([Testing](../areas/testing.md#levels)), with the ci profile's checks: overflow checks and debug assertions on, the dependencies optimized. The workspace's crates compile at opt-level 1 in sixteen codegen units, as fast to build and no slower to test; paths are remapped to Cargo's, so a panic names `crates/<name>/src/...` as a local `cargo test` does.
- **The desktop app builds like every other crate.** Tauri's build scripts hand their dependents paths into their own build directory, and names bash cannot export (`core:path`), which buildRustCrate passes on as sourced `export` lines; a crate that does keeps its build directory in its output, with the paths naming it there, and the names reach the build scripts through `env`. The crates only the app is built on, Tauri's, compile with debug assertions off, as the app ships, since Tauri compiles other code with them; the check wraps the app built for its tests.

## Accepted

- **A crate that reads a file outside its directory names it** in `nix/rust/default.nix`; until it does, its build fails for want of the file.
- **`nix/rust/Cargo.nix` is regenerated by hand** after a change to a manifest, the lockfile or a crate's targets, and a pull request that forgets fails a check.
- **CI no longer builds exactly as `cargo test` does:** the same code and checks, in other optimization settings, and compiled by clippy-driver, which skips MIR's optimizations. A test that passes only at one optimization level is a bug in the test. Nothing CI builds this way ships: releases, the desktop package and the WASM modules are rustc's, with crane.
- **Every binary CI builds has the tests' features,** the end-to-end tests' `dassie` included: `testing` and its kin only add code that a test turns on. Code compiled only without them would go unchecked; there is none, and the release builds compile without them.
- **No doc tests:** buildRustCrate does not run them. A doc example is marked `ignore`, or names another language, and what it shows is tested in the crate's tests; a check (`doc-examples`) fails on one that would be a doc test.

## Rejected

- *crane with finer source filters:* one Cargo build over the workspace still compiles every member whose source is in it, and splitting it per crate means one dependency build per crate, the same dependencies compiled again for each.
- *Cargo's incremental cache, kept between CI runs:* it is not keyed by input, so a run trusts whatever the last one left, and two runs cannot share it.
- *Tests in one derivation per crate, as buildRustCrate builds them:* it compiles the library, its unit tests and every test file one after another on one core; `dassie-node`'s took eight minutes.
- *Features resolved for each member's tests apart, as crate2nix does:* a crate was built once for each set of features a member's tree asked of it, and again for each build of its dependencies; one edit to `dassie-node` compiled it twelve times, and one to `dassie-oer` set off 364 builds.
- *Clippy as builds of its own:* clippy-driver compiles everything rustc does, its lints on top, so a separate clippy build compiled every crate of the workspace a second time. The WASM crates keep a clippy check of their own, which type-checks without compiling, since their modules ship and are rustc's.
- *The desktop app with Cargo:* it compiled the node and every crate below it again, in a profile of its own, and all its dependencies again whenever the lockfile changed.
