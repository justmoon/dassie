Core and periphery

Not every node can be reached from the internet. Dassie has a place for both kinds: nodes with a public address form the core, and nodes without one join at the edge, as the periphery. This page explains how a periphery node connects, how others reach it, and what the machines in between can see.

Two kinds of node

A periphery node always dials out, so it works behind a home router or a firewall, with no port forwarding. It never connects to another periphery node. On a server, setting a hostname makes a node core, and clearing it makes it periphery again. The desktop app's node always stays periphery.

Why it works this way

Uplinks and child addresses

A periphery node finds core nodes in the node list and peers with a few of them that share a settlement hub with it. These are its uplinks. Each one gives it an address beneath its own: if an uplink is test.das. followed by the uplink's node ID, your node is reached at that address followed by a dot and your node ID. The uplink passes on whatever arrives for that address.

Dassie has the testnet's four bootstrap nodes built in, so a new node gets the node list from them and finds its uplinks on its own. Joining the network says more.

  • Your node's payments go out through its uplinks, and reach whatever they reach.
  • Payments to your node come in through the uplink its payment request names, one it is connected to at the time.
  • Your uplinks never list your node as a neighbor, and no route in the network leads to it directly: only its uplinks know it is there.

You can pin a periphery node to particular uplinks with DASSIE_UPLINKS, a comma-separated list of node IDs. A market maker's node does that: the core nodes it pins are the ones it swaps with. See Environment variables.

A periphery node does not need an account in a settlement hub before it can be paid. Its uplink pays it in once it owes it enough to open one, as Settlement hubs explains. On a core node, periphery nodes that have never paid it hold at most half of the places it keeps for periphery nodes, so new keys made for nothing cannot crowd out the ones that pay.

One kind of link: QUIC

Every link between two nodes is a QUIC connection, over UDP. Each side proves its node key in the handshake, and the other checks it against the node ID. Either side can open streams on a connection, so your uplink sends to your node over the connection your node opened. There is no other way to peer, so a node on a server does not start without its UDP port: dassie.service does not start while something else holds UDP 443.

Nodes speak version 2 of the peer protocol, dassie/2, so a node of the 0.2 releases cannot peer with one of 0.3.0 or later. Protocol versions says how versions change.

Some networks block UDP. There, a periphery node carries the same QUIC packets over a WebSocket to the core node's HTTPS port, at /quic. It tries UDP first and the WebSocket a moment later, and keeps whichever connects first. It goes through an HTTP proxy if HTTPS_PROXY names one, except to the hosts NO_PROXY lists. The QUIC inside still proves each node's key, so whatever sits between sees only ciphertext. A core node always uses UDP.

Why it works this way

Relays and front doors

Wallets and apps that want to pay your node speak Open Payments, over HTTPS. A periphery node has no address they can reach, so they reach it through someone else.

  • A relay passes streams to the nodes connected to it. Every core node relays for its downlinks, and your node can keep a connection to one relay of its choice, even one it does not peer with. DASSIE_RELAY takes the relay's entry, as in the list of bootstrap nodes: its node ID, URL and keys, which a front door's operator finds in its log. The format is on Environment variables.
  • A front door is a relay that also answers on the web. It takes Open Payments requests at a name under its domain and passes them through to the node. The project's front door answers for dassiepay.net, where a node is to be reached at its node ID, such as https://<node ID>.dassiepay.net/pay/xrp, though not yet for 0.3.0 nodes (below). Anyone can run another: Run a front door.

A node keeps a relay only when DASSIE_RELAY holds the relay's entry. Dassie names no relay by default, so a node without a hostname, the desktop app among them, keeps none until you set it. Without a relay, your node still pays through its uplinks, but no Open Payments client can reach it, so other wallets and apps can't pay it. The wallet and dassie status warn you about that, and show which relay your node keeps and whether it is connected.

The dassiepay.net front door has no entry a 0.3.0 node can name yet. A node ID now also commits to a post-quantum key, so the front door gets a new ID once it runs a release that makes one, and no release builds that entry in yet. Until then, Dassie names no default relay, and nobody reaches your node at dassiepay.net. A node is reached at a name only through a front door that runs 0.3.0 or later, named by the entry it logs. Later, a node without a hostname keeps the dassiepay.net front door unless you choose another relay or none. What's next

Why a node is to have a default relay

What dassiepay.net can see

A front door answers on the web for your node, so it sees more than a relay does. Here is what the dassiepay.net front door, or any other, can and cannot see.

  • It sees which nodes are online, from which address, and since when.
  • It reads the Open Payments requests and answers it passes on, including the secret a payer uses to pay one of your payment requests. That is the nature of answering HTTPS for someone.
  • It cannot answer for your node to anyone who checks. Your node signs every Open Payments answer with its node key. Dassie nodes that pay you at dassiepay.net check that signature against your node ID, so a front door cannot fake an answer to them. A client that does not check trusts the front door.
  • It never sees your wallet. A front door passes on Open Payments and nothing else, and your wallet is never served through a relay or a front door.
  • It cannot put anything of your node's in front of a browser: it passes on only JSON, sets no cookies, and the one page it serves at a name, which says whose node it is, is its own.

Your node uses a front door only while it keeps it as its relay: today only while DASSIE_RELAY names it. To stop, name another front door, or none.

What is not there yet
