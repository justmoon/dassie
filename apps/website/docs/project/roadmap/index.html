What's next

Dassie is early. This page lists what it does not do yet, so you know where the edges are. The work has no numbered milestones: each area moves forward on its own, side by side with the others.

Early days. Dassie takes test money only: a node refuses the live realm. How far along it is

The full list, with what "done" means for each area, is the roadmap in the specification. This page says the same in plain words, and leaves out the internals.

Real money

Every node refuses the live realm, so nobody can put real money into Dassie yet. It stays that way until every condition on a short list holds. Still left: the node checking the XRP Ledger's validators in a few more cases, a live node that takes none of the testnet's defaults, settlement hubs on mainnet, a mainnet list of bootstrap nodes, and an external security review. Early days lists every condition and where each stands.

Why it works this way: each condition closes a way that real money could be lost.

The public testnet

Each node ID commits to a second, post-quantum key as well, so the testnet's four bootstrap nodes, boot1 to boot4, and its front door need new identities. Until they have them, a new node has no bootstrap nodes and no relay by default, and no default testnet hub is built in: it runs alone. Once the testnet is set up again, its bootstrap nodes, its relay and its XRP and DSUSD hubs become a node's defaults, and a new node finds the network on its own.

Later, testnet names move to test.dassiepay.net, so that dassiepay.net is left for the live realm.

Settlement hubs

Peers settle over settlement hubs, and the node runs as a hub's member and as one of its validators today. Still to come:

  • the testnet's default hubs, for XRP and for DSUSD, founded again under the current rules (see the public testnet);
  • for owners: closing your account in a hub, setting the floor and ceiling your node keeps it between, and moving to another hub of the same asset;
  • for validators: keeping their history across a restart, and a few rarer steps when a hub's validators change;
  • founding: replacing a validator that fails before the hub starts, and following a founding in the wallet;
  • hub balances and holds in the desktop app;
  • once hubs run for a while: fees that follow how busy a hub is, several hubs of one asset per node, and putting what a node earns into its holds.

Names

Names are built, and on the testnet they are free, held for your node by a quorum of the bootstrap nodes. Until the testnet is set up again (above), a node has no bootstrap nodes to register with. Testnet names may be reset at any time. A live node has no names. Next:

  • fees for names and for registering a node, so that nobody can take every good name for free; with them, names on the live realm;
  • showing in the wallet who holds the names your node looks up, and the payment address each of your names gives;
  • moving a name to a new node ID when you move to a new node.

Nodes without a public IP

A node without a public IP joins as a periphery node: it connects to core nodes as its uplinks, gets addresses beneath them, and is reached through a relay. That works today, over UDP or, where UDP is blocked, a WebSocket. Not there yet:

  • dialing a lost uplink again with a backoff;
  • becoming core. Today a node with a hostname is a core node and one without is a periphery node. Later, every node starts in the periphery and is promoted once it has shown it can be relied on;
  • front doors: the consent page for apps that ask to spend from your wallet, your own domain pointed at a front door, your names as a wallet setting, and rate limits per client behind a front door;
  • owner apps. The node pairs apps today (dassie pair), but the apps themselves, a remote mode of the desktop app and a mobile app, are still to be built;
  • the desktop app beyond Linux and Nix: AppImage, .deb and Flatpak packages, macOS and Windows, and updates of its own (Other platforms);
  • receivers that need no deposit of their own, and nodes that run in a browser.

Setting up in the wallet

Today you set a node up with your recovery phrase and a first ledger, and every other choice is a default. A guided setup in the wallet is to walk you through each choice that matters, and what it costs. One of them is your relay. Once the testnet's front door is set up again (above), a node without a hostname keeps a connection to it by default. The front door then learns when your node is online, and sees the Open Payments requests it passes on.

Exchange rates and swaps

  • Open rate sources. A node takes its exchange rates today from exchanges and the European Central Bank, whose terms allow personal or internal use. Next, it takes XRP's rate from mainnet's XRP/RLUSD pool, proven against validated ledgers, and the other currencies' from four central banks.
  • Peer swaps. A node's holdings drift as it forwards payments, and today only market makers bring them back. Next, nodes swap assets directly with their peers, at prices their peers publish.

Checking the XRP Ledger

A node proves what it reads from the XRP Ledger against ledgers its own list of validators signed, with the project's proof servers answering. Left: signing only from a fresh anchor, a few more cases in the simulations, offering the proof servers' patch to rippled, and riding out validators that go offline as rippled does. Issuer transfer fees on tokens are not handled yet: while an issuer charges one, the node does not pay from that token.

Kopje everywhere

This site draws in Kopje, Dassie's visual identity. The wallet and the desktop app's icons and tray do not yet.

Smaller gaps

  • ILP over HTTP. The node speaks BTP and Open Payments to clients, but serves no /ilp route.
  • Post-quantum TLS. The node's TLS uses classical key exchange only. Each node ID already commits to a post-quantum key, which signs nothing yet.
  • Limits per ledger. The largest packet, and the thresholds counted in it, are one value for the whole node, not one per ledger.
  • Live status in the wallet. The wallet asks the node for its status and hubs every few seconds, instead of following a stream.
  • A gentle shutdown. On stop, the node does not wait for payments in flight to finish. After the restart they count as rejected.
  • Peers over a node's lifetime. A node keeps the accounts of every peer it ever had in memory, which caps how many peers it can have in its life at a few thousand.
  • Pre-releases. There is one release channel, and no release candidates.

How Dassie is tested and released

  • Continuous simulation. A campaign already runs the simulations from random seeds and files an issue for each new failure. Next: wider random configurations in more simulations, and, once a live network runs on Dassie's releases, a release that waits until the campaign has cleared it.
  • Rebuilding releases. Each release is built once, then signed. Next, a second builder builds it again and signing waits until the bytes match.

Further out

Some designs stay future work, and the architecture must leave room for them: a way to pay for messages between nodes with tokens, a private transport between peers over UDP, and a wallet that does not have to trust the node that serves it.
