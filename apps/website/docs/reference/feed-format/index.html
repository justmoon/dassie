Rate feed wire format

A core node publishes what it converts at as a signed UDP datagram, its rate feed. This page describes every byte of it, for anyone who writes their own subscriber. Read a rate feed shows how to use one.

Early days. Dassie takes test money only: a node refuses the live realm. How far along it is

Where the feed is

A core node serves its feed on a UDP port of its own, 7768 by default, at the host of its URL. Two places name the port:

  • The discovery document, https://<host>/.well-known/dassie/node, as feedPort, beside the node's id, its publicKey and its slhDsaPublicKey, both in base64url.
  • The node's link state, in extension type 3, for tools that read link states.

Neither names a port the node doesn't serve. A periphery node, one without a URL, has no feed.

Encoding

Every datagram is canonical OER (ITU-T X.696) and starts with a version byte, today 2. Integers are big-endian and fixed in size. Lengths are OER length determinants: one byte below 128, otherwise 0x80 plus the number of bytes that follow. A list count is the count as a big-endian integer in as few bytes as it fits, after one byte that gives how many bytes it takes: zero entries is 01 00, two is 01 02. A CHOICE tag is one byte, 0x80 plus the tag number.

Every value has exactly one encoding, and a decoder refuses anything else: lists in another order, a pair twice, non-zero padding, or a length not written in its shortest form. So a feed's bytes are exactly what was signed. Every datagram fits in 1,200 bytes, which one packet carries on any path IPv6 runs on. 

Datagram ::= SEQUENCE {
  version  UInt8 (2),
  message  CHOICE {
    subscribe [0] SEQUENCE {
      cookie   CHOICE { absent [0] NULL, present [1] OCTET STRING (SIZE (16)) },
      padding  zero octets, up to 64 bytes in all
    },
    challenge [1] SEQUENCE { cookie OCTET STRING (SIZE (16)) },
    feed      [2] SEQUENCE {
      feed       OCTET STRING CONTAINING Feed,  -- what the signature covers
      signature  OCTET STRING (SIZE (64))
    }
  }
}

Feed ::= SEQUENCE {
  type             OBJECT IDENTIFIER (1.3.6.1.4.1.54392.5.1399.3.2),
  publicKey        OCTET STRING (SIZE (32)),
  sequence         UInt64,                       -- ms, only grows
  validUntil       UInt64,                       -- ms, after sequence
  feePpm           UInt32 (0..1000000),
  methods          SEQUENCE (SIZE (0..8)) OF SEQUENCE {   -- ascending by id
    id               IA5String (SIZE (2..32)),  -- a scheme's, [a-z0-9-]
    maxPacketAmount  UInt64
  },
  rates            SEQUENCE (SIZE (0..56)) OF SEQUENCE {  -- ascending
    from UInt8, to UInt8,                       -- indexes into methods
    rate UInt64                                 -- out per in, × 10^15
  }
}

The layouts are in crates/dassie-feed/src/wire.rs.

Subscribe

From a subscriber to the node. Always exactly 64 bytes.

Bytes Field
02 Version
80 Subscribe
80, or 81 and 16 bytes No cookie, or the cookie the node handed out last
Zeros Padding, to 64 bytes in all

The padding makes a Subscribe at least as large as the node's Challenge, so the node never answers an address with more bytes than it got from it.

Challenge

From the node, in answer to a Subscribe without a valid cookie. Always 18 bytes: 02, 81, then the 16-byte cookie. Send a Subscribe with that cookie at once.

The cookie proves that you receive datagrams at your address: it is an HMAC-SHA256 of your address, port and the current two-minute epoch, cut to 16 bytes, under a secret the node draws each time it starts. The node takes a cookie in its own epoch and the next, so it lives two to four minutes. When you renew with one from the epoch before, the node sends a fresh Challenge along with your renewal. After the node restarts, every cookie is void, and you are challenged again.

Feed

From the node, to every subscriber, once per feed. The outer part is 02, 82, the length of the signed feed, the signed feed, then the 64-byte Ed25519 signature. The signed feed's fields:

type

The object identifier 1.3.6.1.4.1.54392.5.1399.3.2, always these 14 bytes: 0d 2b 06 01 04 01 83 a8 78 05 8a 77 03 02. It makes sure a feed's signature never passes for anything else the node signs.

publicKey

The node's Ed25519 public key, 32 bytes. The node's ID derives from it and from its SLH-DSA key, which the feed leaves out.

sequence

When the feed was made, in milliseconds since the Unix epoch. Each feed of a node has a larger one, even if its clock went back.

validUntil

When the feed stops counting, in milliseconds; always after sequence. Usually 90 seconds after it, three heartbeats, or earlier when a rate the node uses ages out.

feePpm

The fee the node takes from every packet it passes on, in parts per million, at most 1,000,000.

methods

The settlement methods the node's peers pay it on, at most 8, in ascending order of their IDs, each once. Each is its scheme's ID, such as hub-xrpl-testnet-xrp (Schemes and hubs), with the largest amount one packet may carry when it comes in on that method, in the units of the scheme's ledger. IDs are strings, so a subscriber can read a feed that names a method it doesn't know.

rates

One rate per ordered pair of methods the node converts between, at most 56, in ascending order of (from, to). from and to are indexes into methods, never equal. rate is what one unit in gets out, times 1015, in the units of each method's ledger, the node's spread included, and never zero. A pair the node doesn't convert now is left out.

A packet that comes in with amount on one method goes out on the other with at most floor((amount − fee) × rate / 10^15), the fee being feePpm of amount. It gets less the larger it is against the node's holdings, since each packet pays for its own effect on them. The rates are what a vanishingly small packet gets, so a feed never promises more than a packet gets.

Checking a feed

The signature is Ed25519 by the node key, over the signed feed's bytes exactly as received, starting with type. Before you act on a feed:

  1. Take datagrams only from the node's address and port.
  2. Decode it, and refuse it if it is of another version, not canonical, or breaks a rule above.
  3. Verify the signature by the ZIP-215 rules, and refuse a key of small order.
  4. Check that publicKey is the Ed25519 key of the node you subscribed to. You learned both its keys, and checked them against its ID, from its discovery document or its link state.
  5. Take it only if its sequence is after the last one you took and validUntil is still ahead, so a replayed or delayed datagram never sets rates back.

A feed is signed, not encrypted. It says nothing the node's packets wouldn't.

Why it works this way and why a feed carries only the key that signs it.

Timing and limits

What Value
Least time between two feeds 1 second
Heartbeat, when nothing changes 30 seconds
How long a feed counts 90 seconds at most
How often a subscriber renews Every minute
A subscription without renewal lasts 5 minutes
Subscribers per node 1,024
Subscribers per client (an IPv4 address or IPv6 /56) 4

A full table refuses newcomers and sends them nothing; it never pushes out a subscriber who keeps renewing. A newly subscribed address gets the latest feed at once, if it still counts. Feeds are sent once, with no retries.

Versions

Within a version, the layout never changes: subscribers run software of their own, outside Dassie's releases. A change is a new version byte, and its feed is signed under a new object identifier, so no signature passes for another version's.

Version Signed under Names
2 …1399.3.2 The settlement methods peers pay the node on. Nodes speak it.
1 …1399.3.1 The node's ledgers. Refused.

A datagram of any other version is refused. The bounds on methods and rates are part of the layout: a feed with every field at its bound still fits in one datagram, and one method more would not.
