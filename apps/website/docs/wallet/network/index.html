Network and peers

The Network page shows your node among its neighbors: who it knows, who it peers with, and how it stands with the network. This page walks you through it, and through ending a peering or banning a node when you need to.

Early days. Dassie takes test money only: a node refuses the live realm. How far along it is

The page at a glance

Open Network in the top menu. At the top right of every page, next to the menu, a dot and a count such as 12 nodes tell you how many nodes your node knows, and whether the wallet is connected to it, still connecting, reconnecting, or failed. Select it to open the Nodes debug page.

The Network page has three parts:

  • The graph. Your node and every node a route reaches, with a line where both ends list each other. A peer that is offline, or that does not list your node back, has no line. Each node keeps its place as the network changes. Select a node to see its details.
  • Nodes. Every node your node knows, grouped by how far it is: This Node, Direct Peers, Peers Not Routed and Offline Peers, Other Nodes two or more hops away, and No Connection for nodes no route reaches. Each shows its name, or the start of its ID, and its URL.
  • Details. Your own node's standing, or, once you select another node, that node's details.

Registered or not

A node with a public address and a domain name is a core node. It joins the network by registering with the bootstrap nodes. Each keeps a list, and a node that more than half of them list is a member, which every other node then knows about.

Your node knows the testnet's four bootstrap nodes from the start, boot1.dassie.xyz to boot4.dassie.xyz, and registers with them by itself when it starts. It renews before a registration lapses. DASSIE_BOOTSTRAP_NODES replaces them, for a network of your own.

On a core node, the details card is Details for Your Node, with a section called Tier 1 Registration:

  • Registered or Not registered: whether enough bootstrap nodes list your node.
  • Listed by 3 of 4 bootstrap nodes: how many list it.

A new node shows Not registered for a while at first: each bootstrap node first checks that your node's URL answers, and your node then has to fetch their lists to see itself on them.

To see each bootstrap node, select Register (or Update registration). The page lists each one with whether it lists your node, when your node last registered, and when it last fetched that node's list. Renew now registers with that one again at once.

Swaps

Below the registration, the card shows how your node swaps with its peers (see Exchange-rate settings). Its badge says swapping when your node swaps by itself, with how many peers' quotes it reads, or on request when it swaps only when you ask. Once it has swapped, the lines below count what it sent: fulfilled, rejected and in flight, and how often it backed off, was refused, or got back too little.

Snapshot

Last, a core node's card shows whether it answers requests for its snapshot: the quotes it swaps at with its peers, signed by your node. Its peers get it over their peering. Anyone else, such as someone choosing a node to swap with, asks for it over UDP.

Badge Means
answering It answers at the address shown. The line below counts the datagrams it took: answered, over its budget, or ignored.
sends failed It answers, but some answers could not be sent.
not answering It has the socket, but no snapshot to give: it answers once it has a domain name and offers swaps to its peers.
none The node has no UDP socket for it, so it answers no request. Its peers still get its snapshot.

It answers on UDP port 7768, which you open as in Requirements. If that port is taken, your node runs without it. To ask a node for its snapshot yourself, see Read a node's snapshot.

Uplinks and relay

A node without a domain name, such as the desktop app or a server behind a router, is a periphery node. It registers with no bootstrap node. Its card says Periphery Node and shows these instead:

  • Uplinks. The core nodes it peers with, which carry its payments in and out, each connected or not connected, with when it was last heard from. With none yet, no payment reaches your node: it looks for core nodes that share a settlement hub with it. On the testnet, three of the four bootstrap nodes peer over both of its hubs, so a node in either finds uplinks among them. In the graph, your node has a line to each uplink it reaches directly.
  • Relay. The front door that apps and wallets using Open Payments reach your node through, with connected, connecting or unreachable. Dassie builds in no relay yet, so a new node keeps none and the card says None. Until you name one in DASSIE_RELAY, no one can reach your node through Open Payments, at its dassiepay.net address or anywhere else. You can still send, and Interledger payments still reach it through its uplinks.
  • Swaps. As on a core node (above), toward the targets you set.

For setting a relay or pinning uplinks on a server, see A server without a public IP; in the desktop app, see How others reach you. For how it fits together, see Core and periphery.

A relay built into Dassie, so that a new node is reached at its dassiepay.net address with nothing to set, is not there yet. What's next

Peers and how they settle

Your node finds its peers by itself: nodes that share a settlement hub with it. It joins a hub when you add the hub's scheme under Ledgers (see Your hubs), and dassie setup on the testnet joins the testnet's XRP hub unless you tell it otherwise. Your node peers only with nodes that speak its version of the peer protocol, so a node still on a 0.2 release never becomes its peer; see Protocol versions.

Select any node, in the graph or the list, to see its details:

Distance

How many hops away it is, or no route.

Settles with

The settlement schemes that node says it runs, by their IDs, such as hub-xrpl-testnet-xrp.

Neighbors

The nodes it lists as its own peers.

Peering

none, requesting, peered or terminating: how your node stands with it.

For a peer, the details go on:

Settles on

Each hub the two of you settle over, in the order you agreed, with what your node owes the peer there, net. A negative amount means the peer owes yours. A method may carry a badge:

  • Winding down: your node takes no new payments on it, asks the peer to settle once, then stops settling there. This happens, for example, while you remove that ledger.
  • Short of room: the peer has not settled for a while, so no payments go through it there until it does.
Status and Last heard

Whether the peer is online now, and when it last spoke.

Advertised

Whether your node tells the network it can route through this peer. A peer that is unhealthy for a while is taken out of that, and comes back once it is healthy again; it stays peered all the while.

Ending, because

Shown while a peering ends, with the reason.

For what peers, credit and holds mean, see Peers and holds.

End a peering

Your node ends peerings with peers that stay silent or short of room for long by itself. You rarely need to. If you do:

  1. Select the peer, and then Terminate peering.
  2. Confirm with Terminate.

Your node first asks the peer to settle once more, without saying why, and takes no new payments from it. Then it tells the peer, and once the payments in flight are done, the peering ends. What either side still owes stays on the books, to be settled if you peer again. The two do not peer again for a day, unless your node restarts.

Ban a node

A ban is for a node you never want to deal with. Select the node, then Ban node, and confirm with Ban.

Your node ends any peering with it at once: it stops routing through it and tells it now, without asking it to settle first. What it owes stays on the books. The details then say Banned by you. Your node never peers with it again until you select Unban node. A ban lasts across restarts.
